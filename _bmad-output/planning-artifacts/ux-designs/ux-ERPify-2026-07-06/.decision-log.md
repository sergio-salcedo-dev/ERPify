## E3 · Modelo de identidad (ratificado por Sergio) — substrato del UX

- **Invitación = modelo principal desde el día 1.** Un admin invita; el usuario acepta → define
  contraseña / MFA. **Nunca** alta libre dentro de una empresa existente sin invitación (debilita el control
  administrativo y complica identidad/autorización).
- **Alta pública = solo para el alta inicial de una empresa nueva** (si el negocio la necesita), como flujo
  independiente añadible más tarde. No es la forma base de crear usuarios.
- **Dos identidades que no se mezclan:** la **organización** (tenant/empresa) y los **usuarios** que pertenecen
  a ella. En un ERP el alta relevante es "crear empresa", no "crear usuario".
- **Convergencia de casos de uso** (una sola forma de crear el primer admin):
  `Self-signup → ProvisionOrganization → CreateInitialAdministrator`; `Admin UI → InviteUser`.
- **Dos bounded capabilities distintas:** *Provisioning de organización* (ocurre una vez) vs *Gestión de
  miembros* (invitar/reenviar/revocar/activar/desactivar — continuo).
- **Ciclo de vida de invitación:** Invitación (sin permisos efectivos) → Aceptación → Activación de identidad →
  Asignación de roles → Primer login → Autorización RBAC.
- **Cuatro capas limpias:** Identity (crear/activar identidad) · Membership (pertenecer a la org) ·
  Authorization (qué puede hacer, = RBAC ya cerrado) · Authentication (cómo demuestra quién es).

## E6 · Backbone de dominio — CUATRO máquinas de estado independientes (ratificado · Sergio 2026-07-06)

Corrección de fondo de Sergio: **no mezclar estado persistente de identidad con condición transitoria de
autenticación**. El backbone se descompone en cuatro responsabilidades ortogonales; ninguna pantalla es un
estado — cada pantalla es una **proyección** de estas máquinas. Estados híbridos prohibidos.

1. **Identity Lifecycle** — `INVITED → ACTIVE ↔ SUSPENDED ↔ DEACTIVATED`
   - **Sin `PENDING`.** Aceptar invitación ⇒ `ACTIVE` directo. El admin ya decidió al invitar; no hay evento
     de negocio entre *aceptar* y *puede trabajar*. Un `PENDING` solo añadiría "esperar otro clic del admin".
   - **Los roles se asignan ANTES de aceptar:** `Admin → invita → asigna rol → envía email → usuario acepta →
     ACTIVE`. **Nunca** un usuario activo que no pertenezca ya a la organización (membership-aware, ver E5).
   - **`SUSPENDED`** = pausa administrativa reversible (`ACTIVE ↔ SUSPENDED`).
   - **`DEACTIVATED`** = *"esta persona ya no pertenece a la empresa"* (employment ended). Técnicamente
     reversible (reactivable), **no** es suspensión prolongada, **no** implica borrado / GDPR / hard-delete.
2. **Invitation Lifecycle** (entidad propia, distinta del User) — `CREATED → SENT → (ACCEPTED | REVOKED | EXPIRED)`
   - Separarla del usuario habilita varias invitaciones, reenvíos, auditoría, métricas e histórico **sin**
     convertir al User en una máquina de estados gigante.
3. **Authentication State** (condición transitoria, NO ciclo de vida) — `Unlocked / LockedUntil(T)` (+ futuras
   `PasswordExpired`, `MFARequired`).
   - Ortogonal a Identity: `ACTIVE + Locked` o `ACTIVE + Unlocked` son válidos; `SUSPENDED + Locked` es
     **imposible** (un suspendido ni entra en el flujo de autenticación).
4. **Session Lifecycle** (máquina independiente) — `Active → (Revoked | Expired)`
   - Existe un **"dispositivo/sesión actual"** distinguible del resto.
   - **Cambiar contraseña ⇒ invalida las demás sesiones.** **Suspender/Desactivar ⇒ invalida sus sesiones.**
   - El usuario puede cerrar sesiones (mínimo "cerrar todas las demás"). UI mínima al principio (E7), pero el
     **modelo mental existe desde el día 1**.
   - Abiertas (en el radar, no bloquean Fase 1): ¿varias sesiones simultáneas? ¿granularidad por-dispositivo?

## E6.1 · Reglas transversales elevadas a invariante (ratificado)

- **[SEGURIDAD · transversal, no solo UX] Indistinguibilidad pre-identidad.** *Antes* de establecer la
  identidad del usuario, todas las respuestas deben ser **indistinguibles para un atacante**; *después* de
  autenticar, la app puede dar mensajes específicos y orientados a resolver. Aplica a login, forgot-password,
  reset, invitaciones, magic links, MFA y futuras APIs. (Los muros específicos — `SUSPENDED`/`LockedUntil` —
  solo se muestran POST-autenticación.)
- **[TOKEN] Opacidad total del token.** Un enlace no elegible **nunca** explica el motivo (usado / revocado /
  caducado / ya aceptado / eliminado = info interna). Solo *"Este enlace ya no es válido"* + una acción
  (*Solicita una nueva invitación* / *Contacta con tu administrador*). Tokens de un solo uso + caducidad.

## E7 · Proyección estado → superficie pública (de aquí caen las pantallas)

| Disparador (máquina · estado) | Superficie pública |
|---|---|
| Invitation `SENT` + token válido · Identity `INVITED` | **Accept invitation** (define contraseña) |
| Invitation `EXPIRED/REVOKED/ACCEPTED` (token no elegible) | **Access wall** opaco + acción (E6.1 token) |
| Identity `ACTIVE` · Auth `Unlocked` | **Login** → ERP |
| Identity `ACTIVE` · Auth `LockedUntil` | **Access wall** "bloqueada temporalmente" (post-auth) |
| Identity `SUSPENDED` | **Access wall** "acceso suspendido · contacta admin" (post-auth) |
| Identity `DEACTIVATED` | **Access wall** genérico (opaco; ver E6.1) |
| cualquiera | **Forgot password** siempre responde el mismo mensaje neutro (pre-identidad) |
| Session `Revoked/Expired` | re-login (silencioso salvo acción del usuario) |

## E11 · Resultado de la prueba narrativa — modelo estable + 3 reglas de proyección

Los 6 journeys + V1 (reabrir invitación aceptada) **fluyen sin ningún estado nuevo**. Afloran tres reglas de
**proyección** (comportamiento, no estados) a ratificar:

- **D-a** — el **muro de enlace no válido ofrece siempre «Iniciar sesión»** (además de *solicitar nueva /
  contactar admin*): rescata cobertura-perdida y reapertura de enlace aceptado **sin romper la opacidad**.
- **D-b** — un **reset con éxito limpia `LockedUntil`** (la recuperación puentea el bloqueo de autenticación).
- **D-c** — **`Session.Active` se crea solo para `Identity=ACTIVE`**; `SUSPENDED`/`DEACTIVATED` prueban
  identidad (credenciales válidas) pero **no reciben sesión**, solo el muro post-identidad. Frontera
  *autenticado ≠ admitido*.
- Refinamiento J2: tras reset, confirmación **no dramática** *"…hemos cerrado las demás sesiones abiertas."*

**D-a · D-b · D-c · refinamiento J2 → RATIFICADAS (Sergio 2026-07-06).**

- **D-c elevada a REGLA ARQUITECTÓNICA (Sergio).** Hay **tres momentos**, no dos: `credenciales válidas →
  identidad demostrada → evaluación de admisión → creación de sesión`. **Nunca** `credenciales válidas → sesión`.
  Ese matiz separa una arquitectura limpia de un login lleno de excepciones.

## E12 · Concern scan (ratificado · Sergio 2026-07-06)

- **Accesibilidad AA** — heredada de `pwa/DESIGN.md`; nada específico que añadir.
- **Resiliencia de conectividad (PRIORIDAD ALTA, no offline completo).** ERPify se usa en obras, sótanos,
  parkings, ascensores, mala cobertura. Principios de primera clase: (1) botones con **estado de carga claro**;

  sea posible; (5) **mensajes de error recuperables**. → *UX resiliente*, no offline-first.
- **i18n = español primero, arquitectura preparada para varios idiomas.** UI y emails en español; **ninguna
  cadena hardcodeada**. No invertir en traducciones aún, pero no impedirlas.
- **Foco / teclado** (crítico en flujos token): autofocus correcto, orden de tabulación, **retorno del foco
  tras errores**, compatibilidad con lectores de pantalla.
- **Motion** — heredado: respeta `prefers-reduced-motion`, transiciones discretas, evitar loaders innecesarios.
  Sin animaciones específicas de Auth.
- **Modo oscuro** — cubierto (heredado). Motivo: abrir un email a las 6:30 desde el móvil en modo oscuro debe
  sentirse el mismo producto. Sin diseño adicional si el DS ya lo soporta.

## E13 · Contrato de emails (ratificado)

- **Idioma:** el del usuario cuando exista; mientras tanto, español.
- **Remitente:** **evitar `no-reply`** (los usuarios responden por inercia) → `soporte@` / `hola@` / `seguridad@`
  (aunque desemboque en tickets).
- **Contenido:** extremadamente simple — **más comunicación bancaria que newsletter**. Sin marketing, imágenes
  enormes, banners ni colores llamativos.
- **Enlaces:** muy visibles, especialmente en móvil.
- **Pie legal:** sí, pero **mínimo**; no convertir el email en una página de texto.

## E14 · Señales de seguridad visibles al usuario (concern añadido por Sergio)

No es auditoría técnica: son **confirmaciones legibles tras cada acción de seguridad relevante**, siempre con el
**siguiente paso** claro. Ej.: *"Contraseña modificada correctamente"* · *"Invitación aceptada"* · *"Sesiones
cerradas"* · *"Esta invitación ya no es válida"*. Reduce la incertidumbre del usuario.

## E15 · Expiración de sesión (comportamiento documentado, sin pantalla propia)

`Session=Expired` → volver al login **conservando `?next=`** → mensaje breve: *"Tu sesión ha expirado. Inicia
sesión de nuevo para continuar."* No se diseña pantalla dedicada; es comportamiento del día a día del ERP.
