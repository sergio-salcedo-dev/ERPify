# Decision Log — Cuentas asociadas (Backoffice/Bank)

Canonical record of UX decisions. Spines (DESIGN.md / EXPERIENCE.md) are distilled from this at Finalize. Spines win on conflict.

## Entry 1 — 2026-06-10 — Captured context (carried from the originating conversation)

Pre-design intake from the Sentry/UX triage that spawned this feature. To be confirmed with Sergio, not treated as final.

**Problem origin.** `DELETE /banks/{id}` on a bank with associated accounts returns 409 `bank-in-use` (Sentry `ERPIFY-API-DEV-6`). Today the PWA shows a persistent error panel with **no recovery path** — a UX dead-end. The user can't see *which* accounts block the delete, nor act on them.

**Surfaces (existing backoffice web, desktop-first, responsive; stacked `<md`).**
- Banks list — `pwa/src/app/backoffice/banks/page.tsx` (+ `BanksTable` / `BanksStackedList` / `BanksCards`).
- Bank detail — `pwa/src/app/backoffice/banks/[id]/page.tsx`.

**Provisional direction (proposed, awaiting confirmation):**
- Show associated accounts at BOTH altitudes, different fidelity:
  - **List** = lightweight count signal (badge/column) — scan + delete-guard, NOT embedded account rows (keyset-pagination / N+1 cost).
  - **Detail** = full "Cuentas asociadas" section — the canonical place to understand & resolve the linkage.
- Phasing: Phase 1 detail section → Phase 2 list count → Phase 3 delete-guard.
- **Delete-guard**: when accounts > 0, prevent the DELETE before it fires (no 409 round-trip) + explain + "Ver cuentas" affordance.

**Anchor contract.** ux-ERPify-2026-06-03 (recoverable from git history): Code-first, scannable list; integral detail H1; badge AA dot-first; persistent mutation-error surface; confirm closes on failure. New work must inherit it.

**Architecture constraint (from Winston track).** `BankAccount` is a separate bounded context/aggregate; API today exposes only `countByBankId()` (no accounts read endpoint); no BankAccount context in the PWA yet. UX must not assume an account-detail page exists.

**Open questions (for Discovery):**
1. Account fields shown in the detail section + **IBAN/BIC masking** (PII).
2. First-N + "ver todas" vs paginated list in the detail.
3. Empty state copy when a bank has zero accounts.
4. Account row affordance — clickable to what? (no account-detail surface exists yet).
5. Realtime (Mercure) for the accounts section / count — in scope for v1?
6. Standalone accounts route, or detail-section + list-badge only?

## Entry 2 — 2026-06-10 — Sergio's decisions (confirmed)

**Working mode = Fast path.** Sally drafts both spines with `[ASSUMPTION]` tags in the gaps; Sergio corrects.

**Q2 — IBAN/BIC display = masked + reveal + copy.** Masked by default (`ES•• ···· 1234`). Add a **reveal toggle (eye), password-style "show momentarily"** — reveals the full value, then re-hides. PLUS a copy control (existing `<CopyButton>`) that copies the full value. (`[ASSUMPTION]` on the exact momentary mechanism: eye-toggle that auto-hides after ~10s / on focus-out, `aria-pressed`, accessible label "Mostrar/Ocultar IBAN".)

**Q3 — Detail depth = count + link only.** The bank detail shows **"Cuentas asociadas: N" + a "Ver cuentas" link** — it does NOT embed account rows. The actual account rows (with the IBAN reveal/copy control) live on a **new accounts-by-bank surface**.

**Resulting IA (3 surfaces):**
1. **Banks list** (`/backoffice/banks`) — per-row count badge (one batched `GROUP BY` query per page; index `IDX_53A23E0A11C8FB41` on `bank_account.bank_id` already exists). Badge → accounts surface for that bank.
2. **Bank detail** (`/backoffice/banks/{id}`) — "Cuentas asociadas: N" + "Ver cuentas" link. Delete-guard reads only the count (cheap, already `countByBankId()`); blocks the DELETE before it fires (no 409 round-trip).
3. **Accounts-by-bank list** (NEW) — `[ASSUMPTION]` route `/backoffice/banks/{id}/accounts`. The account rows: holder, IBAN (masked + reveal + copy), alias, currency, status. `[ASSUMPTION]` paginated later (keyset), simple `limit` now.

**Architecture handoff (Winston / next track):**
- Q3 means a **new BankAccount read context in the PWA** + an accounts read endpoint (`GET /backoffice/banks/{id}/accounts`) — more scope than an embedded detail section, but cleaner DDD (accounts owned by their own surface/context, not embedded into Bank detail).
- DB performance is a non-issue: single-bank counts are index scans; the list badge uses ONE batched `GROUP BY` per page (avoid N+1). Denormalized `bank.account_count` is a future escape hatch, premature now.

**Resolved open questions:** Q4 (account-row affordance → rows live on their own page) · Q6 (standalone accounts route = YES).
**Still open / `[ASSUMPTION]`:** exact reveal momentary mechanism · accounts route path · v1 realtime (assume static, no Mercure for accounts in v1) · delete-guard microcopy · empty state copy.

## Entry 3 — 2026-06-10 — Sergio confirms the 6 assumptions (now decisions)

Sergio reviewed the Fast-path drafts and **confirmed all six** open assumptions; they are promoted from `[ASSUMPTION]` to decisions in both spines:

1. **Accounts route** = `/backoffice/banks/{id}/accounts` (bank-scoped).
2. **IBAN "momentary"** = reveal toggle that auto-hides after **~10s OR on focus/hover loss** (timeout + blur).
3. **List count** = its own right-aligned numeric column (~72px, header "ACCOUNTS"), placed after Status, hidden `<lg`, **not sortable in v1**.
4. **Account rows do NOT navigate** in v1 (no account-detail surface yet).
5. **Delete-guard** = a **Popover** (neutral, non-destructive) anchored to the Delete control — not inline.
6. **Realtime** for the count/accounts = **deferred to v2** (static in v1).

**Remaining micro-`[ASSUMPTION]` (non-blocking for handoff):** accounts-table pagination timing (with Winston) · i18n (inherited, deferred) · `0`-count color nit (`text-subtle` vs `text-muted`) · single-IBAN-revealed-at-a-time · final guard popover wording.

Spines committed at this point. Next: optional Reviewer Gate / key-screen mocks, then `bmad-create-architecture` (Winston) + `bmad-create-epics-and-stories`.
