- (note) Origin: Shared/Images epic closed 2026-08-31 (img-1-1..3) shipped the pipeline, Image aggregate, ImageStorage port, DeleteImage and GET /api/v1/images/{imageId} with no consumer and no upload route; docs/adr/images-vs-documents-conservation-contract.md D6 names Bank.logoImageId and User.avatarImageId as the intended consumers
- (note) Mandate: invariant 4 of the conservation ADR makes the owning aggregate responsible for issuing delete(ImageId) on replace, on removal and on erasure of the subject; PRODUCTION_SECURITY_CHECKLIST.md section 7 items 2-6 and image-read-route-contract D1-D3 hand obligations to the first consumer
- (decision) No generic POST /images route: each consumer exposes its own raw-body PUT (and DELETE) on its resource, same shape as the Documents ingest PUT. Reason: a generic upload would need to know which consumer it serves to authorize it, and a mint-then-attach two-step leaves unattached images whose orphaned bytes are unfindable by construction (checklist 7 item 3). Discarded: generic upload + attach. Reversible by Sergio before dispatch
- (capability) CAP-1 Shared attachment seam (API): an authorized caller replaces or removes a consumer's single image through one raw-body request, and the previous image is released
- (constraint) Wire contract: the Infrastructure adapter turns the request body into bytes plus an optional declared media type; no UploadedFile, SplFileInfo, path, filename or URL reaches Application (conservation ADR invariant 6; guard TransportOnlyUploadedFileDenormalizer stays); the API is JSON-only except these raw-body routes
- (constraint) Replace order: mint the new image, hold its id on the aggregate in one transaction; the aggregate records ImageDeletionRequested for the previous id and the use case publishes it through the outbox, consumed after commit (ImageDeletionRequestedPublisherGateTest PUBLISHERS entry plus functional test required). If the attach fails after the mint, the new id is released by a compensating deletion request. Byte removal is never synchronous inside the owner transaction
- (constraint) An ImageId is held by exactly one aggregate instance and never copied (invariant 4): no clone or duplicate path may copy logoImageId, avatarImageId or the bank-account image id
- (constraint) Each consumer holds only the opaque id (private ?string $fooImageId, UUID v7, Uuid::ensure at the edge): no ORM ManyToOne to Image and no foreign key into image, because a foreign key makes the row deletion fail identically on every retry (checklist 7 item 2)
- (constraint) Per-identity-and-route rate limit on every new image write and read route, and a PWA fallback when an image answers 429 (checklist 7 item 5 is inherited by the first consumer); the edge body bound for raw-body routes follows the Documents upload gates (UploadRoutePathAgreementGateTest), never a lifted bound
- (decision) Read policy is declared per consumer in docs/adr/image-read-route-contract.md D1 (ImageConsumerAuthorizationGateTest forces it into the diff) and audit classification per consumer (BankLogo, UserAvatar, ...) per D2; the cache window D3 is re-examined against each consumer's deletion promise
- (capability) CAP-2 Per-consumer read policy: each consumer declares who may read its image, whether the read is audited and how long a client may keep it, recorded in the read-route ADR
- (capability) CAP-3 Bank logo: a back-office user with the bank update permission sets, replaces or removes a bank's logo, and the logo shows in the bank list and detail
- (constraint) Bank deletion and logo replacement release the logo bytes; BankSnapshot rides in BankCreated/Updated events and the read models, so the logo id joining it is an event-contract change the story decides against the event-catalog versioning rule
- (capability) CAP-4 User avatar: a user sets, replaces or removes an avatar, and erasing the identity releases the avatar bytes
- (decision) User::$avatarImageId is classified non-person in api/.person-reference-policy (it holds an image id, not a person id; checklist 7 item 4 says so) so it takes no PersonSubjectReference and no PersonReferenceSource; the erasure obligation is carried by FulfilIdentityErasure publishing the deletion request in its own transaction and by #[PersonalData] sealing the avatarImageId diff in audit_log with the subject's scope (invariant 4 consequence 3). Corrects the brief, which framed it as a person reference
- (constraint) An avatar read is a read of a personal record: its audit resource type is person-denoting and needs an erasure use case wiring AuditResourceAnonymiser plus an acceptance scenario proving no row survives (api/.audit-resource-types), or the story records why the read stays unaudited
- (capability) CAP-5 Bank-account image: a user with the bank-account update permission sets, replaces or removes the image of a bank account, with the same release guarantees
- (question) What does the bank-account image depict (card, cheque, logo, holder)? It fixes whether it denotes a natural person, hence its audit classification and whether EraseBankAccountSubject must release it
- (question) Who may set an avatar: only the user on their own profile, an administrator on behalf of another user, or both? Decides the permission and confirms the credential re-proof rules do not apply (an avatar is not a credential)
- (question) May any authenticated identity read any avatar? If an identity class outside the back-office (frontoffice or portal) can hold a session, bare authentication is a cross-user read of a face; the alternative is a consumer-scoped read route with its own voter. Story ic-4 decides before code
- (question) Cache window for avatars: keep private max-age 3600 or move to no-store once a deletion promise for an erased person exists (read-route ADR D3: a zero SLA means no-store)
- (question) Does the logo id travel in BankSnapshot and the read models (list shows the logo without a second request) or is it read from the aggregate; consequence on event version and projection rebuild
- (capability) CAP-6 PWA image seam: one reusable upload-and-display component pair with an English-copy, accessible, ProblemDetails-aware flow that every consumer screen composes

- (direction) Three-layer review of the spec (2026-11-16, PR #1251): Blind Hunter, Edge Case Hunter, Acceptance Auditor. Findings deduplicated and the expensive claims re-verified against the tree before applying.
- (question) OPEN, being consulted externally (Sergio, 2026-11-16): how images are read. The shared GET /api/v1/images/{imageId} holds no owner, so it cannot carry a per-consumer audience, audit type or cache window. Options: (A, provisional) the avatar gets its own owner-scoped read route with its own voter, audit type and cache, while logo and bank-account image keep the shared route with the ADR D1 recording the audience as the authenticated session; (B) one read route per consumer; (C) shared route only. Gates ic-4 and the read half of ic-3 and ic-5.
- (question) OPEN, being consulted externally (Sergio, 2026-11-16): how an avatar write is audited. User is deliberately not an AuditedEntity (password_hash), so #[PersonalData] on avatarImageId seals nothing and an avatar change leaves no audit row. The sealed-diff claim is dropped from the spec either way. Options: (A, provisional) an explicit AuditLogger row of a person-denoting type with an erasure owner and acceptance scenario; (B) audit User excluding password_hash and the lockout fields, plus destroyScope in the identity erasure; (C) no write audit.
- (constraint) Edge: every PHP request outside the Documents content PUT is bounded at 1 MB by Caddy and a cut body reaches PHP as a clean shorter stream, so an image PUT would store a truncated image. Image write routes get their own cookie-gated Caddy matcher bounded at erpify.images.max_input_bytes, a mandatory Content-Length, and a byte count that must equal it; UploadRoutePathAgreementGateTest covers both matchers; a through-Caddy test sends more than 1 MB.
- (constraint) Concurrency: the attach transaction loads the owner FOR UPDATE (Bank gains findByIdForUpdate; User and BankAccount have it), reads the old id under that lock, treats a vanished owner as 404 and compensates the new id. Lock order (user row before image) is declared beside ErasureLockOrderTest.
- (constraint) Compensation order: store bytes, then one transaction attaches the new id and queues the old id's release; on failure roll back, then publish the release of the new id in a fresh transaction (publishing inside the failed one rolls back with it). Crash, OOM and a failure inside UploadImage after store() leave an orphan: accepted, recorded in checklist section 7 item 3. The consumer-scoped route narrows the mint-then-attach window, it does not remove it.
- (constraint) Errors: the five Shared/Images exceptions extend the native DomainException with no ErrorContract marker, so an HTTP caller gets 500. ic-1 maps them to minted Problem Details types (413, 415, 422, 411) and edits docs/api-error-contract.md. A decodable polyglot is re-encoded and stored, so its criterion is that the stored bytes carry no trailing payload, not a 4xx.
- (constraint) ImageConsumerAuthorizationGateTest asserts an empty list with no registry and its regex needs a capital-I ImageId suffix, so BankAccount::$imageId would escape it and any real holder turns it permanently red. ic-1 redesigns it as a registry property => anchor in read-route ADR D1 with a code-derived universe; the bank-account holder is named $accountImageId.
- (constraint) #872: ImageDeletionRequestedPublisherGateTest PUBLISHERS is empty. A shared Shared/Images replace service is the creating site, registered with its use case and a functional test following the rollback recipe, so ic-3..5 never edit that constant. ic-1 also owns the section 7 row and ADR tag edits and the section 7 items 2, 5 and 6 updates.
- (constraint) Erasure: EraseBankAccountSubject releases the image unconditionally (invariant 4 binds every owner removal; personhood decides only the audit type and #[PersonalData]). The identity erasure reads avatarImageId under findByIdForUpdate before users->remove, adds a result category avatar_release_queued, and its wording says queued, not erased.
- (constraint) Spool and session: the plaintext of an uploaded image sits in the PHP tmpfs spool until the worker serves another request, and the session lock blocks the user's other requests during a slow PUT. ic-1 generalises the spool-discard listener (a shared one, not an import of Documents) and releases the session lock before streaming; authorization runs before the body is read.
- (constraint) Content-Type: the adapter hands the declared type to the processor only when it is a clean image/* token and ignores anything else; the served type comes from detection. DELETE is idempotent: 204, no event when no image is held. The wire contract lives in wire-contract.md, a spec-authored companion.

- (decision) Read: the avatar gets its own owner-scoped read route resolving the image only through the target user's current avatarImageId, with its own voter, audit type and cache window; logo and bank-account image keep the shared GET /api/v1/images/{imageId} and read-route ADR D1 records that their audience is the authenticated session. Confirmed after an external consult (Codex agreed with the same option on both decisions). Reason: the shared route holds no owner, so it cannot carry a per-consumer audience, audit type or cache.
- (decision) Hole the consult did not name: the shared route serves any image id to any authenticated session and an id is not a secret, so an avatar id exposed in a Resource DTO would let a session bypass the owner route's voter, audit row and no-store. The user Resource DTO therefore exposes a boolean hasAvatar, never the id, and the owner route is the only product path to avatar bytes. A leaked or enumerated avatar id still reaches the shared route (cache max-age 3600 included): residual recorded in checklist section 7 items 5 and 6 and in ADR D1, not closed, because closing it needs a kind on Image, which the module refuses by construction.
- (decision) Audit: an avatar write (set, replace, remove) writes an explicit AuditLogger row of the person-denoting type UserAvatar, in the same transaction as the mutation and the queued release, with an erasure owner (AuditResourceAnonymiser) and an acceptance scenario. The row records operation, actor and subject, never the image id. The claim that #[PersonalData] seals the avatar diff is dropped: User is not an AuditedEntity (password_hash), so no diff is captured. User stays unaudited.
- (decision) A batch avatar-read endpoint to absorb list fan-out is rejected as speculative (YAGNI); the read budget is sized against a list page in ic-1 and the cache window stays an open question for ic-4.
