topic: Optional TOTP two-step verification for the ERPify Iam/Identity context (MFA half of DW-42)
updated: 2026-11-22T18:16

- (direction) Owner (2026-11-22): two-step verification is OPTIONAL for every user including ADMIN, OFF by default, each user enables it when they want. No enforcement flag, no grace period; per-role enforcement is a later small policy change and is not built now.
- (direction) Owner: TOTP with single-use recovery codes first; the second factor sits behind a port so WebAuthn/passkeys can be added later. No SMS.
- (direction) Owner: the TOTP secret is a state-oriented aggregate (not event-sourced), sealed with the existing Shared/Crypto envelope under a per-identity scope so GDPR erasure crypto-shreds it.
- (direction) Owner: enabling re-proves the current password; DISABLING requires a valid current code (app or recovery code) so a stolen session cannot remove it.
- (direction) Owner: login shows the second step only AFTER a correct password; users without it see no change; no response or timing difference may reveal whether an account has it (D10, pre-identity floor).
- (direction) Owner: the recovery-secret channel must NOT bypass two-step verification for an identity that has it enabled.
- (direction) Owner: lost device is covered by recovery codes; another administrator can reset someone's MFA (caller password re-proved, audited, self-reset forbidden, like self-unlock-forbidden); last resort is an operator console command like organization:administrator:create.
- (direction) Owner: admins are alerted when a privileged identity is locked out; adaptive throttling stays rejected (administrative-recovery-channel ADR); the DoS half of DW-42 is otherwise accepted risk because the lockout is pre-second-factor.
- (direction) Owner approved the proposed story order: port+aggregate+secret+enrol; login second step; recovery codes and disable; admin reset and operator CLI; privileged-lockout alert; PWA surfaces.
- (capability) CAP-1 A signed-in user can enable TOTP: password re-proved, secret shown once, active only after a valid code confirms it.
- (capability) CAP-2 A user with TOTP enabled completes a second step after a correct password on EVERY path that would mint a session, and nothing observable differs for users without it.
- (capability) CAP-3 Recovery codes: ten single-use codes shown once at activation, accepted at the second step and to disable.
- (capability) CAP-4 A user can disable TOTP by presenting a valid current code.
- (capability) CAP-5 Another administrator, or an operator on the console, can reset a user's TOTP when the device and codes are lost.
- (capability) CAP-6 Erasing an identity deletes its TOTP rows and destroys the key that sealed the secret.
- (capability) CAP-7 Administrators are alerted when a privileged identity is locked out.
- (capability) CAP-8 The PWA offers the login second step and a profile panel to enrol, view recovery codes once and disable.
- (capability) CAP-9 Every state change and refusal of the second factor is recorded in the audit trail.
- (constraint) Code facts: there is no challenge or partially-authenticated concept today; IS_AUTHENTICATED_FULLY is the only level and the session is minted inside LoginSuccessEvent (SessionMintingSuccessListener, priority -128).
- (constraint) Five paths mint a session through ReauthenticateDevice/Security::login: login, reset-password completion, invitation accept, change-password, recovery redeem. The gate must cover every one that can reach an identity with TOTP, or provably cannot.
- (constraint) The firewall token is serialised into the native session even after invalidate(); a withheld mint must clear token storage (setToken(null) + invalidate) as RedeemRecoverySecretController does, or the session stays authenticated.
- (constraint) Second-step failures must collapse into the uniform 401 and pay PreIdentityTimingFloor; the proof is a STRUCTURAL test, never a wall-clock assertion (docs/rules/security.md).
- (constraint) Wrong second-step codes spend their own per-identity budget and never feed the persisted email-keyed lockout (same reasoning as CurrentPasswordProofThrottle).
- (constraint) A code is accepted at most once: the last accepted time step is stored and a code at or before it is refused; window is plus or minus one 30 s step; 6 digits, HMAC-SHA1 (RFC 6238); changing algorithm, digits or period invalidates enrolled users.
- (constraint) Recovery codes are stored only as digests of high-entropy values, consumed atomically, shown once; the TOTP secret is never logged or returned after activation (SensitiveParameter on every plaintext parameter).
- (constraint) The secret is sealed with an AAD bound to the identity; erasure follows the EraseBankAccountSubject pattern (lockState, delete row, Keystore::destroy with DestroyReason::Erasure) and writes an evidence action registered in .audit-evidence-actions.
- (constraint) Registries every story touches: api/.route-manifest.json, .credential-proof-policy, .person-reference-policy plus PersonReferenceSource, .audit-evidence-actions, .audit-resource-types, .behat-step-vocabulary, docs/api-error-contract.md, PRODUCTION_SECURITY_CHECKLIST.md, a new ADR; deptrac needs no registration inside Iam/Identity.
- (constraint) Admin reset is an authority-affecting write: it re-proves the CALLER password through ProveActorPassword (ADR D11 pattern), refuses self-targeting before the transaction, and is audited.
- (constraint) The privileged-lockout alert runs from the identity_maintenance schedule, never from the failing login (timing oracle), carries no exercisable material, and must not filter locked_until in DoctrineActiveAdministratorDirectory (closed and rejected).
- (constraint) PWA: LoginOutcomeKind gains a second-step outcome routed by problem.type, never status alone; secret and recovery-code displays follow the PasswordInput/CopyButton rules; testids follow the contract.
- (assumption) Story checkpoints were set by the assistant under the owner's instruction to ask only for blockers: spec_checkpoint on the login and admin-reset stories, done_checkpoint after the login story; the owner may change them.
- (assumption) Reset-password completion and invitation accept are treated like recovery redeem: an identity with TOTP enabled needs the second step there too (extension of the owner's decision on recovery, same bypass reasoning).
- (assumption) Privileged means Role::ADMIN (enforced via in_array on roles); there is no separate flag.
- (assumption) The alert goes by mail to the other active administrators, since no in-app notification model exists; the owner of the locked identity is already told by NotifyLockedIdentities.
- (assumption) TOTP is implemented in-house over hash_hmac and tested with the RFC 6238 vectors (no new runtime dependency); no TOTP library exists in composer.lock.
