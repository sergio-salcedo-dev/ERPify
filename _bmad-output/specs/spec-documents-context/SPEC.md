# Documents bounded context — evidence-class binaries

## Why

A mandate and a vision. The ERP targets construction, which produces technical documentation whose **original byte is the proof**: drawings, reports, contracts, certificates, RAW, and the site photograph attached to a progress certificate. The images module re-encodes and strips on purpose, so it destroys exactly what makes these evidence. Nothing in the tree accepts evidence yet: the images pipeline rejects non-image formats, but a site JPEG passes `UploadImage` and is stripped (the ADR D3 misfiling hazard). Guidelines are fixed now so that the first `Documents` story inherits decided boundaries and named open questions instead of rediscovering them. Boundary authority: the accepted ADR in `companions:`.

## Capabilities

- **CAP-1**
  - **intent:** A caller can file an evidence-class binary, which is stored untransformed with its digest, actor, date, legal basis and retention policy recorded.
  - **success:** The bytes read back and decrypted equal the uploaded bytes, and the recorded digest equals the digest of the uploaded bytes. A truncated or aborted upload leaves no document and no object in the final namespace, and its key is destroyed within the reaper bound. The acceptance reads through the storage port and the decryptor in a test, since ingest exposes no read route.
- **CAP-2**
  - **intent:** A document is consumable only once it is scanned and ready; scanning classifies and never cleans.
  - **success:** A read in `Received`, `Scanning`, `Quarantined` or `ScanFailed` is refused with a defined RFC 9457 problem type; only a read in `Ready` returns bytes. The refusal is one guard on the `Document` aggregate (`assertReadable()`, owned by doc-4), not a check in a controller.
- **CAP-3**
  - **intent:** Originals are sealed at rest under a key scoped to the document, with peak memory independent of the size of the original.
  - **success:** The peak memory of sealing an original of 1 MiB and one of `MAX_ORIGINAL_BYTES` (measured, not asserted) differs by less than a bound doc-1 fixes by measurement, and both decrypt back byte-identical.
- **CAP-4**
  - **intent:** Erasure ends the conservation contract by destroying the document's key, from any non-terminal state, leaving digest and custody record intact.
  - **success:** After erasure the content cannot be decrypted, sealing under the same scope is refused, and digest and custody remain readable.
- **CAP-5**
  - **intent:** Derivatives of a document (previews) are materialised through the images module with their origin recorded, and die with it.
  - **success:** After erasure, the variant URL answers 404 or 410, no `Image` row with that origin remains, and no storage key for it remains; a derivative that arrives after erasure is deleted on arrival.
- **CAP-6**
  - **intent:** Each state change of a document is recorded, and the document's metadata and custody trail can be listed in order.
  - **success:** The ordered sequence of states of one document can be listed, including after erasure.
- **CAP-7**
  - **intent:** A new version is a new immutable original linked to its predecessor, never a modification.
  - **success:** Both versions are retrievable with distinct digests until erased; erasing one leaves the other's link to it as a readable tombstone.
- **CAP-8**
  - **intent:** Scanned PDFs yield a searchable text derivative.
  - **success:** A phrase present only in a scanned page is found by search; the text derivative dies with its document.
- **CAP-9**
  - **intent:** An authorised user can read a `Ready` document, and the read is audited.
  - **success:** The route declares its voter, refuses non-`Ready` states (CAP-2), writes an audit row, and serves the bytes with `nosniff` and a locked-down `Content-Security-Policy`, under a fixed `Content-Disposition: attachment` with no filename parameter (the sealed name is never put in a response header).

## Constraints

- **Decided (the user, 2026-10-30): state-oriented persistence plus a custody log.** `Document` is a snapshot row; every transition also appends a `document_custody` row in the same transaction, except the scan lease returns named under Custody guarantees. Event sourcing was rejected on measurement: the event store has no per-aggregate stream loading (`DbalEventStore::stream()` is a global, sequence-ordered projection feed), and its `aggregate_version` is informative (`DbalEventStore::append()` computes `MAX+1`, under a `UNIQUE (tenant_id, aggregate_id, aggregate_version)` from `api/migrations/2026/Version20260616201857.php` that never fires because `tenant_id` is always `NULL` and PostgreSQL treats `NULL`s as distinct), so it would first need aggregate loading, optimistic concurrency and a serialised append. `document_custody` is not `audit_log`: reads stay in `audit_log`, which has a retention prune; custody never expires.
- **Custody guarantees.** The aggregate is loaded under the lock (`PESSIMISTIC_WRITE`, or re-read after `SELECT … FOR UPDATE`), so the compare-and-set never runs against a stale snapshot; `seq` is computed inside that same transaction. `UNIQUE (document_id, seq)` is the second defence, not a substitute, and a violation of that constraint maps to a retry, never a 500; a unique violation is mapped by constraint name, so the idempotency-key constraint (and the successor constraint doc-9 adds, if any) maps to a conflict and is never retried. The first row (`seq` 1) has no row to lock: the document insert and its first custody row share one transaction and only the `UNIQUE` guards it. The global lock order is upload-intent rows, then documents (a document's custody rows travel with it), then keystore rows, each class in ascending id. The claim's transaction-scoped advisory locks (per actor, then global) are taken after its own intent row and nothing else is acquired while one is held. Within one document it is document, then keystore; ingest and a new version lock their intent row, then only the keystore row of the new, not-yet-visible scope (reachable only through the intent lock the commit holds, which is the one sanctioned inversion of the class order) and, for a new version, the predecessor document, and never the keystore row of an existing document without that document first. A series erasure takes one document per transaction. A repeated erasure appends nothing. `Erased` is a snapshot state, never a row delete, and the custody foreign key has no cascade. Custody rows are never deleted and are updated by no statement except the single sanctioned actor-anonymisation one decided below. `DocumentCustody` is mapped read-only after insert (`#[ORM\Entity(readOnly: true)]`, so the ORM emits no `UPDATE` for it), the gate also refuses `remove()` on it, and the sanctioned statement is the only DBAL write. A `deadlock_detected` maps to a retry wherever it can occur, from doc-2 on. **Enforcement is a new source gate and engine over `api/src` in the style of `SanctionedLogMutationGateTest` (whose `SANCTIONED` set and `TABLES` cover `event_store` and `audit_log` only), classified in `api/.artifact-gate-placement`, and nothing more:** no database role separation, `GRANT`, `REVOKE` or trigger exists in the tree, the gate sees neither a migration nor runtime-built SQL, and adding a restricted role or a `BEFORE UPDATE/DELETE` trigger is a separate decision. Custody stays readable after the key is destroyed and is not claimed cryptographically immutable. Custody records the first scan claim since the last operator decision, every verdict (including `ScanFailed` reached by either cap or by a deterministic failure) and every operator decision; a lease return (`Scanning` back to `Received`) and a re-claim are counted on the snapshot and write no custody row, an explicit exemption from "every transition appends" that the ordered listing of CAP-6 accepts.
- **Decided: a version is its own `Document` aggregate.** It carries its own bytes, digest, key scope, retention, scan lifecycle and custody. It links to its predecessor by an immutable id and to its series by a scalar series id (the first version's series id is its own id); these two columns exist from the first migration and nothing else about versioning does. No series aggregate exists before doc-9 (a pointer design would introduce a series table whose row is not an aggregate) and a read projection lists versions. A consumer references the exact version it relied on. **The accepted chain is linear; failed attempts are siblings.** The use case authorises the caller on the predecessor (a voter) before sealing and answers "absent" and "forbidden" with the same problem type, so the conflict response leaks neither existence nor state; the short transaction that inserts a new version also takes `FOR UPDATE` on the predecessor row (after the new scope's keystore row, per the lock order above) and rechecks that it is `Ready`, because the predecessor's state when the upload began proves nothing; the lock is taken after the new bytes are sealed, never across the stream, so an upload cannot block the predecessor's erasure. The loser of a successor race has already sealed bytes and a key: it falls into the aborted-upload class and maps to a conflict. A tombstone keeps id, digest, declared size, the retention fields (`retention_reason`, `legal_basis`, `review_at`), the key hash (nulled by the actor's erasure), `series_id`, `predecessor_id`, state and timestamps, which name no person; everything else is gone or sealed, and a replay against an `Erased` original compares exactly those. **The mechanism that refuses a second live successor is decided by doc-9, not here (the user, 2026-11-04).** No node has a child before versioning ships, so doc-2, doc-4 and doc-7 carry no slot column, index or walk-up. doc-9 compares two designs and records the choice: a `holds_slot` flag with a partial unique index on `predecessor_id`, kept consistent by a locked walk-up over the contiguous `Erased` ancestors on every transition that takes or frees the slot (entry to `Quarantined` or `ScanFailed`, an operator reopen, `Erased`); and a series row whose head pointer moves by one `UPDATE` under the row lock, which the assistant leans to because it removes the ancestor walk. A `version_no` with `UNIQUE (series_id, version_no)` alone is insufficient, since it does not refuse two concurrent successors of one predecessor. Whichever is chosen keeps these properties: a child that ended `Quarantined`, `ScanFailed` or a childless `Erased` frees the slot, so a corrected version is filed as a sibling; erasing a node that still has a live descendant never opens a fork; reopening a `ScanFailed` document whose slot a replacement already holds maps to a conflict, and a reopen takes `FOR UPDATE` on the predecessor and refuses with a conflict when it is `Erased`; an `Erased` middle node blocks a successor (it needs a `Ready` predecessor) and the projection renders the gap and orders by creation, not by chain position; when the last live descendant under a contiguous run of `Erased` nodes is erased or quarantined, the whole run stops holding the slot; a new version's `series_id` is copied from the locked predecessor row, never from the caller; the predecessor lock orders successors but does not exclude them, only the mechanism refuses the second; of two concurrent reopens of `ScanFailed` siblings only one wins; the design states where its lock (the ancestor set or the series row) sits in the global lock order, and a reopen takes the predecessor (or the series) before its own row, loading itself unlocked and revalidating, so the order stays ascending; documents that exist before doc-9 are backfilled in its migration (a series row per `series_id`, or the flag's default); a unique violation maps to a conflict by constraint name and is never retried, and a `deadlock_detected` maps to a retry. Until doc-9 the declare DTO has no predecessor field, `predecessor_id` is written `NULL` and `series_id` equals the document's own id, so no code path can create a successor. doc-9 amends the doc-4, doc-7 and lock-order paragraphs if it needs to.
- **Decided: the first evidence adapter is the local filesystem behind the `Documents` port**, and the port declares no WORM guarantee an adapter cannot enforce. S3 with object-lock waits for a first consumer and a defined retention vocabulary; the port keeps the move reversible (ADR D6). **Before first real use** (owned by doc-3, verified before doc-5 serves real documents) the stored bytes need an encrypted offsite backup, digest verification and a proven restore of originals and metadata: a database dump is not a backup of the evidence. Two tracked proof records, this one and the restore drill with ledger replay, live at a path and in a format doc-3 fixes; a gate test in doc-5 reads them and fails when the tracked production configuration sets `documents.read_enabled` true while either is missing, and the read route answers 404 while that parameter is false (default false outside dev and test). **Ordering on the local filesystem.** Before any byte is sealed, a durable upload-intent record (created by the declare step of the transport decision; mechanism chosen in doc-3) holds the document's scope id (an `EncryptionScopeId` of type `Document` whose id is a random UUID), the actor, a lease expiry and a heartbeat, and is a state machine the PUT claims (the derived bullet after the transport decision). The scope id is random, is the document's own from that moment, is stored on the row under a `UNIQUE` (two documents sharing a scope would let one's erasure shred the other's bytes), and the staging key embeds it, so promotion needs no re-seal; the stream seal's associated data binds the scope, never a storage path. The seal mints the key under that scope and commits on its own: no database transaction spans the stream, and a long upload renews its lease by heartbeat or the lease outlasts the bound on upload time. Staging sits on the same mount as the final namespace (`rename(2)` is atomic only within one filesystem) with the file and its directory synced; at boot the adapter creates a probe file in staging, renames it into the final root and removes it, and refuses to start on any failure: `st_dev` equality is not proof, because `rename(2)` fails with `EXDEV` across two mount points even when both are one filesystem, and every promotion would then fail after the commit. A short transaction then locks the intent row, then the keystore row of the scope (through a `Keystore` method added in doc-1 that locks the row and reports live, tombstoned or absent, since `wrappedDekFor()` filters tombstones out and cannot tell them from absence), asserts that the intent is `Streaming` with a live lease and a deadline not passed and that the scope is not tombstoned (the actor and the key hash come from the locked intent row, never from the writer's memory), inserts the `Received` row and its first custody row, and commits; the object is renamed to final and the final directory synced after that, `promoted_at` on the snapshot is then set by compare-and-set, and the scan message is dispatched only after that. **The intent row is the one lock the commit and the reaper share.** The reaper locks the intent row, then the keystore row, rechecks under both locks that the intent is expired (its TTL, lease or deadline passed, or its state `Expired`) and that no `Document` row holds the scope (when one does, the intent is deleted without a tombstone), and only then tombstones and deletes the intent in the same transaction (an intent that was never claimed, `claimed_at` `NULL`, is deleted without a tombstone; one that was claimed is tombstoned whatever state it has been moved to since); the commit locks them in the same order. Lease expiry is judged by the database clock (`NOW()`), never the application's. A `NOT EXISTS` inside the reaper's `UPDATE` would not do, because under `READ COMMITTED` its snapshot predates a row that commits while the `UPDATE` waits on the lock. A writer whose heartbeat finds its intent gone or expired aborts and deletes its own staged file, and an age sweep over the staging namespace deletes any staged object older than the upload bound plus a margin that has neither a live intent nor a row. **A committed row owns its staged object:** the reaper acts on intents, never deletes a staged object whose scope has a row and never destroys that scope; a sweep rolls the promotion forward for a `Received` row older than a bound with `promoted_at` `NULL` (the rename is idempotent and accepts the final object already present), sets `promoted_at` and then dispatches the scan; a filesystem stat cannot sit in an SQL predicate, so the scan claim and the scan sweep require `promoted_at` not `NULL`, and rows awaiting promotion never starve the scan sweep. The roll-forward sweep acts on `Received` rows only and skips an `Erased` one: the object of an `Erased` row belongs to the delete step decided below, and a roll-forward rename rechecks under the document row lock that the row is still `Received`. A final object with no row cannot arise in the normal flow (the row commits first); it appears after a restore to an older dump or by hand, so the sweeps **alarm on it and delete nothing in the final namespace for a scope that has no row** (outside a ledger replay), and the restore step disables the sweeps and the reaper along with the writers. The one deletion in the final namespace is the `Erased` delete step, keyed on an `Erased` row (or, during a ledger replay, on a ledger scope with no row). The sweeps also alarm on rows with no object anywhere, except `Erased` rows. The stream seal authenticates truncation (the last chunk carries a final-chunk marker in its associated data), so a short file from a partial restore or a full disk fails instead of decrypting as a prefix. Each chunk's nonce or associated data also binds its 64-bit index and the final flag, so reordering, duplicating or dropping a chunk fails authentication, and the unseal refuses any byte after the final-marked chunk; the filesystem adapter has no WORM guarantee, so tampering with a sealed object is detected at read, not prevented. A `Ready` document whose bytes are missing, mismatch the digest or whose scope is tombstoned (`DekDestroyed` on decrypt) fails closed with a defined problem type and an alarm. A read that finds the object gone or the scope destroyed re-reads the row first: an `Erased` row answers the gone problem type with no alarm, and only a row still not `Erased` alarms, so an erasure that commits between the read's snapshot and its open is not reported as lost evidence.
- **Mechanisms the capabilities lean on.** Ingest is a dedicated `UploadEvidence` use case; sealing is a stream-oriented sibling of `EnvelopeEncryptor` over `EncryptionScopeId` (one scope per document); erasure is `destroyScope()`. The sibling must keep the existing guarantee that sealing under a destroyed scope throws `DekDestroyed` instead of minting a fresh key; a test seals, destroys, seals again and expects refusal. **Until doc-1 closes it, that guarantee has a hole:** `DbalKeystore::destroy()` is an `UPDATE … WHERE destroyed_at IS NULL`, so on a scope never minted it affects zero rows and leaves no tombstone, and `SodiumEnvelopeEncryptor::mint()` then mints a live key for a late writer. Erasure and the staging reaper therefore leave a tombstone even when no key was minted (`destroy()` upserts a destroyed row; `kek_version` is `NOT NULL`, so the row carries a KEK version and a null `wrapped_dek`; the current version is a private constant of `SodiumEnvelopeEncryptor` that `destroy()` cannot see, so doc-1 passes it through the port or states a sentinel; the upsert is first-writer-wins and never changes the `reason` or `destroyed_at` of an existing tombstone, so a stale aborted-upload reap cannot relabel an erasure), and `Erased` is decided by the aggregate's compare-and-set, never by the boolean `destroyScope()` returns, which is `false` both for a repeat and for a scope that never existed. A test destroys an unminted scope, seals, and expects `DekDestroyed`. A tombstone carries a `reason` on the keystore row (`aborted-upload` or `erasure`) and is never classified by the absence of a ledger entry; the erasure ledger does not carry aborted-upload scopes, and the tombstone reconciler is driven by `Document` rows, so any non-`Erased` row whose scope is tombstoned is an alarm whatever the ledger says. **The existing `DbalSubjectErasureReconciler` must be amended in doc-1:** its query selects every destroyed `dek_keystore` row with no `SUBJECT_ERASED` audit row and filters on neither reason nor scope type, so left alone the scheduled reconciler logs every aborted-upload and every `Document` tombstone at `error` level as a GDPR divergence, for ever, burying a real one. It excludes `aborted-upload` tombstones and `Document` scopes, which the Document-driven reconciler owns; a test plants one of each and expects `unreconciledScopes()` to be empty. **Erasure converges across its stores:** the `Erased` transition, its custody row and the key destruction commit together or are re-drivable from a recorded intent, with a scenario for a crash at each point. **The scanner never makes plaintext reach persistent storage:** the scan decrypts after sealing and streams to the scanner, size limits are measured against `MAX_ORIGINAL_BYTES`, and exceeding one ends in `ScanFailed`, never `Ready`; the scanner decision below states what that means for its temporary files.
- **Decided (the user, 2026-11-04): a zero-length original is refused, and `MAX_ORIGINAL_BYTES` is 100 MiB.** What follows from it, not separate decisions: the refusal comes before the upload-intent record exists, so it leaves no keystore row and no tombstone (it is refused at the declare step of the transport decision, on a declared size of zero), and the stream seal never receives an empty stream from this use case. Exactly 104,857,600 bytes is accepted at the declare step and a larger declared size is refused there; a body that runs past the size it declared aborts the upload at the first extra byte, counted before each chunk is sealed or staged; a writer that detects the overflow itself deletes its staged file and expires its own intent under the shared lock, the reaper tombstones as usual, and the upload falls into the aborted-upload class. The constant is also the size the scanner limit is measured against: once the scanner is chosen a gate compares the two and the scanner's real limit is verified then, not assumed; a scanner whose limit is below the constant fails the gate, and resolving that mismatch is a new decision. There is no multi-gigabyte promise: CAP-3 asks for peak memory independent of size.
- **Body bounds of the upload route (a consequence, sized in doc-3).** `api/frankenphp/Caddyfile` caps every request PHP serves at `1MB` with `request_body @frontController`, matched on `index.php` after the rewrite, so the upload route needs a bound of its own, scoped to the original path (`{http.request.orig_uri.path}`) so that the 1 MB block does not also cap it (`api/config/services.yaml` says the same). Caddy's `MB` is 10^6 bytes, so the bound is written in bytes; the body is the original, so it equals the cap and needs no framing allowance. Caddy applies the bound as the body is read and promises no 413: the mandatory `Content-Length` and the end-of-stream byte count of the transport decision are what keep a body it cuts off from reading as a complete shorter original, and the application answers with a Problem Details. `post_max_size`, `upload_max_filesize` (unset in `api/frankenphp/conf.d`, so PHP's defaults apply), the upload temp directory and the request time limit are in the same set; whether they apply to a raw body is measured by the transport spike, not assumed.
- **Decided (the user, 2026-11-04): the sealed object of an `Erased` document is deleted, never kept on purpose.** Deletion is a post-commit step, idempotent and re-driven by a sweep, with an alarm on an object older than a bound measured from the `Erased` custody row; a failed delete never rolls the erasure back. What follows from it: this sweep is the single owner of the object of an `Erased` row; it removes the staged path first and then the final path, tolerates ENOENT on each and counts a row done only when neither exists, because a writer's post-commit rename can race an erasure and recreate the final object (the writer treats ENOENT on its own rename as normal); a durable marker on the snapshot, a nullable timestamp set after a verified delete with no custody row, keeps the sweep from probing every `Erased` row for ever; after a restore the sweeps stay disabled until the erasure ledger is replayed, and the delete step then removes the restored objects of already-erased documents. Offsite backups still hold the ciphertext of an erased document, a residual closed only by the key staying destroyed on every restore (the key-resurrection question below). The missing-object alarm exempting `Erased` rows holds unchanged.
- **Decided (the user, 2026-11-04): evidence upload is two steps over a raw body.** Step 1 declares the size (and optionally a sha256), carries the actor-scoped idempotency key and creates the upload-intent record; a zero or over-cap declared size is refused there, before any keystore row, so it leaves no tombstone. Step 2 is a raw-body `PUT` sealed as it is read: `Content-Length` is mandatory (411 otherwise) and must equal the declared size, and the bytes counted at end of stream must equal it, otherwise the upload falls into the aborted-upload class. No unknown-length stream exists, no multipart `UploadedFile` spool of plaintext exists for evidence, and a body Caddy cuts off cannot read as a complete shorter original. Whether the framework hands the controller a raw stream without spooling it, and what PHP's body limits do to it, is **not verified** and is measured by a spike before doc-3.
- **Derived (the assistant's, review rounds 5 and 6): the PUT claims the upload intent.** A per-actor rate limit applies to step 1 through the existing limiter pattern, and live `Declared` intents are capped per actor. The intent row carries `state` (`Declared`, `Streaming`, `Committed`, `Expired`), the actor, the scope id, the declared size, the declared sha256, the key hash, the predecessor id (`NULL` until versioning ships), the retention fields, the document id (`NULL` until `Committed`; a GUID classified `non-person`), `ttl_expires_at` (set at declare) and `claimed_at`, `lease_expires_at` and `upload_deadline_at` (set by the claim). The PUT loads the intent, authorises the caller as its actor (absent and forbidden answer alike, with the gone problem type), dispatches on the intent's state, and only on `Declared` validates everything it can before it claims (`Content-Length` present and equal to the declared size, the caller authorised as the intent's actor by the voter of the declare step, because the id is not a capability), so a request that fails leaves the intent `Declared`. The `PUT` carries the original filename as a percent-encoded UTF-8 `filename` query parameter, never a header, a path segment or the declare step (Caddy writes every request header except `Referer` and the whole path to its access log in clear, and strips the query). The name is read only when the intent is `Declared` (a `Committed` intent answers its document and ignores any name, so a lost response is recoverable whatever the retry carries) and is required and validated before the claim: valid UTF-8 (checked first), NFC, 1 to 255 bytes, not empty after trimming Unicode whitespace, and no code point of general category Cc, Cs, Co, Cn, Zl or Zp nor any format character other than U+200C and U+200D (the bidi controls, zero-width and tag characters are refused); `/` and `\` are stored as inert text and a consumer sanitises on output. Exactly one `filename` parameter must be present in the raw query (a repeat answers 422), and the client encodes with `encodeURIComponent` because PHP decodes an unencoded `+` as a space. An invalid name answers 422 and leaves the intent `Declared`, and no exception message, problem detail or log context quotes the value. It is held in request memory only, never in the intent row, and sealed in the commit transaction under its own associated data (the scope id and a `filename` purpose), so it shares no domain with the stream chunks; a PUT on a `Committed` intent ignores a supplied name. It then claims the intent with a compare-and-set `Declared` to `Streaming` under the intent row lock, before it reads a byte or mints a key; the claim sets `claimed_at`, `lease_expires_at = NOW() + lease` and `upload_deadline_at = claimed_at + declared size / minimum accepted throughput + a constant margin` (fixed by the doc-3 spike so that a 100 MiB upload on the slowest accepted link finishes inside it, and a commit refused for crossing it answers the aborted-upload problem type), the heartbeat renews the lease and never beyond `upload_deadline_at`, and the commit requires `state = Streaming`, a live lease and `NOW() < upload_deadline_at`. **Decided by the user, 2026-11-04 (round 6):** the claim also enforces a cap on `Streaming` intents, per actor and globally (provisional 2 per actor and 4 globally, sized by the doc-3 spike against the slowest accepted link, where a 100 MiB upload holds its slot for the whole deadline), because a raw-body PUT pins a PHP thread and staging space for the whole transfer; the claim also requires `ttl_expires_at > NOW()`; the count runs under transaction-scoped advisory locks (per actor, then global) that serialise claims and counts only `Streaming` intents whose lease and deadline are live, so dead claims never saturate the cap whatever the reaper's cadence; a claim over a cap answers the rate-limit problem type, without `Retry-After` since a cap has no limiter snapshot, and leaves the intent `Declared` and retryable. A replay or PUT that meets a `Streaming` intent past its lease or deadline treats it as `Expired`. A second PUT, or a PUT on a `Streaming` or `Expired` intent, answers a conflict or the gone problem type and touches nothing; a PUT on a `Committed` intent answers the existing document, so a lost response is recoverable without a key. The commit transaction sets the intent `Committed` with the document id rather than deleting it, and a retention sweep deletes `Committed` intents after a window (a constant fixed in doc-3), from which point the snapshot's `UNIQUE` and the declare re-read take over. Every transition to `Expired` (the writer's own overflow abort, the reaper, a person's erasure) replaces the key hash with `NULL`, so an expired intent never blocks its key, and sets `lease_expires_at = NOW()`, so the reaper can act at once. A `Declared` intent expires at `ttl_expires_at` and a `Streaming` one at `lease_expires_at` or `upload_deadline_at`, whichever comes first. The reaper selects `Declared` intents past `ttl_expires_at`, `Streaming` ones past `lease_expires_at` or `upload_deadline_at` and `Expired` ones, and never a `Committed` one. It tombstones the scope exactly when `claimed_at` is set, whatever state the intent has been moved to since, and no `Document` row holds the scope; when one does it deletes the intent without a tombstone, and it deletes a never-claimed intent without a tombstone, since no key was minted and the claim under the same lock means a late PUT finds nothing to claim; abandoned declares therefore add no keystore row. An aborted-upload tombstone is never pruned (pruning reopens the late-writer hole) and a growth metric watches the keystore. A person's erasure replaces the actor with the marker and the key hash with `NULL` on every intent of the actor and expires only the `Declared` and `Streaming` ones; a `Committed` intent stays `Committed` (its document exists) and is deleted by the retention sweep. It never deletes a row itself, so the reaper still tombstones a scope that was minted.
- **Decided (the user, 2026-11-04): scan retry accounting.** "Scanner unavailable" means only that no content was sent: a health probe runs before the claim, and a down scanner leaves the document in `Received` with no claim, no epoch, no attempt and no custody row, so a scanner that is down at claim time never moves a document toward `ScanFailed`. The first counter on the snapshot, `scan_attempts`, counts each claim that began streaming and ended with no verdict (connection reset, scanner timeout, scanner crash, worker death, lease expiry, deadline); reaching the cap ends in `ScanFailed`. The return path (the worker's failure handler or the lease-expiry sweep) probes the scanner again before it returns the document: if the probe fails the scanner was down, so the return is an outage return that burns no attempt and increments a second counter, `scan_outage_returns`, with its own higher cap (provisional 10, with an alarm at 5, fixed in doc-4) whose breach ends in `ScanFailed`; a circuit breaker for the scanner was discarded, since the pre-claim probe is already the health check and a breaker adds shared state; the per-claim deadline bounds one claim, not the number of refunded claims, so the second cap is what stops a poison file that takes the scanner down from looping for ever. A deterministic failure goes `Scanning` to `ScanFailed` with no retry, and `Ready` is never rescanned. The scan lease is renewed by heartbeat, not scaled to size, and an absolute per-claim deadline bounds a poison document: the heartbeat compare-and-set requires `now < claimed_at + deadline`, so no heartbeat extends it. The wait for the verdict is a poll with a read timeout below the heartbeat interval, so the worker keeps heartbeating while `clamd` scans; if the spike shows it cannot, the lease must exceed `MaxScanTime` plus a margin. Together the two counters bound every claim since the last operator decision, which resets both and increments `lease_epoch`. A sweep on `next_scan_at` in PostgreSQL drives retries and is authoritative; the Messenger message only wakes it. The heartbeat is a compare-and-set on `state = Scanning` and `lease_epoch`; a heartbeat that finds the epoch superseded or the row `Erased` aborts the scan without counting an attempt, and so does `DekDestroyed` seen mid-scan. The starting values are provisional and fixed by measurement in doc-4: an attempt cap of 3, a claim deadline of 10 minutes, a scan lease of 2 minutes renewed by a 30-second heartbeat, and a backoff of 1, 5, 15 and 60 minutes with 20 percent jitter: the cap counts claims (three), not retries, so counted returns use the first two entries, while outage returns walk the whole ladder and then stay at 60 minutes, so the cap of 10 tolerates about 7 hours of a flapping scanner. **Mechanics derived in review round 5 (the assistant's):** the snapshot carries `scan_streaming_started_at`, set by compare-and-set immediately before the first byte goes to the scanner and cleared on every return to `Received`; a return with it `NULL` (the connect failed after the claim) burns no attempt, because no content was sent, and increments `scan_outage_returns`, so a scanner that answers its probe and refuses the stream cannot loop for ever; a return with it set increments `scan_attempts`, or `scan_outage_returns` when the re-probe finds the scanner down. Either increment goes, in the same compare-and-set, to `ScanFailed` with its custody row when the value reaches its cap, and otherwise sets `next_scan_at` to `NOW()` plus the ladder entry for the outage-return count (an outage return) or the backoff for the attempt number (a counted one). The return path probes once per sweep run and applies the result to every row the run returns, with a probe timeout shorter than the sweep interval. The claim requires `scan_attempts` and `scan_outage_returns` below their caps, `promoted_at` not `NULL` and `next_scan_at <= NOW()`; `next_scan_at` is the transaction time of the insert (so the one sweep also re-drives a lost first message) and now on an operator reset, and the sweep moves a `Received` row found at or above a cap (a constant lowered at a deploy) to `ScanFailed`, so no row sits for ever unclaimable. A `first_claim_recorded` flag, cleared only by an operator decision, decides the first-claim custody row. A worker whose heartbeat fails stops and posts no verdict, and the verdict compare-and-set also requires `NOW() < claimed_at + deadline`, so the deadline is absolute. A local failure is classified: a failed authentication, a missing final-chunk marker or a missing final object is deterministic (`ScanFailed` and an alarm), and a transient local I/O error counts as no verdict.
- **Decided (the user, 2026-11-04): the scanner is ClamAV, a local `clamd` container, scanning after sealing.** The scan decrypts the original and streams it to `clamd`; `Received` stays after sealing and no pre-seal state exists. The constraint is restated from "a disk file or a spool" to **plaintext never reaches persistent storage**: `clamd` extracts archives into its temporary directory, so that directory is a `tmpfs`, swap is off, the scanner container's `memswap_limit` equals its `mem_limit` and core dumps are disabled for the scanner and PHP containers; what remains (memory, `tmpfs` pages, a host `core_pattern` outside the stack) is recorded in `PRODUCTION_SECURITY_CHECKLIST.md` §7 by doc-4. **Not verified, from memory, and owned by the doc-4 spike:** `StreamMaxLength`, `MaxFileSize`, `MaxScanSize`, `MaxFiles` and `MaxRecursion`; whether `AlertExceedsMax` is off by default (exceeding a limit would then answer clean, which the `MAX_ORIGINAL_BYTES` gate must rule out); and the memory `clamd` needs against the VPS. `clamd`'s `MaxScanTime` stays below the scan lease when the worker cannot heartbeat while waiting, and in every case below the claim deadline, and a limit-exceeded answer maps to `ScanFailed`, never `Ready` (how `AlertExceedsMax` reports it is verified by the same spike).
- **Decided (the user, 2026-11-04): the actor of `document_custody` is anonymised by one sanctioned `UPDATE`.** Sealing the actor under the subject's scope is circular (the scope id derives from the person id, so keeping it in the row is the linkable stable pseudonym that is forbidden). The statement rewrites the actor to one constant marker, never a per-subject value, is a line in the `SANCTIONED` set of the custody gate (the new gate above) with its decision in the Documents ADR (precedent: `DbalAuditActorAnonymiser`, `docs/adr/audit-activity-log.md` D4), runs inside the identity erasure's transaction (the Documents seam is called by `FulfilIdentityErasure` and `ResweepErasedSubjects` within their one transaction, like the existing purges, so there are no batches and the locks are held until that transaction commits; the erasure is rare), after the locks that transaction already holds on identity, session and audit rows, which no Documents flow takes, and inside the lock order above: first the actor's intents are rewritten and expired, then the document and custody statements run in ascending id, so that an in-flight commit has either committed and is visible to them or is blocked on its intent until it is expired; it needs an index on the actor. Reference anonymisation is not a state transition: it applies in every state, `Erased` included, outside the compare-and-set invariant below. The marker is one fixed, valid value of the column type (the nil UUID), declared once as a constant, and the `PersonReferenceSource` excludes it; a test plants an anonymised row and expects the detective source to report nothing. A row committed after the statement's snapshot by an in-flight action of that person is missed by the `UPDATE` and is reported by the detective source and re-swept by the identity erasure's re-sweep, which are the controls for that race. The idempotency hash lives on the mutable snapshot row and is nulled by the same erasure; replay protection for that actor ends, accepted. Cost: custody is no longer absolutely append-only.
- **Decided (the user, 2026-11-04): a person's erasure never erases a document.** The uploader is not the subject, and erasing an employee must not destroy the company's evidence. It anonymises the person's references (above) and nothing else; content erasure is per document, an authorised decision through the erasure use case, with no per-subject fence and no subject scope. Erasing a whole series is a repeatable operator action that erases each non-`Erased` version in its own transaction, newest first, and reports what remains: a version filed meanwhile under a `Ready` node whose child just became `Erased` is a new live version, so the operation guarantees no termination and is not a legal guarantee.
- **Decided (the user, 2026-11-04): the erasure ledger is fixed by properties, and its first adapter is a restic repository behind an append-only REST server on a second host.** The adapter sits behind an `ErasureLedger` application port so the channel can change without touching the use case, and the repository is kept apart from the backup repository. Invocation: the `restic` binary runs in array form through `Process` in the `Infrastructure` adapter (the port lives in the Documents `Application` layer), from the php/worker image or from a sidecar, which doc-7 decides; the repository password and the REST credentials come from environment variables or secret files, never from the repository URL or argv (the console error listener logs argv at CRITICAL and restic quotes the URL in its errors), the adapter rethrows a sanitised exception, the write credential and the repository password necessarily live on the VPS (the erasure writes the entry and the completion sweep lists the ledger from there), so a VPS compromise yields them (the residual below); an independent copy of every ledger credential and the repository password is held off the VPS, in the secrets store of `docs/vps-deployment.md`, and the restore drill proves the ledger readable from that copy alone. Whether the sweep and the restore can read with a credential that cannot write is not verified (a stock append-only REST server may express no read-only user) and the doc-7 spike settles it, the fallback being the same credential, which changes no residual. A leaked repository password cannot be rotated while the repository is append-only (`restic key remove` is refused), so rotation is a documented procedure that needs an administrator session on the ledger host. Its acceptance, proved the way `docs/vps-deployment.md` proves Gate 2 (a refused `restic forget`, `restic check`, the production credential against the real backend): the write credentials cannot delete or shorten retention, the entry is confirmed durable before `destroyScope()`, and `restore.prod` stays in recovery mode, writers and sweeps off, whenever the ledger cannot be read in full ("in full" means `restic check --read-data` exits 0 and the listing prints no `Ignoring` line, which the doc-7 spike confirms rather than assumes, since restic may skip an unreadable snapshot file and still exit 0; a deleted entry leaves no trace, so the append-only server is the only control on that direction). Object-lock object storage was discarded: the tree has no object storage and S3 is a non-goal of the first slices. The ledger lives outside the PostgreSQL failure and restore domain, is append-only and held as a single copy on its own host (the user, 2026-11-05, over a periodic second copy): losing it fails closed, `restore.prod` stays in recovery mode, and only an explicit, documented override procedure exercised in the drill lets a restore proceed while accepting that erased keys may return; it holds scope ids only (random, not derivable from the document id), and each entry is a write-ahead intent completed forward, never rolled back. The entry is written synchronously off the VPS before `destroyScope()`, because the nightly backup's 24-hour RPO in `docs/vps-deployment.md` would otherwise bring back the key of a document erased that morning; an erasure therefore depends on the offsite channel being available (accepted: erasures are rare and the legal term is a month). The write follows the voter, existence and erasable-state checks and precedes the erasure transaction, holds no database lock and has a bounded timeout, and entries are at-least-once (a retry writes a second snapshot, so the sweep and the replay deduplicate by scope id and a duplicate is harmless); the erasure transaction sets `lock_timeout` and `statement_timeout` to the bound the sweep margin uses, and an entry's age is judged from its snapshot timestamp, which the VPS clock sets, so the margin includes clock skew. A write that fails before the entry is durable leaves the document untouched and erasable on retry; a timed-out write is outcome-unknown, so the caller is told that the erasure may still complete, and an entry that did land is completed forward by the sweep as the write-ahead intent it is. A per-scope completion sweep with an alarm finishes interrupted erasures: it lists the ledger, ignores entries younger than the write timeout plus the transaction bound plus a margin (so it never steals an erasure whose transaction is still running and whose authorisation custody must record) and alarms when it cannot read the ledger; a replay goes through a separate application service, never a parameter of the use case the controller calls, reachable only from the restore command and the completion sweep (a reflection gate test asserts that the classes whose constructors depend on it are exactly those two, and the HTTP erase route's closed-enum reason is a separate type that excludes `ledger-replay` and `ledger-completion`), that skips the ledger write and records the nil-UUID marker as actor (the same constant as an anonymised person; the reason tells them apart, and it has no voter by construction because it runs under the restore procedure or the sweep, never an HTTP route) and the closed-enum reason `ledger-replay` for a restore replay or `ledger-completion` for the sweep finishing an entry that landed (the ledger holds scope ids only, so the operator who authorised it is not recoverable by design), so the snapshot, custody, the `ImageDeletionRequested` signal and the key converge, an object under a ledger scope with no row in the restored database is deleted during the replay (the ledger is the authority for that scope), a ledger scope unknown to the restored database still gets a tombstone with reason `erasure`, and fail-closed applies globally only during a restore. The falsifier is a real restore drill that proves the key does not return. Signing the ledger is YAGNI, which leaves the residual that whoever holds the write credential can append an entry for a live scope and the sweep then destroys that document with no voter.
- **Agreed in bulk, not asked one by one (the assistant's recommendations, 2026-11-04).** *Host:* `Documents` is a top-level context and its first consumer is BankAccount evidence, since no progress-certificate context exists. *Operator surface:* an API route behind a voter, never a console command (it would name a person on argv), with the reason as a closed enum and no free text, delivered with doc-4 because `ScanFailed` has no exit without it (the erase route of a `Quarantined` or `ScanFailed` document ships with doc-7, so between the two they cannot be erased, which the stuck-document alarm tolerates); every story that adds a route regenerates `api/.route-manifest.json` (`make sf.routes.manifest`), classifies it in `api/.credential-proof-policy` and names its voter and `Permission`; every problem type a story mints is added to `docs/api-error-contract.md` and passes `make php.lint.error-contract`; a re-scan resets `scan_attempts` and `scan_outage_returns` and increments `lease_epoch`. *Retention:* `retention_reason` (closed enum), `legal_basis` (GDPR Article 6 enum) and a nullable `review_at` supplied by the consumer; period, anchor, jurisdiction, policy version and enforcement wait for counsel's matrix. *Misfiling guard:* UI-only, decided at the first UI offering both entry points, with no boolean parameter on a use case.
- The contract is chosen by the use case (`UploadEvidence` vs `UploadImage`), never by a heuristic over MIME or size. `UploadEvidence` is added by doc-3 as a second example to the existing Upload row (6) of `docs/rules/cqrs-naming.md`.
- There is no promotion between contracts. A fungible image never becomes evidence; the supported path is re-supplying the original through `UploadEvidence`.
- `Documents` has its **own** storage port, written as a stream and sealed. No generic port spans it and `ImageStorage`.
- The upload seam is a raw request body, so the Symfony 8.1 argument resolver (`mergeParamsAndFiles`) and `Shared/Http/Infrastructure/TransportOnlyUploadedFileDenormalizer` are not on the evidence path, and the denormalizer keeps guarding the images seam. Neither a transport type (`UploadedFile`, `SplFileInfo`) nor a caller-supplied path or URL reaches `Application` or the `Documents` tree, and the caller's original filename reaches it only as a validated, length-bounded value that is sealed and never used as a path; bytes arrive as a stream the Infrastructure adapter produced. A scan over the context's own tree plus a regression test that goes red when the scan stops matching enforces it, because deptrac cannot express it: the scan matches a transport type and path- or URL-typed values and excludes the one filename value object, which is a sealed value and never a location.
- **Ingest is atomic from the caller's view.** Bytes land under a staging key and are promoted only when the stream is complete and matches any declared length or digest (the `PUT` hashes the plaintext as it is sealed and compares the result with the declared sha256 before the commit, a mismatch falling into the aborted-upload class, and the computed digest is what the `Received` row stores); an upload intent whose lease expired with no row is reaped: its staged object is deleted and its scope tombstoned (a never-claimed intent has neither). A replayed `UploadEvidence` carries an actor-scoped idempotency key and returns the existing document, which is not deduplication; the same key with different bytes is a conflict, and a replay after the original became `Erased` returns the tombstone, never a revived document. The sha256 is mandatory whenever an idempotency key is supplied (64 hex characters, validated at declare, stored and compared in lower case), so a replay is compared at the declare step on digest and declared size and never streams a second time; a mismatch is a conflict even against an `Erased` original, and a replay compares every declared parameter (size, sha256, predecessor id and the retention fields) against what is stored, so a different one is a conflict instead of silently returning the earlier document. A replay answers by the state of the intent it finds: `Declared` returns the intent, `Streaming` answers a conflict with the remaining lease as `Retry-After`, `Expired` counts as absent (its key hash is already `NULL`) and `Committed` returns the document. The declare step inserts the intent under the `UNIQUE` on the actor-scoped key hash and then re-reads the document table in a new statement of the same transaction (a hit rolls the insert back and answers the document, or a conflict on a parameter mismatch; when the conflicting intent vanishes before it can be read the declare retries once, the single exception to "never retried"); the commit transaction leaves the intent `Committed` with the document id, so the intent keeps holding the key until its retention sweep deletes it and an insert that succeeds after that deletion sees the document in the re-read, and the snapshot carries a nullable `UNIQUE` on the same hash (`NULL` after the actor's erasure) as the backstop. Two concurrent first uploads under one key therefore do not both stream: the loser is answered there with the existing intent or document and has no scope and no bytes.
- **Two digests with different meanings:** the original's (integrity, custody, signature) and, for images, the canonical image's (visual identity, caching). Neither is an identity or a uniqueness key; no unique index on a digest.
- **Every state change is a compare-and-set on the aggregate and `Erased` rejects all of them** (reference anonymisation is not a state change). A late scan verdict or a late derivative never revives or outlives an erased document. The compare-and-set of a scan transition also carries a monotonic `lease_epoch`, incremented on every claim and on an operator reset, never reset and independent of the retry counter (the attempt number is not the token), so a verdict from a superseded lease is dropped and cannot override the verdict of the scanner that now holds it. The expiry that returns `Scanning` to `Received` is itself a compare-and-set whose predicate is `state = Scanning AND lease_epoch = e AND lease_expires_at < NOW()`, evaluated inside the `UPDATE` by the database clock, so it cannot expire a lease a late verdict just completed or one a heartbeat has just renewed.
- Erasure keeps no person reference; the one declared exception is the sealed original filename. A person's erasure anonymises their references (uploader, custody actor, upload-intent actor, idempotency hash) and never erases a document. **The original filename is persisted sealed under the document's own scope (the user, 2026-11-04, superseding the earlier rule that no free-text field is persisted):** it dies with the document and a person's erasure leaves it, consistent with D7 (the uploader is not the subject, and the document's own content names people too). It travels in the `PUT`, never the declare step, and is sealed in the commit transaction once the scope key exists, so the upload-intent row never holds it in plaintext. It stays out of logs, Sentry, audit metadata and events by construction: `filename` joins a dedicated `QUERY_KEYS` set of `RequestUriRedaction`, matched as a substring after the same padding and decoding reduction (so `filename[]`, `filename[0]` and `x-filename` are caught) and consulted only by the URI redaction paths: not `RedactionDenylist::KEYS`, which strips response-body extension keys, and not `IDENTITY_KEYS`, which is matched whole and parity-gated (Monolog's `request_uri`, the per-error log line and Sentry's `url` and `query_string` redact by key name, so an unlisted key would pass). The PWA vocabulary (`pwa/src/context/shared/observability/domain/redaction.ts`, which scrubs fetch breadcrumbs and span URLs) mirrors the set and `RedactionVocabularyParityTest` compares the two. Sentry transaction events are a separate hook (`before_send_transaction`) and a raw body of up to 10,000 bytes can ride on an error event, so doc-3 closes both. Caddy already strips the whole query from its access log; `Document`, `UploadIntent` and `DocumentCustody` are not `#[AuditedEntity]` (a reflection test) and `AuditMetadataKey` gains no filename key; and a containment test in the style of `AccessLogQueryContainmentGateTest` sends real `PUT`s with a distinctive name (completed, aborted mid-body, past the Caddy bound) and reads both the access log and the container's default log, beside unit tests over the Monolog and Sentry redaction. It is not searchable in SQL, and is never a storage path: the server-generated name stays the physical key. The `Erased` compare-and-set sets the filename ciphertext to `NULL`, so a tombstone holds no name and the listing tests for null instead of decrypting a destroyed scope. No title field is persisted; a field that can carry a name is added only by a story that decides which scope seals it. What survives in custody is digest, timestamps, the anonymised actor marker and legal basis.

The document's own id is not marked. Classify the `Document` resource type (`non-person`) in `api/.audit-resource-types` in the story that first writes it, since the gate refuses a type nothing writes; `api/.audit-evidence-actions` is owed where an audit action is declared as a string constant on an `AuditLogger` collaborator.

The uploader on the snapshot, the actor column of `document_custody`, the actor of the upload-intent record (which exists before any `Document` row and is expired and anonymised, never deleted, on the actor's erasure) and the operator of an operator-decision custody row (who is that row's `actor`, not a separate column) are such columns. The idempotency hash is not a `Types::GUID`, which is the registry's whole universe, so it is not registered there: the same purge nulls it and an acceptance scenario proves it. ## Non-goals

- No code, schema or route is produced by this spec; it fixes guidelines and a story order.
- No deduplication, shared blob identity, reference counting or GC (ADR invariant 3).
- No transformation of an original, and no virus scanning, OCR or versioning inside the images module.
- No migration of images into evidence; no best-effort original kept in the images module.
- No S3, object-lock or other non-local backend for evidence storage, and no hash-chaining of custody, in the first slices.
- Retention is recorded but not enforced: no schedule erases on expiry. Erasure is on request until a story says otherwise (it would need a schedule consumer on a single replica).

A first `Documents` story can start from this folder without reopening the fungible-vs-evidence boundary, the storage-port split, the erasure mechanism or the story order, and with the open questions below answered or consciously deferred.
