# Documents bounded context — evidence-class binaries

## Why

A mandate and a vision. The ERP targets construction, which produces technical documentation whose **original byte is the proof**: drawings, reports, contracts, certificates, RAW, and the site photograph attached to a progress certificate. The images module re-encodes and strips on purpose, so it destroys exactly what makes these evidence. Nothing in the tree accepts evidence yet: the images pipeline rejects non-image formats, but a site JPEG passes `UploadImage` and is stripped (the ADR D3 misfiling hazard). Guidelines are fixed now so that the first `Documents` story inherits decided boundaries and named open questions instead of rediscovering them. Boundary authority: the accepted ADR in `companions:`.

## Capabilities

- **CAP-1**
  - **intent:** A caller can file an evidence-class binary, which is stored untransformed with its digest, actor, date, legal basis and retention policy recorded.
  - **success:** The bytes read back and decrypted equal the uploaded bytes, and the recorded digest equals the digest of the uploaded bytes. A truncated or aborted upload leaves no document and no object in the final namespace, and its key is destroyed within the reaper bound. The acceptance reads through the storage port and the decryptor in a test, since ingest exposes no read route.
- **CAP-2**
  - **intent:** A document is consumable only once it is scanned and ready; scanning classifies and never cleans.
  - **success:** A read in `Received`, `Scanning`, `Quarantined` or `ScanFailed` is refused with a defined RFC 9457 problem type; only a read in `Ready` returns bytes.
- **CAP-3**
  - **intent:** Originals are sealed at rest under a key scoped to the document, with peak memory independent of the size of the original.
  - **success:** The peak memory of sealing an original of 1 MiB and one of `MAX_ORIGINAL_BYTES` (measured, not asserted) differs by less than a bound doc-1 fixes by measurement, and both decrypt back byte-identical.
- **CAP-4**
  - **intent:** Erasure ends the conservation contract by destroying the document's key, from any non-terminal state, leaving digest and custody record intact.
  - **success:** After erasure the content cannot be decrypted, sealing under the same scope is refused, and digest and custody remain readable.
- **CAP-5**
  - **intent:** Derivatives of a document (previews) are materialised through the images module with their origin recorded, and die with it.
  - **success:** After erasure, the variant URL answers 404 or 410, no `Image` row with that origin remains, and no storage key for it remains; a derivative that arrives after erasure is deleted on arrival.
- **CAP-6**
  - **intent:** Each state change of a document is recorded, and the document's metadata and custody trail can be listed in order.
  - **success:** The ordered sequence of states of one document can be listed, including after erasure.
- **CAP-7**
  - **intent:** A new version is a new immutable original linked to its predecessor, never a modification.
  - **success:** Both versions are retrievable with distinct digests until erased; erasing one leaves the other's link to it as a readable tombstone.
- **CAP-8**
  - **intent:** Scanned PDFs yield a searchable text derivative.
  - **success:** A phrase present only in a scanned page is found by search; the text derivative dies with its document.
- **CAP-9**
  - **intent:** An authorised user can read a `Ready` document, and the read is audited.
  - **success:** The route declares its voter, refuses non-`Ready` states (CAP-2), writes an audit row, and serves the bytes with `nosniff` and a locked-down `Content-Security-Policy`.

## Constraints

- **Decided (the user, 2026-10-30): state-oriented persistence plus a custody log.** `Document` is a snapshot row; every transition also appends a `document_custody` row in the same transaction, except the scan lease returns named under Custody guarantees. Event sourcing was rejected on measurement: the event store has no per-aggregate stream loading (`DbalEventStore::stream()` is a global, sequence-ordered projection feed), and its `aggregate_version` is informative (`DbalEventStore::append()` computes `MAX+1`, under a `UNIQUE (tenant_id, aggregate_id, aggregate_version)` from `api/migrations/2026/Version20260616201857.php` that never fires because `tenant_id` is always `NULL` and PostgreSQL treats `NULL`s as distinct), so it would first need aggregate loading, optimistic concurrency and a serialised append. `document_custody` is not `audit_log`: reads stay in `audit_log`, which has a retention prune; custody never expires.
- **Custody guarantees.** The aggregate is loaded under the lock (`PESSIMISTIC_WRITE`, or re-read after `SELECT … FOR UPDATE`), so the compare-and-set never runs against a stale snapshot; `seq` is computed inside that same transaction. `UNIQUE (document_id, seq)` is the second defence, not a substitute, and a violation maps to a retry, never a 500. The first row (`seq` 1) has no row to lock: the document insert and its first custody row share one transaction and only the `UNIQUE` guards it. Lock order is document, then keystore, within one document; ingest and a new version lock only the keystore row of the new, not-yet-visible scope before their own insert and never the keystore row of an existing document without that document first. A flow that locks several documents (a subject's erasure over a chain) takes them in ascending id. A repeated erasure appends nothing. `Erased` is a snapshot state, never a row delete, and the custody foreign key has no cascade. Custody rows are never deleted and are updated by no statement except the single sanctioned actor-pseudonymisation one, if the actor question below chooses that route. **Enforcement is a source gate over `api/src` in the style of `SanctionedLogMutationGateTest`, and nothing more:** no database role separation, `GRANT`, `REVOKE` or trigger exists in the tree, the gate sees neither a migration nor runtime-built SQL, and adding a restricted role or a `BEFORE UPDATE/DELETE` trigger is a separate decision. Custody stays readable after the key is destroyed and is not claimed cryptographically immutable. Custody records the first scan claim since the last operator decision, every verdict (including `ScanFailed` reached by the attempt cap or by a deterministic failure) and every operator decision; a lease return (`Scanning` back to `Received`) and a re-claim are counted on the snapshot and write no custody row, an explicit exemption from "every transition appends" that the ordered listing of CAP-6 accepts.
- **Decided: a version is its own `Document` aggregate.** It carries its own bytes, digest, key scope, retention, scan lifecycle and custody. It links to its predecessor by an immutable id and to its series by a scalar series id (the first version's series id is its own id); both columns exist from the first migration. No series aggregate exists and a read projection lists versions. A consumer references the exact version it relied on. **The chain is linear:** a `UNIQUE` on `predecessor_id` refuses a second child, and the use case authorises the caller on the predecessor (a voter) before sealing and answers "absent" and "forbidden" with the same problem type, so the conflict response leaks neither existence nor state; the short transaction that inserts a new version also takes `FOR UPDATE` on the predecessor row (after the new scope's keystore row, per the lock order above) and rechecks that it is `Ready`, because the predecessor's state when the upload began proves nothing; the lock is taken after the new bytes are sealed, never across the stream, so an upload cannot block the predecessor's erasure. The loser of the `UNIQUE` race has already sealed bytes and a key: it falls into the aborted-upload class and maps to a conflict. A tombstone keeps id, digest, `series_id`, `predecessor_id`, state and timestamps, which name no person; everything else is gone or sealed. Whether a failed or erased child frees its predecessor's slot, and how a subject's erasure traverses the chain, are open below.
- **Decided: the first evidence adapter is the local filesystem behind the `Documents` port**, and the port declares no WORM guarantee an adapter cannot enforce. S3 with object-lock waits for a first consumer and a defined retention vocabulary; the port keeps the move reversible (ADR D6). **Before first real use** (owned by doc-3, verified before doc-5 serves real documents) the stored bytes need an encrypted offsite backup, digest verification and a proven restore of originals and metadata: a database dump is not a backup of the evidence. **Ordering on the local filesystem.** Before any byte is sealed, a durable upload-intent record (mechanism chosen in doc-3) holds the document's scope id, the actor, a lease expiry and a heartbeat. The scope id is random, is the document's own from that moment, is stored on the row under a `UNIQUE` (two documents sharing a scope would let one's erasure shred the other's bytes), and the staging key embeds it, so promotion needs no re-seal; the stream seal's associated data binds the scope, never a storage path. The seal mints the key under that scope and commits on its own: no database transaction spans the stream, and a long upload renews its lease by heartbeat or the lease outlasts the bound on upload time. Staging sits on the same mount as the final namespace (`rename(2)` is atomic only within one filesystem) with the file and its directory synced; the adapter compares `st_dev` of the two roots at boot and refuses to start otherwise, because on two volumes every promotion fails with `EXDEV` after the commit. A short transaction then locks the intent row, then the keystore row of the scope (through a `Keystore` method added in doc-1 that locks the row and reports live, tombstoned or absent, since `wrappedDekFor()` filters tombstones out and cannot tell them from absence), asserts that the intent lease is live and the scope is not tombstoned, inserts the `Received` row and its first custody row, and commits; the object is renamed to final and the final directory synced after that, and the scan message is dispatched only after the rename succeeds. **The intent row is the one lock the commit and the reaper share.** The reaper locks the intent row, then the keystore row, rechecks under both locks that the lease has expired and that no `Document` row holds the scope, and only then tombstones and deletes the intent in the same transaction; the commit locks them in the same order. Lease expiry is judged by the database clock (`NOW()`), never the application's. A `NOT EXISTS` inside the reaper's `UPDATE` would not do, because under `READ COMMITTED` its snapshot predates a row that commits while the `UPDATE` waits on the lock. A writer whose heartbeat finds its intent gone or expired aborts and deletes its own staged file, and an age sweep over the staging namespace deletes any staged object older than the upload bound plus a margin that has neither a live intent nor a row. **A committed row owns its staged object:** the reaper acts on intents, never deletes a staged object whose scope has a row and never destroys that scope; a sweep rolls the promotion forward for a `Received` row older than a bound whose object is only staged (the rename is idempotent and accepts the final object already present) and then dispatches the scan. The roll-forward sweep acts on `Received` rows only and skips an `Erased` one: the object of an `Erased` row belongs to the delete step decided below, and a roll-forward rename rechecks under the document row lock that the row is still `Received`. A final object with no row cannot arise in the normal flow (the row commits first); it appears after a restore to an older dump or by hand, so the sweeps **alarm on it and delete nothing in the final namespace for a scope that has no row**, and the restore step disables the sweeps and the reaper along with the writers. The one deletion in the final namespace is the `Erased` delete step, keyed on an `Erased` row. The sweeps also alarm on rows with no object anywhere, except `Erased` rows. The stream seal authenticates truncation (the last chunk carries a final-chunk marker in its associated data), so a short file from a partial restore or a full disk fails instead of decrypting as a prefix. A `Ready` document whose bytes are missing, mismatch the digest or whose scope is tombstoned (`DekDestroyed` on decrypt) fails closed with a defined problem type and an alarm. A read that finds the object gone or the scope destroyed re-reads the row first: an `Erased` row answers the gone problem type with no alarm, and only a row still not `Erased` alarms, so an erasure that commits between the read's snapshot and its open is not reported as lost evidence.
- **Mechanisms the capabilities lean on.** Ingest is a dedicated `UploadEvidence` use case; sealing is a stream-oriented sibling of `EnvelopeEncryptor` over `EncryptionScopeId` (one scope per document); erasure is `destroyScope()`. The sibling must keep the existing guarantee that sealing under a destroyed scope throws `DekDestroyed` instead of minting a fresh key; a test seals, destroys, seals again and expects refusal. **Until doc-1 closes it, that guarantee has a hole:** `DbalKeystore::destroy()` is an `UPDATE … WHERE destroyed_at IS NULL`, so on a scope never minted it affects zero rows and leaves no tombstone, and `SodiumEnvelopeEncryptor::mint()` then mints a live key for a late writer. Erasure and the staging reaper therefore leave a tombstone even when no key was minted (`destroy()` upserts a destroyed row; `kek_version` is `NOT NULL`, so the row carries a KEK version and a null `wrapped_dek`; the current version is a private constant of `SodiumEnvelopeEncryptor` that `destroy()` cannot see, so doc-1 passes it through the port or states a sentinel), and `Erased` is decided by the aggregate's compare-and-set, never by the boolean `destroyScope()` returns, which is `false` both for a repeat and for a scope that never existed. A test destroys an unminted scope, seals, and expects `DekDestroyed`. A tombstone carries a `reason` on the keystore row (`aborted-upload` or `erasure`) and is never classified by the absence of a ledger entry; the erasure ledger does not carry aborted-upload scopes, and the tombstone reconciler is driven by `Document` rows, so any non-`Erased` row whose scope is tombstoned is an alarm whatever the ledger says. **The existing `DbalSubjectErasureReconciler` must be amended in doc-1:** its query selects every destroyed `dek_keystore` row with no `SUBJECT_ERASED` audit row and filters on neither reason nor scope type, so left alone the scheduled reconciler logs every aborted-upload and every `Document` tombstone at `error` level as a GDPR divergence, for ever, burying a real one. It excludes `aborted-upload` tombstones and `Document` scopes, which the Document-driven reconciler owns; a test plants one of each and expects `unreconciledScopes()` to be empty. **Erasure converges across its stores:** the `Erased` transition, its custody row and the key destruction commit together or are re-drivable from a recorded intent, with a scenario for a crash at each point. **Whichever scan order is chosen, the scanner never makes plaintext reach a disk file or a spool:** a decrypt-for-scan receives a stream only, size limits are measured against `MAX_ORIGINAL_BYTES`, and exceeding one ends in `ScanFailed`, never `Ready`.
- **Decided (the user, 2026-11-04): a zero-length original is refused, and `MAX_ORIGINAL_BYTES` is 100 MiB.** What follows from it, not separate decisions: the refusal comes before the upload-intent record exists, so it leaves no keystore row and no tombstone (with a raw stream it is the first read returning end of stream, with a multipart `UploadedFile` a size of zero), and the stream seal never receives an empty stream from this use case. Exactly 104,857,600 bytes is accepted and the 104,857,601st aborts the upload, counted before each chunk is sealed or staged; a writer that detects the overflow itself deletes its staged file and expires its own intent under the shared lock, the reaper tombstones as usual, and the upload falls into the aborted-upload class. The constant is also the size the scanner limit is measured against: once the scanner is chosen a gate compares the two and the scanner's real limit is verified then, not assumed; a scanner whose limit is below the constant fails the gate, and resolving that mismatch is a new decision. There is no multi-gigabyte promise: CAP-3 asks for peak memory independent of size.
- **Body bounds of the upload route (a consequence, sized in doc-3).** `api/frankenphp/Caddyfile` caps every request PHP serves at `1MB` with `request_body @frontController`, matched on `index.php` after the rewrite, so the upload route needs a bound of its own on the original path, placed so that the 1 MB block does not also cap it (`api/config/services.yaml` says the same). Caddy's `MB` is 10^6 bytes, so the new bound is written in MiB or in bytes. It counts the whole body, framing included, so it sits strictly above the cap plus a stated framing allowance, and the application counter is the authority that answers with a Problem Details. Caddy applies the bound as the body is read and promises no 413, so a body it cuts off must never read as a complete shorter original. Where PHP parses the body, `post_max_size` and `upload_max_filesize` (unset in `api/frankenphp/conf.d`, so PHP's defaults apply), the capacity of the upload temp directory and the request time limit belong to the same set; which of them apply is the transport question below.
- **Decided (the user, 2026-11-04): the sealed object of an `Erased` document is deleted, never kept on purpose.** Deletion is a post-commit step, idempotent and re-driven by a sweep, with an alarm on an object older than a bound measured from the `Erased` custody row; a failed delete never rolls the erasure back. What follows from it: this sweep is the single owner of the object of an `Erased` row; it removes the staged path first and then the final path, tolerates ENOENT on each and counts a row done only when neither exists, because a writer's post-commit rename can race an erasure and recreate the final object (the writer treats ENOENT on its own rename as normal); a durable marker on the snapshot, a nullable timestamp set after a verified delete with no custody row, keeps the sweep from probing every `Erased` row for ever; after a restore the sweeps stay disabled until the erasure ledger is replayed, and the delete step then removes the restored objects of already-erased documents. Offsite backups still hold the ciphertext of an erased document, a residual closed only by the key staying destroyed on every restore (the key-resurrection question below). The missing-object alarm exempting `Erased` rows holds unchanged.
- **Decided (the user, 2026-11-04): scan retry accounting.** "Scanner unavailable" burns no attempt, because counting it would turn every in-flight document into `ScanFailed` during an outage, and the scan lease is renewed by heartbeat and not scaled to the size of the original. Which other scanner failures count toward the cap, the cap value and the rest of the retry policy are open below. The heartbeat is a compare-and-set on `state = Scanning` and `lease_epoch`; a heartbeat that finds the epoch superseded or the row `Erased` aborts the scan without counting an attempt, and so does `DekDestroyed` seen mid-scan.
- The contract is chosen by the use case (`UploadEvidence` vs `UploadImage`), never by a heuristic over MIME or size. The upload category joins `docs/rules/cqrs-naming.md` with the first slice.
- There is no promotion between contracts. A fungible image never becomes evidence; the supported path is re-supplying the original through `UploadEvidence`.
- `Documents` has its **own** storage port, written as a stream and sealed. No generic port spans it and `ImageStorage`.
- The upload seam is designed against the Symfony 8.1 argument resolver (`mergeParamsAndFiles`) from the start, using the existing `Shared/Http/Infrastructure/TransportOnlyUploadedFileDenormalizer`. Neither a transport type nor a caller-supplied path, filename or URL reaches `Application`; bytes arrive as a stream the Infrastructure adapter produced. A scan over the context's own tree plus a regression test that goes red when the scan stops matching enforces it, because deptrac cannot express it.
- **Ingest is atomic from the caller's view.** Bytes land under a staging key and are promoted only when the stream is complete and matches any declared length or digest; an upload intent whose lease expired with no row is reaped: its staged object is deleted and its scope tombstoned. A replayed `UploadEvidence` carries an actor-scoped idempotency key and returns the existing document, which is not deduplication; the same key with different bytes is a conflict, and a replay after the original became `Erased` returns the tombstone, never a revived document. Bytes are compared by digest first, so a mismatch is a conflict even against an `Erased` original. Two concurrent first uploads under one key both stream in full, because the intent record is not keyed and the early probe cannot see an upload that has no row yet; the loser is cleaned at the `UNIQUE`. That cost is accepted.
- **Two digests with different meanings:** the original's (integrity, custody, signature) and, for images, the canonical image's (visual identity, caching). Neither is an identity or a uniqueness key; no unique index on a digest.
- **Every state change is a compare-and-set on the aggregate and `Erased` rejects all of them.** A late scan verdict or a late derivative never revives or outlives an erased document. The compare-and-set of a scan transition also carries a monotonic `lease_epoch`, incremented on every claim and on an operator reset, never reset and independent of the retry counter (the attempt number is not the token), so a verdict from a superseded lease is dropped and cannot override the verdict of the scanner that now holds it. The expiry that returns `Scanning` to `Received` is itself a compare-and-set whose predicate is `state = Scanning AND lease_epoch = e AND lease_expires_at < NOW()`, evaluated inside the `UPDATE` by the database clock, so it cannot expire a lease a late verdict just completed or one a heartbeat has just renewed.
- Erasure keeps nothing that names a person. Metadata fields that can carry one (original filename, title, uploader) are either sealed under the subject's scope or forbidden as free text in the surviving custody record; what survives is digest, timestamps, actor pseudonym and legal basis. The decision is taken in the story that first persists the field (doc-2 for the schema, doc-3 for the values), never after: a plaintext filename or uploader persisted between those stories would outlive the erasure. Each such field names the scope that seals it, because the document's bytes die with the document's scope while a person's fields die with theirs.
- A consumer's `*DocumentId` field that references a natural person's evidence is personal data in that consumer: mark it `#[PersonalData]` so `PiiDiffSealer` seals it under the subject's scope. The document's own id is not marked. Classify the `Document` resource type in `api/.audit-resource-types`.
- A column holding a person id needs a named erasure owner (`api/.person-reference-policy`, `#[PersonSubjectReference]` and a `PersonReferenceSource`), registered in the story that introduces the column, never later. The actor column of `document_custody`, the actor-scoped idempotency key, the actor of the upload-intent record (which exists before any `Document` row and dies with the intent or is purged on the actor's erasure) and the operator named by an operator-decision custody row are such columns.
- **Derivative removal rides the existing signal.** `Shared.Image` is classified `person` in `api/.persistent-transport-policy` and `ImageDeletionRequested` routes to `async` under `docs/adr/image-deletion-signal-transport.md`, which closes no erasure risk and records its own residuals (the id stays in `event_store`; a dead letter swept at 30 days drops the instruction). The `Document` aggregate stays unrouted; the payload carries image ids only. Removal is never synchronous inside the owner's transaction, retries re-query by origin rather than from a list built once, and an alarm fires on derivatives of an erased document that outlive a bound.
- An `ImageId` is held by exactly one aggregate instance. `Documents` is the holder of its derivative ids.
- Other contexts reference a document by id only; reads compose through an explicit DQL JOIN projection.
- Evidence semantics (retention, legal basis, what counts as proof) live in `Documents`, never in `Shared/`.
- The first merged code in which another context materialises a rendition through the images module is the ADR D4 trigger to decide renaming `Images`; that story records the decision.
- Every story touching erasure or derivative lifecycle records an adversarial pass; the three-layer review is owed per story.

## Non-goals

- No code, schema or route is produced by this spec; it fixes guidelines and a story order.
- No deduplication, shared blob identity, reference counting or GC (ADR invariant 3).
- No transformation of an original, and no virus scanning, OCR or versioning inside the images module.
- No migration of images into evidence; no best-effort original kept in the images module.
- No S3, object-lock or other non-local backend, and no hash-chaining of custody, in the first slices.
- Retention is recorded but not enforced: no schedule erases on expiry. Erasure is on request until a story says otherwise (it would need a schedule consumer on a single replica).

## Success signal

A first `Documents` story can start from this folder without reopening the fungible-vs-evidence boundary, the storage-port split, the erasure mechanism or the story order, and with the open questions below answered or consciously deferred. In particular, a demonstration where an uploaded drawing is stored byte-identical, is unreadable until scanned, and after erasure leaves digest and custody while every derivative is gone.

## Assumptions

- `Documents` lives outside `Shared/`, because evidence semantics are business meaning (ADR D4); its host context is open below.
- The `#268` item "`UploadedDocument` port wrapping the request file" is superseded by ADR invariant 6.
- Fail closed while the scanner is unavailable.
- `Shared/Images` has no origin on `Image` and no entry point for another context to materialise a derivative; the derivatives story creates both.

## Open Questions

- **Key resurrection on restore.** A restored PostgreSQL dump brings back the wrapped key of a scope destroyed since, and the tombstone reconciler lives in the same restored database. Candidate: a ledger of erasures outside PostgreSQL holding scope ids only, plus a mandatory restore step that stops writers and readers, replays the ledger, verifies, and only then re-enables. Consulting it on every read is rejected as an availability dependency. Constraints on any candidate: an entry is a write-ahead intent recorded before `destroyScope()` and completed forward, never rolled back, because written after the destruction a crash between the two loses the erasure and written before a commit that rolls back it names a live document; a replay goes through the erasure use case, not the key alone, so the `Document` snapshot, its custody row, the `ImageDeletionRequested` signal and the key converge (destroying the key alone leaves a `Ready` row and resurrected derivatives); the scope id is a random value not derivable from the document id, since the ledger outlives the erasure; the ledger itself needs a backup, a retention rule and its own residual in `PRODUCTION_SECURITY_CHECKLIST.md` §7. Open: its authority and durability, and the change to `restore.prod`. Blocks doc-7.
- **Actor pseudonymisation in `document_custody`.** The actor column is a person reference, so it needs an erasure owner and a `PersonReferenceSource` under `api/.person-reference-policy`, while the custody row survives the document's erasure. Two routes: the actor id sealed under the actor's subject scope, so erasing the person is a crypto-shred with no `UPDATE` of custody; or one sanctioned anonymising `UPDATE` declared in the gate's `SANCTIONED` set with a line in its ADR. A plaintext actor id in custody is forbidden, and a stable pseudonym shared across rows still links one subject's documents, so it is rewritten to a non-linkable value on erasure or its mapping is destroyed. A `PersonReferenceSource` over sealed values must understand them. The actor-scoped idempotency record is keyed on a hash of actor and key held on the document row: state which scope seals it, or accept that erasing the actor ends replay protection. Blocks doc-2.
- **Custody against a PostgreSQL administrator.** Hash-chaining or external anchoring stays the revisit trigger of `docs/adr/regulatory-audit-trail.md` (A.8.15), not a decision made here.
- Which bounded context hosts `Documents` (new top-level or under `Backoffice`), and what is its first consumer? The ADR names bank-account evidence and progress certificates only as examples.
- Scanner: ClamAV container vs external service. The scanner needs plaintext, so the choice is to scan during ingest before sealing or to decrypt for the scan; it shapes doc-4. `evidence-lifecycle.md` puts `Received` after sealing, so scanning before sealing needs a pre-seal state and decrypt-for-scan does not.
- **Version slot.** Whether a child that ended `Quarantined`, `ScanFailed` or `Erased` frees its predecessor's slot, so a corrected version can be filed. Candidate: the unique index excludes those states, a replacement becomes a sibling, and the series projection orders by creation rather than chain position. Without it, one infected upload blocks versioning of its predecessor for ever.
- **Subject erasure over versions.** What "a subject's document" means (candidate: its uploader, the owner of the sealed-field scope) and a per-subject erasure fence recorded first, which `UploadEvidence` and new-version transactions refuse in their row transaction, so the iteration terminates; versions by other actors under the subject's predecessor are not erased by it; an `Erased` middle node blocks a successor (it needs a `Ready` predecessor) and the series projection renders the gap. Blocks doc-9.
- **Operator surface.** No story provides the entry point for the operator decisions the lifecycle names: re-scanning a `ScanFailed` document and erasing a `Quarantined` or `ScanFailed` one. It needs a voter, a custody row naming the operator (a person reference) and a reason; a re-scan resets the retry counter and never `lease_epoch`.
- **Tombstone growth from aborted uploads.** Every aborted upload, an upload over `MAX_ORIGINAL_BYTES` included, adds a keystore row and a tombstone. Open: a per-actor in-flight quota and rate limit in `UploadEvidence`, and whether such a tombstone is ever pruned (pruning reopens the late-writer hole unless its lease is long expired and its object gone).
- **Scan retry policy.** Open: the attempt cap and its backoff; whether a lease expiry (a worker that stopped heartbeating) counts toward the cap; which scanner failures count (a deterministic failure already goes `Scanning` to `ScanFailed` with no retries); how a connection reset, a scanner timeout, a scanner that crashes on the input and a worker that dies on it are classified, since none of them is plainly "unavailable"; a terminal bound independent of that classification, because with unavailable uncounted and heartbeats renewing the lease a poison document that hangs or crashes the scanner never reaches `ScanFailed` (candidate: an absolute per-claim deadline the heartbeat cannot extend, plus a ceiling on claims since the last operator decision); the backoff between unavailable retries; who drives the retry; whether `Ready` is ever rescanned. Shapes doc-4.
- **Upload transport.** The seam is the Symfony 8.1 `UploadedFile` resolver (multipart), where PHP has already spooled the whole plaintext to the upload temp directory before the controller runs: that is plaintext at rest outside the sealed path, "while streaming" and "the first read" then mean little, and `post_max_size` and `upload_max_filesize` fire before the application counter. The alternative is a raw-body stream the adapter seals as it reads. Open: which one, which layer detects overflow, and whether an oversize upload with a known size is refused before the intent record (no tombstone) as a zero-length one is.
