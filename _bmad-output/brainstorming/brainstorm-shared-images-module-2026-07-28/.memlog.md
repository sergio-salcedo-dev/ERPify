# Memlog — sesión de brainstorming

- direction (user): el módulo vive en `Shared`, no en un bounded context de negocio.
- idea (idea by user): consumidores previstos de imágenes — logos de bancos, logos de empresas, avatares de usuario, imágenes de producto, miniaturas.
- insight (by user): todos esos casos comparten el mismo ciclo — se validan, se decodifican, se normalizan, se rehacen (re-encode), se hashean, se almacenan.
- direction (user): tener en cuenta desde ya que en el futuro existirá un contexto Documents (proyectos, memorias técnicas, planos, PDFs, Excel, DWG, ZIP, vídeos, fotografías RAW).
- idea (idea by user): pipeline de imágenes = Upload → Decode → Normalize → Re-encode → Hash → Store.
- idea (idea by user): pipeline de documentos = Upload → Virus scan → Metadata → Store stream (normalmente).
- idea (idea by user): capacidades que interesan a futuro — backend Dropbox, backend S3, antivirus (ClamAV o similar), versionado documental, metadatos documentales, OCR para PDFs escaneados (muy útil en construcción).
- direction (user): ERPify está orientado a construcción y tendrá una enorme cantidad de documentación técnica.
- decision (user, hipótesis de partida): la frontera correcta sería — imágenes pequeñas → `UploadedImage` (VO simple); documentos grandes → pipeline independiente con streaming desde el primer día.
- note: `_bmad/` no existe en este contenedor remoto (sin `memlog.py` ni `resolve_customization.py`); el memlog se mantiene a mano con el mismo formato.
- decision: stance = Creative Partner; selección de técnicas = Facilitator Chosen.
- technique: batería elegida — Morphological Analysis (deep) → Assumption Reversal (deep) → TRIZ Contradiction (deep) → Time Horizon Ladder (speculative_future).
- technique: started Morphological Analysis
- idea (idea by coach): rejilla de 10 ejes independientes — A transferencia · B postura ante el byte (transformar vs preservar) · C confianza del contenido · D identidad · E backend · F ciclo de vida · G momento del procesado · H derivados · I pertenencia · J metadatos.
- insight (by coach): B y C podrían no ser independientes — re-encodear ES la desinfección de una imagen; el antivirus es la factura de haber renunciado a transformar el byte.
- decision (user): no diseñar un módulo `Files` genérico; dos bounded contexts distintos desde el principio — `Shared/Images` (imágenes pequeñas que forman parte del modelo de dominio) y `Documents` (gestión documental, archivos grandes, flujos asíncronos). Comparten infraestructura de almacenamiento, no ciclo de vida.
- idea (idea by user): `Shared/Images` extremadamente pequeño y estable — Domain: UploadedImage, ImageHash, ImageDimensions, MimeType, ImageStorage (port); Application: ImageProcessor; Infrastructure: Imagine/Libvips/GD + S3/Local/Dropbox storage.
- idea (idea by user): el dominio de Images no sabe nada de JPEG, PNG, AVIF, S3 ni Dropbox.
- idea (idea by user): pipeline de imágenes determinista — Upload → Decode → Validate → Normalize → Strip metadata → Resize if needed → Re-encode → Hash → Store.
- insight (by user): el hash se calcula sobre la imagen NORMALIZADA, nunca sobre el fichero original — iphone.jpg / .png / .webp convergen en la misma imagen canónica y el mismo hash, lo que habilita deduplicación real.
- idea (idea by user): `UploadedImage` prácticamente inmutable — id, hash, mime, width, height, size, storageKey. Nada más.
- idea (idea by user): no exponer S3/Dropbox/Local; el dominio sólo conoce el port `ImageStorage` con store/read/delete/exists, y los adapters (Filesystem, S3, Dropbox, Azure Blob, Backblaze) entran sin tocar el dominio.
- idea (idea by user): en Documents no existe UploadedImage sino `Document`; pipeline totalmente distinto y asíncrono — Upload → Store stream → Queue → Virus → OCR → Preview → Extract metadata → Index → Ready.
- decision (user): streaming desde el primer día en Documents — HTTP stream → temporary stream → S3 multipart, nunca $_FILES → memoria → string → storage; habilita ZIP de 3 GB, vídeo, DWG, IFC, PDFs enormes sin consumir memoria.
- idea (idea by user): `DocumentMetadata` con mime, pages, dpi, author, producer, creationDate, gps, camera, duration, codec…; cada extractor añade lo suyo.
- decision (user): versionado sólo en Documents (planos, memorias, contratos, certificados, presupuestos), nunca en Images.
- decision (user): antivirus sólo en Documents (DocumentUploaded → ClamAV → Ready | Infected → Rejected), nunca en Images.
- idea (idea by user): OCR no pertenece al almacenamiento sino al pipeline documental (PDF → OCR → extract text → search index); en construcción permite buscar dentro de memorias técnicas, pliegos, certificados y facturas escaneadas.
- decision (user): las miniaturas no son otro agregado sino DERIVADOS de un recurso (thumbnail_64/256/1024; preview PNG para PDF).
- idea (idea by user): separar almacenamiento físico (Storage: Local, S3, Dropbox, Azure Blob, Backblaze) de procesamiento (Processors: Image, Virus, OCR, Metadata, Thumbnail) para que cualquier pipeline combine procesadores y backends sin acoplarlos.
- decision (user, recomendación final): arquitectura en tres capas de responsabilidad — `Shared/Storage` (BlobId, BlobHash, Blob, BlobStorage port + adapters) como capacidad compartida; `Shared/Images` (UploadedImage, ImageProcessor, ImageStorage sobre BlobStorage); `Documents` (Document, DocumentVersion, VirusScanner, MetadataExtractor, OCRProcessor, ThumbnailGenerator, SearchIndexer, DocumentPipeline). Blob compartido, modelos/pipelines/invariantes independientes.
