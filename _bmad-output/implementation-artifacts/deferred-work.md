## Deferred from: code review of bank-account-search-endpoint (2026-06-30)

- **(Shared/Search) El fingerprint del cursor keyset no incluye el predicado base (`WHERE`/`JOIN`), así que un cursor cruza entre rutas con el mismo root entity.** `DoctrineSearchEngine` deriva el fingerprint de `trace(rootEntity FQCN, appliedFilters, appliedSort, appliedLimit)` — excluye el `WHERE`/`JOIN` del query base. La ruta anidada `GET /banks/{id}/accounts` (scope vía `WHERE ba.bankId`, no un `filters[]`) y la nueva colección `GET /bank-accounts` comparten `rootEntity = BankAccount` y `appliedFilters` vacíos → fingerprint idéntico, así que un cursor minted en una se acepta (en vez de 422 `invalid-cursor`) en la otra y pagina sobre todos los bancos desde la fila frontera de un banco. Limitación **pre-existente** del motor compartido; esta feature solo la hace alcanzable al ser la 2.ª ruta de lectura de `BankAccount` con inputs de fingerprint colisionantes. Sin auth en `/backoffice` hoy no es bypass de privilegios, y los clientes tratan los cursores como opacos por-endpoint, pero es una brecha real de contrato (ensanchamiento silencioso de scope, sin 422). Fix correcto: incluir un discriminante del query base (DQL del `WHERE`/`JOIN`, o el route-name) en el `QueryExecutionTrace`/fingerprint — toca el kernel de `Shared/Search` y afecta a TODOS los endpoints, por eso fuera del alcance de esta PR. Ref: `api/src/Shared/Search/Infrastructure/Persistence/Doctrine/DoctrineSearchEngine.php:106-107` (trace) y `Keyset/FingerprintCanonicalizer.php`.
