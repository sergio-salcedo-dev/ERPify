## Adversarial pass

Run by a separate read-only agent against the worktree, before the pull request
was opened, over commit `8a8500b9` and its full diff against `origin/main`. Five
findings; three applied, one dismissed as pre-existing, one raised to the user as
a question. Every claim below was re-measured by the author rather than accepted
on the reviewer's word.

**F1 — MODERATE — applied.** The commit message explained #887's exclusion with a
peer chain the published metadata does not support. `@vitejs/plugin-react`
declares `@rolldown/plugin-babel ^0.1.7 || ^0.2.0` as an OPTIONAL peer at 6.0.5
and 6.1.x alike — byte-identical — so nothing in the bump's metadata makes that
peer enter a tree the 6.0.5 in the lock does not. The `^8` was also mis-attributed:
`@rolldown/plugin-babel@0.2.3` peers `@babel/core: ^7.29.0 || ^8.0.0-rc.1` and
therefore ACCEPTS the tree's 7.29.7; the `^8.0.0` belongs to
`@babel/plugin-transform-runtime@8.0.1`, reached only because npm resolves that
disjunction to its maximum. Both verified with `npm view`.

The reviewer could not test the reproduction (read-only), so the author extended
the measurement rather than only softening the wording. Forcing npm to
re-resolve the SAME 6.0.5 that main already holds
(`npm install @vitejs/plugin-react@6.0.5 --package-lock-only --dry-run`) exits 0
with no ERESOLVE, as does untouched main — which kills the "any re-resolution
under npm 12" hypothesis and attributes the red to the 6.1.x version
specifically. What remains unestablished is WHY 6.1.x makes npm walk a peer
6.0.5 declares identically, and the message now says so instead of asserting a
mechanism. The exclusion itself stands: 6.1.0 (dependabot's exact target) and
6.1.1 both red, and each of the other four npm bumps installs alone.

**F2 — MODERATE — applied.** "Both prod stages report Debian 13 (trixie) and PHP
8.5.9" is vacuous: frankenphp's old and new digests both carry `PHP_VERSION=8.5.9`
and `trixie-20260803`/`trixie-20260824` are both Debian 13, so the sentence is
equally true of `origin/main` and distinguishes nothing. The reviewer supplied the
discriminating evidence and the author re-derived it independently from the
registry: comparing rootfs `diff_ids`, frankenphp OLD sits on
`debian:trixie-20260803-slim`, frankenphp NEW on `debian:trixie-20260824-slim`,
and node NEW on `debian:trixie-20260824` — so the two rebuilt images sit on the
same debian point release the prod stage now pins. That is the claim the message
now makes. (The reviewer additionally read the local image store as
uncorroborating; that is an artifact of the author's own `docker rmi` cleanup —
the builds ran at exit 0 and `os-release`/`php -v`/`node --version` were read out
of `docker run` against them. The correction to the sentence stands either way.)

**F3 — MINOR — applied.** `api/config/reference.php` was in the diff and the
message never mentioned it, in an enumeration that invited being read as
complete. It is benign regeneration churn — the identical `// Default: null`
hunk oscillates back and forth across several commits and no Mercure/Config
package moved — but committing an oscillating autogenerated file guarantees a
conflict with any in-flight branch that warms the prod cache, and it belongs to
none of the 14 bumps. The hunk is dropped; the file is back at `origin/main`.

**F4 — procedural — applied.** No adversarial-pass record existed on the branch,
so `gh pr create` would have been refused by the `PreToolUse` hook. This section
is that record.

**F5 — dismissed as pre-existing, raised to the user.** `roave/security-advisories`
is frozen at source reference `4991713e587e` dated 2026-07-21 on BOTH main and
head, so the targeted `composer update` did not freeze it — it was already there,
and the previous batch did not move it either. No dependabot lane watches it
because `dev-latest` has no version to bump. Not this batch's defect and not
fixed here; whether the weekly batch should also refresh it is a standing
question for the user.
