# pwa/CLAUDE.md — ERPify PWA (Next.js 16 App Router)

PWA-scoped guidance. Root [`../CLAUDE.md`](../CLAUDE.md) is authoritative for monorepo conventions, the Docker stack, and the full `make` target list — this file only covers PWA specifics. For UX, [`DESIGN.md`](DESIGN.md) is authoritative (enterprise-first UX philosophy & UI review mandate, the design-system contract — tokens, composites, patterns — and the accessibility non-negotiables). Also consult [`../docs/rules/frontend.md`](../docs/rules/frontend.md).

## Stack

- **Next.js 16** (App Router) + **TypeScript** (strict).
- **Tailwind 4** + **Shadcn UI**. Styling follows **BEM** class naming (`block__element--modifier`), mobile-first.
- **Inversify** for DI — constructor-inject interfaces defined in `domain`.
- **Vitest** for unit tests, **Playwright** for E2E.

## Folder structure

- `src/app/` — Next.js App Router (routes, layouts, route handlers). Keep components here thin; push logic down.
- `src/context/<bounded-context>/{domain,application,infrastructure}/` — DDD core. Dependencies point inward:
  - `domain/` — pure types, value objects, interfaces. **No** Next, Inversify, HTTP, or ORM imports.
  - `application/` — use cases / orchestration; depends only on `domain`.
  - `infrastructure/` — adapters (HTTP clients, storage, framework glue).
- `src/context/shared/` — cross-cutting **domain/application/infrastructure** code (ports + adapters), organised as vertical-slice capability modules. Presentation primitives live in `src/components/`; pure cross-cutting helpers are capability modules here too — see the decision rule below.
- `src/components/` — reusable UI as foundational siblings: `ui/` (raw Shadcn vendor primitives), `erpify/` (business-agnostic design-system primitives), and `cn.ts` (the class-name merge helper — the single foundational dependency `ui/` is allowed to import). Boundary rule + CI enforcement below ("Component-layer boundary"). No `src/lib/`: other pure helpers are capability modules under `src/context/shared/`.
- `tests/` — mirrors `src/` structure.

### Where shared code goes (decision rule)

Several homes exist for cross-cutting code; pick by **purpose**, not just "is it reused":

| Put it in…                                             | When it is…                                                                                                                                                                                                                                                                                             | Examples                                                                                                                                                         |
| ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `context/shared/<capability>/{domain,infrastructure}/` | a self-contained **vertical-slice capability module** — a `domain/` port + its swappable `infrastructure/` adapter, **or a pure cross-cutting helper/hook with no domain identity** (materialise only the layers it needs — a pure helper is a lone `infrastructure/`/`domain/` file, no port required) | `notification/`, `date-time-provider/`, `http-client/`, `validation/`, `observability/`, `navigation/` (`safeHref`), `uuid/`, `keyboard/`, `storage/`, `search/` |
| `app/_components/` (or a route's own `_components/`)   | a **landing/marketing** presentational component (its own raw-palette + `tw-animate-css` / CSS language) used only by its `app/` route — co-located, not shared                                                                                                                                         | `Navbar`, `Footer`, `FeatureCard`                                                                                                                                |
| `components/erpify/`                                   | an **entity-agnostic backoffice / app-shell design-system primitive** (component _or_ its presentation hook), reused across surfaces, barrel-exported from `@/components/erpify`                                                                                                                        | `DataTable`, `AsyncBoundary`, `EmptyState`, `StatusBadge`, `Spinner`, `Logo`, `SidebarItem`, `StatCard`, `useIsTruncated`                                        |
| `components/ui/`                                       | a raw **Shadcn** primitive                                                                                                                                                                                                                                                                              | `button`, `dialog`, `input`                                                                                                                                      |

The back-office (token-driven Shadcn + `@/components/erpify`) and the landing/marketing surface (raw-palette + `tw-animate-css` / CSS, under `app/_components/`) are two deliberate design languages — use the one matching your surface, don't cross-import. App-shell primitives reused by both (e.g. `Logo`) live in `@/components/erpify`. The former `context/shared/infrastructure/ui/components/` folder was retired: app-shell primitives (`Logo`, `SidebarItem`, `StatCard`) moved to `@/components/erpify`, marketing components (`Navbar`, `Footer`, `FeatureCard`) to `app/_components/`, and `PlaceholderCard` folded into `<EmptyState>` (new optional `icon` prop). The former `src/lib/` glue bucket was likewise dissolved entirely — each helper became a `context/shared/<capability>/` module (`navigation/` ← `safeHref`/`safeInternalPath`, `uuid/` ← `uuidV7`/`isUuid`, `keyboard/` ← `useSlashFocus`, `storage/` ← `useStoredPreference`, `search/` ← `useDebouncedValue`), except `useIsTruncated`, which joined its design-system owner `<TruncatedText>` under `@/components/erpify`. No generic `lib`/`utils`/`hooks` bucket replaces it.

#### Component-layer boundary — where a shared UI piece lives (Criterio A)

The home of a shared UI piece is decided **by its nature**, not by whether it consumes a domain type:

- **Reusable primitive** (button, badge, toggle, display, composable boundary) → `components/erpify`. Consuming a `*/domain` port or type does **not** promote a primitive to a capability: `ThemeToggle` (consumes the `useTheme` port), `StatusBadge`, and the error trio `ProblemDisplay` / `MutationError` / `AsyncBoundary` are erpify primitives, not capability UI.
- **System screen / boundary, or UI owned by one capability** (404/403/500, `error.tsx`, `not-found.tsx`) → `context/shared/<capability>/infrastructure/ui` — e.g. the error **screens** under `error/infrastructure/ui`, kept distinct from the reusable error **primitives** above.

Layering is enforced in CI by **two gates with different eyes** — both run from `make pwa.quality` / `pwa.quality.dry-run`. On coverage the graph gate strictly **contains** the specifier gate; what it cannot give is the editor squiggle, which is why neither is retired:

- **`no-restricted-imports`** (`eslint.config.mjs`) matches an import **specifier**, one file at a time: `components/ui` must not import `@/components/erpify`, `@/app`, or `@/context/**`; `components/erpify` must not import a bounded context (`@/context/backoffice`/`@/context/frontoffice`) or `@/app`. This is the half that puts the squiggle under the offending line in the editor.
- **`dependency-cruiser`** (`.dependency-cruiser.cjs`, `make pwa.lint.graph`) walks the resolved **module graph**, so it sees the three shapes a specifier match cannot state: transitive reach through a facade, relative escapes that dodge the `@/` patterns, and barrel re-exports. Measured: with a `@/context/**` import planted in `cn.ts`, ESLint exits 0 while the graph gate reds all ten `ui/` files that import `@/components/cn`. It also covers `src/components/*.ts`, which no ESLint block matches at all.

The one foundational helper `ui` needs — `cn` — lives at `@/components/cn` (sibling of `ui/`/`erpify/`, below the DDD context tree), **not** in `context/shared`: a vendor primitive must not reach up into the context tree for its class-name merge, so this lone helper stays out of the capability modules. `components/erpify` may build on both `ui` and `context/shared` (17 edges today, all legitimate; the graph rule is stated in the negative so they pass on their own shape, with zero exception lines).

`Resource*` primitives (`ResourceBulkBar`, `ResourceColumnPicker`, `ResourceViewToggle`) stay in `erpify`: the name denotes a generic resource-list UI reused across entities, not a coupling to `context/shared/resource/**` — moving or renaming them buys nothing.

## Env

- **Docker stack** (default): `NEXT_PUBLIC_API_BASE_URL=https://localhost`, `SYMFONY_INTERNAL_URL=http://php:80` (set in Compose).
- `NEXT_PUBLIC_APP_ENV` (`dev` | `staging` | `prod`) — public, non-secret, baked at build (`pwa/Dockerfile` ARG fed from the same-named Compose build arg). Drives client-telemetry verbosity; set per environment (`staging` enables console diagnostics, `prod` keeps them silent). `NODE_ENV` can't distinguish staging from prod (the built image is always `production`).
- `NEXT_PUBLIC_SENTRY_DSN` — public, non-secret (write-only browser ingest key), baked per environment image (`pwa/Dockerfile` ARG; `erpify-pwa-dev` locally, `erpify-pwa-prod` in prod where **required**). Empty keeps the SDK inert. Events route through the same-origin `/monitoring` tunnel (CSP `connect-src` untouched). The real secret is `SENTRY_AUTH_TOKEN` (source-map upload — deferred, never `NEXT_PUBLIC_`).
- **`NEXT_PUBLIC_*` is public by construction — allowlisted, never secret.** Next.js inlines every `process.env.NEXT_PUBLIC_FOO` literal into the browser bundle at build time, so any value behind the prefix ships to every visitor. The **only** permitted names are `NEXT_PUBLIC_API_BASE_URL`, `NEXT_PUBLIC_APP_ENV`, `NEXT_PUBLIC_SENTRY_DSN`. Adding another: register it in `ALLOWED_PUBLIC_ENV_VARS` in [`tests/next-public-env-allowlist.test.ts`](tests/next-public-env-allowlist.test.ts), add it to this list, and confirm in review it carries no secret/credential/PII. Secrets are read server-side only (`SYMFONY_INTERNAL_URL` is the pattern). The guard test fails the build (part of `make pwa.test.unit`) if any non-allowlisted `NEXT_PUBLIC_` name appears in `src/`, the `Dockerfile`, or `.env.example`.

## Rules that bite

- `Domain/` must not import from Next, Inversify, `fetch`, or any infrastructure.
- New bounded contexts follow the `domain`/`application`/`infrastructure` split — don't flatten into `src/app/`, and never reintroduce a generic `src/lib`/`utils`/`hooks` bucket (cross-cutting code is a capability module under `src/context/shared/`).
- Prefer functional components + hooks; strict TS types (no `any` unless justified).
- BEM class names — entity/surface-prefixed, `block__element--modifier` (`.banks-list__title`, `.card__header--highlighted`); not arbitrary utility clusters that escape the component. This is the HTML/CSS naming convention, independent of the `data-testid` contract (which shares the `__`/`--` characters but disclaims BEM semantics — see "Test ID rules").
- **No `maxLength` on inputs — never silently truncate typed/pasted text.** The HTML attribute cuts user input with zero feedback (a 300-char paste saved as 255). Declare the limit in the entity's Zod schema (`.max()`) so the user sees the same "must not exceed" error the API returns. Enforced by an ESLint `no-restricted-syntax` ban on the `maxLength` JSX attribute in `eslint.config.mjs`.
- **A full-document navigation goes through `hardNavigate`** (`@/context/shared/navigation/infrastructure/hardNavigate`) — it is the single place in `src/` that spells one, and therefore the single `eslint-disable-next-line no-restricted-syntax` the tree carries. Reach for it rather than calling `location.replace()` yourself: a navigation has **three** outcomes and a `try/catch` sees one. It can be refused (throws), it can commit (the document is discarded), or it can be **ignored** — a sandboxed navigable drops it silently, raising nothing — and both callers here latched state across the call, so keying recovery on the throw wedged each of them for the life of the document (an `isLeaving` that dropped every menu navigation from then on; a session-expiry claim that swallowed every later 401). `hardNavigate` reports the third outcome by elimination: a document that committed never observes its own budget elapsing, so a budget that elapses with no `pagehide` means the document stayed. The reading is one-sided on purpose — a real-but-slow navigation reports the same way — so treat `not-committed` as "assume nothing left, make the affordance usable again", never as proof of refusal, and have any live region that already announced the leaving state the **wait**, never the outcome. It refuses a destination that is not a root-relative in-app path (through `safeInternalPath`) rather than trusting its callers: this is the one line the linter will never look at again, and "callers pass a constant" is a review rule — the review rule it used to lean on had itself already failed, passing `/<TAB>/evil.com`.
- **A full-document navigation (`location.assign` / `replace`, `location.href =`, `<receiver>.location =`) needs a reason on the line above it.** Inside the app, route with `router.push()`/`replace()` from `next/navigation`; a hard navigation discards every piece of in-memory client state. Two cases are legitimate and the disable comment must say **which**: leaving an authenticated area, or running where no React context exists to reach a router from (an infrastructure adapter). Enforced by two `no-restricted-syntax` selectors in `eslint.config.mjs`, keyed on the **receiver** — `window|globalThis|self|document|top|parent` — rather than on the destination. That is deliberate: `@next/next/no-location-assign-relative-destination` folds the argument to a static string prefix, so **how a destination is spelled** decides whether it sees it (`location.assign(Routes.HOME)` escapes, `location.assign("/")` does not), it never looks at `replace()`, and it reports at `warn` under an `eslint .` carrying no `--max-warnings`, so it cannot turn a gate red in either direction. It is therefore not the control — but it is kept **on**, not disabled: measured with it forced to `error` over `src/**/*.{ts,tsx}`, 469 files report **0**, because the one legitimate call site spells the navigation `location.replace()`, which it never inspects. Zero reports means zero second rule ids and zero extra `eslint-disable` directives, so turning it off would save none of the rule-wide-disable cost that argument implies, and would give up the one reader here that resolves a receiver through scope analysis instead of matching its name. The containment is asserted rather than assumed: forced to `error` in a cloned config, every line it reports is a line these selectors report too — and `languageOptions.globals` is what lets it resolve a receiver at all, so the gate test asserts one shape per receiver, because stripping that block drops its visible corpus from 36 shapes to 8 with every other assertion still green. Both halves of the member expression are matched through computed access as well — `globalThis["location"]["assign"](u)` and `window["location"].href = u` are the same navigation spelled differently, and the receiver enumeration is what keeps them apart from a domain object reached the same way — but only when its name is outside the set: `site["location"]` is clean, while a local called `window`, `globalThis`, `parent`, `top`, `self` or `document` **is** swept in (`parent.location.replace(…)` fires, and always has) — and so, most consequentially, is a binding named `location` itself, the likeliest domain identifier of the set: `const { location } = warehouse; location.replace(/ /g, "-")` is reported as a navigation, because the bare-receiver arm cannot tell the global from a binding that shadows it. That is the price of enumerating real cross-frame receivers rather than an oversight, it is pinned as a passing test so narrowing the set stays a decision, and it is the one direction where this gate costs a rule-wide disable on innocent code. Keying on the receiver is also what keeps a domain field out of it: an ERP has `warehouse.location`, and matching "any object with a `.location`" fired on a string field that never navigates — whose disable would then, being rule-wide, also switch off the `maxLength` and test-id bans on that line. **Blind spots, measured:** an aliased receiver (`const l = location; l.assign(u)`) needs scope analysis and escapes; `location.reload()` and `window.open(u, "_self")` are navigations this rule does not claim; assigning the global binding itself (`location = u`) escapes, because every arm of both selectors requires a `MemberExpression` on the left and this left-hand side is an `Identifier` — TypeScript refuses it in `.ts`/`.tsx`, but this config block also matches `.js`/`.jsx`, where nothing does; **any** computed key that is not a string `Literal` escapes, because the match reads `property.value` — the template literal (``globalThis[`location`]``) is one member of that class and a variable key (`globalThis[k]`) another; reaching the member through a call or a branch rather than naming it escapes too (`Object.assign(location, { href: u })`, `const { assign } = location`, `(cond ? window : self).location.assign(u)`); and the receiver arms reach exactly one level, so `window.top.location.assign(u)` and `iframe.contentWindow.location.replace(u)` escape while the bare `top.location.assign(u)` is flagged — an asymmetry that is stated rather than fixed, because reaching arbitrary depth means matching any `.location` and that is the domain false positive again. Both directions are pinned by [`tests/eslint/hardNavigationGate.test.ts`](tests/eslint/hardNavigationGate.test.ts), which imports the real config — the negatives matter as much as the positives, because a widening that resurrects the domain false positive is otherwise silent.
- **Accessibility is linted here.** `eslint-plugin-jsx-a11y`'s `recommended` set runs over `**/*.tsx` / `**/*.jsx` from `eslint.config.mjs`. It is the same family SonarCloud reports as S6822/S6847/S6853, so a regression reds `make pwa.quality` instead of surfacing in a cloud analysis after the merge — which is what happened while the plugin sat in `package.json` with nothing importing it. **`settings["jsx-a11y"].components` is load-bearing, not decoration**: without it the plugin inspects intrinsic elements only, and this tree routes almost every control through a wrapper (66 `<Link>`, 80 `<Button>`, 21 `<Input>` against one intrinsic `<label>`) — the set would be green over a back-office it never looked at. Closing that cost zero findings, and the mapping is live rather than inert: pointed at `a` instead, `Button` alone produces 191. Extend the map when a new primitive wraps an intrinsic control.
  The set **follows upstream** rather than being frozen, so a release that adds a rule is adopted instead of silently skipped; the direction that costs is bounded by [`tests/eslint/jsxA11yRuleSetGate.test.ts`](tests/eslint/jsxA11yRuleSetGate.test.ts), which classifies all 39 shipped rules and reds **naming the moved rule** when one enters, leaves or flips severity. It reads the **resolved** config, not the block that declares it — ESLint applies the last matching block, so reading the declaration would let a later block downgrade the whole set to `warn` (invisible under an `eslint .` with no `--max-warnings`) with every assertion still green. That matters because the gap is wide: measured, `recommended` reports 5 findings on this tree and every shipped rule forced on reports 54 — 21 of them behind one unlisted rule — so an unpinned minor could red product files in bulk under a `chore(deps)` title naming none of them.
  An exemption is an `eslint-disable-next-line <rule>` with its reason on the line above, **never** a config-level `off`: `off` hides the next occurrence for ever, including one in a dialog or a surface where the finding is real. Before writing one, check the finding is not simply true — a vendor primitive forwarding `htmlFor` through a spread reports `label-has-associated-control`, and naming the prop makes the rule go quiet with no directive at all. **Placement is a real trap** — a directive above `return (` does not cover the JSX under it: it reports "unused" _and_ the rule still fires. It goes immediately above the element, inside the parentheses. `linterOptions.reportUnusedDisableDirectives` is an **error**, which catches a stale directive in `pwa.lint.dry-run` and CI — but **not** under `make pwa.quality`, which runs `eslint . --fix`: there ESLint deletes the directive and exits 0, taking its paragraph of reasoning with it. So a stale exemption is caught before merge, never at the moment it goes stale.
- **No linter-narration comments.** Never add a comment whose only purpose is to justify a construct against a lint/Sonar rule ID (e.g. `// block body avoids S6544/S3735`). Make the linters pass and let the code stand; for a non-obvious pattern state the _intent_ ("fire-and-forget", "stable callback") without naming rules. The only allowed rule-referencing comment is the load-bearing `// eslint-disable-next-line <rule>` directive.
- **A test that opens a row's `⋯` overflow menu goes through `openRowDeleteItem(surface, id)`** ([`tests/app/backoffice/banks/_interactions.ts`](tests/app/backoffice/banks/_interactions.ts)) — never its own `fireEvent.click(trigger)` followed by `await findByTestId(item)`. Under jsdom a just-opened Base UI popup can close again before its content mounts, so a single-shot open is a race: it survives a thousand runs and then goes red under CI parallelism, where the 1000 ms `findBy` budget runs out. The helper retries the **open** (three attempts) and awaits the item single-shot on the last one, so a Delete that genuinely never renders still fails. `surface` is the testid surface owning the row (`banks-table`, `banks-cards`, `bank-accounts-table`). **Reading the failure:** the error names the missing `…__delete-<id>`, but if the preceding `…__actions-<id>` resolved, the row is present and the failure is the _open_, not the data. Enforced by a `no-restricted-syntax` selector in `eslint.config.mjs`: a statement awaiting `…__delete-<id>` fails the build when an earlier sibling statement in the same block reached for that row's `…__actions-<id>`, while a lone presence assertion on the same testid stays legal. Like the testid bans below it is a syntactic heuristic — a testid built by concatenation, extracted to a variable, or reached through a differently-named helper escapes it — and the guard that keeps the selector from matching across whole `it(…)` blocks also skips a genuine racy pair whose statement carries an inline arrow function; both gaps rest on review.
- **Question the status quo** (root [`../CLAUDE.md`](../CLAUDE.md) → "Question the status quo — argued improvement"): on every PWA change, distrust the existing design _of the code you touch_ and look for the real improvement toward clean architecture / SOLID / DDD — a component reaching infrastructure directly instead of an injected `domain/` port (DIP), logic that belongs in `application/` leaking into a `page.tsx`, a client/server boundary that pulls hooks into the RSC payload, a re-implemented primitive that already lives in `@/components/erpify` or a `@/context/shared/<capability>` module. Propose with principle + objective (maintainability / performance / speed) + cost; let the user decide scope — never a unilateral refactor or a speculative abstraction (Rule of Three / YAGNI gate it).

### Vercel `react-best-practices` skill — house overrides

The project-scoped `vercel-react-best-practices` skill (`.claude/skills/`) is a **performance reference** — 70 Vercel Engineering rules (waterfalls, RSC data-fetching, re-render, bundle). Apply it with judgement (_"performance is measured, not asserted"_, root [`../CLAUDE.md`](../CLAUDE.md)) and treat it as **subordinate to this file** on conflict. Three of its rules are overridden here:

- **`bundle-barrel-imports`** ("avoid barrel files") — the `@/components/erpify` barrel is an architectural public-API boundary, not a tree-shaking accident: measured, **zero** modules import `@/components/erpify/<Name>` deeply. Keep it; if bundle tracing ever bites, reach for `optimizePackageImports` in `next.config.ts`, don't dissolve the boundary. **A capability's public API is its per-LAYER barrel, not a capability-root one.** Nine real barrels exist under `context/shared/**`, all of them `…/<capability>/{domain,infrastructure}/index.ts` (or one level deeper, e.g. `notification/infrastructure/Toast/`) — that is what "export it from the matching barrel" means below, and what `docs/architecture-pwa.md` documents for the Observability singleton. What does **not** exist is a capability-root `context/shared/<capability>/index.ts`: **zero** across 24 capabilities, while **567** imports reach past the layer barrels into individual files. This line used to call that non-existent boundary a barrel "enforced in CI" — wrong twice over, since it is not a barrel and nothing enforced it. Creating it would mean 24 new files and an allowlist of 567, so it is a decision with its own measurement, not a rule to state here. The one barrel a gate actually checks is the erpify one, and only for the error screens (`erpify-barrel-excludes-error-screens` in `.dependency-cruiser.cjs`).
- **`client-swr-dedup`** ("use SWR") — data access goes through the injected `http-client` port (`FetchHttpClient`) + `useMercureRealtime`, never a bare library (DIP). Any request dedup lives behind that port, not via SWR bolted on top.
- **`rendering-conditional-render`** ("ternary, not `&&`") — stylistic, not load-bearing; follow the touched file's own convention.

## Security review (mandatory on every change)

Every PR — even small fixes — runs the checklist in the root [`../CLAUDE.md`](../CLAUDE.md) ("Security review on every change"); its **Frontend (`pwa/`)** list is authoritative. The XSS rules below are part of that checklist, not optional.

### XSS prevention rules

React escapes JSX text by default but does **not** block script-bearing URL schemes, and several attribute / sink categories remain attack surface. Treat as load-bearing:

- **Dynamic `href` / `src`** — every URL influenced by API data, route params, query strings, or user input MUST go through `safeHref(value, fallback)` from `@/context/shared/navigation/domain/safeHref` (rejects `javascript:`, `data:`, `vbscript:`, `file:` regardless of casing/whitespace obfuscation). Combine with `encodeURIComponent` on the dynamic path segment. Never interpolate raw API data into an `href` template literal.
- **`router.push` / programmatic navigation** — same rule: wrap the URL in `safeHref`.
- **Redirect targets from untrusted sources** (a `?next=` param, location state, an API payload) — `safeHref` blocks dangerous schemes but still allows an absolute `https://evil.com`, so a redirect target MUST additionally pass `safeInternalPath(value, fallback)` from `@/context/shared/navigation/domain/safeInternalPath`, which accepts only a root-relative in-app path (rejects absolute, protocol-relative `//host`, and backslash-smuggled `/\host`). The login return-URL flow is the reference (`RequireAuth` writes `?next=`, `LoginForm` reads + validates it).
- **`dangerouslySetInnerHTML`** — banned outside specific, sanitized Markdown/SVG embeds; if genuinely needed the input MUST come from a vetted sanitizer (e.g. DOMPurify) and be reviewed. Never for "richtext"/"format-as-bold" hacks.
- **`innerHTML` / direct DOM writes / `document.write` / `eval` / `new Function(string)`** — banned. Use React state.
- **Non-executing attributes (`title`, `aria-label`, `data-*`)** — safe to interpolate (React escapes them). Still keep static `aria-label`s where row context conveys the resource name (see `BanksTable`'s actions cell).
- **Server response headers** — baseline lives in `next.config.ts#headers()`: strict-ish CSP (`object-src 'none'`, `frame-ancestors 'none'`, `base-uri 'self'`, `form-action 'self'`, `upgrade-insecure-requests`), plus `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy`, COOP/CORP, HSTS. `script-src` keeps `'unsafe-inline'` for now (Next.js hydration); future state is a nonce-based CSP via `middleware.ts`. Do NOT add `'unsafe-eval'` outside development.
- **Clipboard / navigator APIs** — `CopyButton` is the canonical path (never trusts the value as HTML). Don't compose your own `navigator.clipboard.writeText` flows from entity components.

## Shared building blocks (use these, don't reinvent)

## Test ID rules

A `data-testid` is a **first-class, published QA interface** — app-wide-unique and **independent of DOM/CSS structure**, stable across styling/layout refactors. It addresses _what an element is for QA_, never _where it sits in the markup_ (so two elements with the same id never land on the same page — Playwright strict-mode locators fail with "more than one element matched"). Contract + rationale: [`../docs/adr/test-id-naming-contract.md`](../docs/adr/test-id-naming-contract.md).

- **Coverage — every CTA and QA target carries a stable testid, proactively (ADR D7).** Any interactive control (button, link/anchor, dialog trigger, form submit, pagination) and any element a test would assert on gets a `data-testid` **whether or not a test consumes it today** — a QA address outlives the current suite, so "no consumer yet" is never grounds to omit or delete one. This is a **presence** rule, enforced by review: the lint bans below reject a _malformed_ testid but cannot require a _present_ one.
- **Grammar is `<surface>__<element>[--<state>]`, but `__`/`--` are lexical separators with NO BEM semantics** (e.g. `banks-list__title`, `banks-pagination__next`). `<surface>` names a semantic feature (not a CSS block); `--<state>` is a QA variant (not a BEM modifier). The characters overlap the CSS BEM convention by history only — never copy a `className` into a `data-testid`.
- For lists/tables, encode row identity with the **backend entity id** (a UUID v7) from the API — e.g. ``data-testid={`banks-table__row-${row.id}`}`` for the row and `banks-table__edit-${row.id}` / `banks-table__delete-${row.id}` for per-row actions. Unique by construction. **Never key a testid by array index/position** (`index`/`i`/`idx`/`n`) — unstable under reorder, filter, or pagination. Do NOT emit a parallel `data-row-id` — `data-testid` is the canonical row identity. `<DataTable>` enforces this with its `rowTestId` prop.
- For reusable primitives, **never hardcode a testid** — accept a `testId` / `testIdPrefix` prop (see `<DataTable testId rowTestId>`, `<CopyButton testId>`, `<DateField testId>`); the consumer owns `<surface>`, the primitive owns `<element>`. Hardcoding traps every consumer into the same id and triggers strict-mode failures.
- **Never derive a testid from the presentation layer** — a `cn()`/`clsx()`/`cva()`/`twMerge()` call or a `className` value must not become a `data-testid`. It is a QA address, not a style hook.
- Enforcement (`make pwa.quality` + CI), never weakened:
  - The guard `tests/data-testid-uniqueness.test.ts` walks `src/` and fails if a **static** `data-testid="..."` literal appears in more than one file or twice in one file.
  - Two contract bans (four `no-restricted-syntax` selectors) in `eslint.config.mjs` fail the build — on `data-testid` **and** on the `testId` / `testIdPrefix` prop channel (where consumers author the value, D3) — for a presentation-derived id (class-helper / `className`) or a dynamic value (template or `+` concatenation) keyed by a positional index (`index`/`i`/`idx`/`n`). The bans are syntactic heuristics (they don't chase every spelling — extracted vars, aliased helpers, `.join()`); completeness rests on review, per the ADR.

## Route-level accessibility (a route names itself, and takes the focus)

Two things are owed by every route in a title-gated tree, and neither is visible to `jsx-a11y`:

- **A title of its own.** Next's route announcer reads `document.title` and speaks **only when it changes**; its `<h1>` fallback runs when the title is falsy, and `app/layout.tsx` fixes a static one, so on this tree that fallback is dead code. A route declaring no title inherits the root's, the title never changes, and the navigation is **never announced** — the state 47 back-office routes were in, separately all four `(auth)` routes (`login`, `forgot-password`, `reset-password`, `accept-invitation`), and `/status` (fixed via a `layout.tsx`, being a Client Component). A Server Component page declares `export const metadata`; a Client Component page cannot (`metadata` is server-only) and gets a `layout.tsx` carrying it. `banks/[id]/accounts/new` is the precedent for the other direction — it takes `params: Promise<{ id: string }>` as a prop and is a Server Component again, so its title lives on the page and the segment layout is gone. The remaining client routes stay client because they are interactive surfaces (local state, effects, realtime), not for want of that precedent. `/` is the one deliberate exception: it inherits the root's default title by design (it IS the site's default identity), not by omission — the defect is two-or-more routes sharing an inherited title, and after `/status` got its own, nothing else does. Gate: [`tests/backoffice-route-titles.test.ts`](tests/backoffice-route-titles.test.ts), which runs the same set of checks over each gated tree (`app/backoffice`, `app/(auth)`, `app/(errors)`) — resolving each route through its own metadata then every layout above it up to that tree's root, asserting the root layout stays title-free (a title _there_ satisfies every route by inheritance and reinstates the silence), distinctness asserted both within each tree and across the union of all three (a successful login does a real client-side `router.push` from `(auth)` into `backoffice`, so that boundary is one a screen reader actually crosses). The title itself is read with the TypeScript compiler's AST rather than a text regex: a regex scanning for `title:` cannot tell a top-level `metadata` property from one nested in a sub-object (`openGraph: { title: … }`), and cannot tell a live `title:` from one sitting inside a comment — a comment is trivia attached to a token, never a node the walk visits. The walk also unwraps a `satisfies`/`as`/parenthesized initializer; it does NOT resolve a `title` written as a shorthand property or reached only through a spread, both unused today. A green says each route resolves a title, never that the title is meaningful or distinct from its neighbour's; two routes sharing a string announce nothing when you move between them.
- **The focus, on navigation.** Next calls `.focus()` on the changed segment's first host node (`layout-router.js`), which is the page root — and no page root carries `tabIndex`, so the call is a no-op and focus stays on `<body>`, making the next Tab restart at the skip link. `<main>` in `BackOfficeLayoutClient` carries `tabIndex={-1}` and takes the focus on every `usePathname()` change, which also makes the skip link land (a fragment link moves focus only to a focusable target). Keyed on the pathname and not the full URL: the lists write filters and cursors to the query string, and keying on those would pull focus out of a filter input on every keystroke. A page that placed the focus itself keeps it — `autoFocus` lands in the commit phase, ahead of this passive effect, so only a stranded `<body>` is corrected. Pinned by [`tests/app/backoffice/backOfficeLayoutRouteFocus.test.tsx`](tests/app/backoffice/backOfficeLayoutRouteFocus.test.tsx), including both limits.

**`<output>` is a live region — never a badge.** HTML-AAM maps it to role `status`, so an `<output>` announces politely whenever its content changes. Right for the result of a user action, wrong for a badge rendered once per row: a table of N rows declares N polite regions announcing nothing and competing with the ones that do. `jsx-a11y` ships no rule for it, so the set wired in `eslint.config.mjs` looks green over exactly this defect. Registry + gate: [`tests/live-region-surfaces.test.ts`](tests/live-region-surfaces.test.ts) — per file, because a file arriving with its first `<output>` is when the decision is owed, and an entry has to state why that surface announces. Detection walks the TypeScript AST (a JSX `<output>`, or a `createElement("output", …)` call resolved through the file's own `import … from "react"`, alias included) rather than a text regex, so a comment or a string mentioning `<output` cannot compete with a live one, and a dynamically created element is still found under whatever local name its import binds; a tag whose name is itself a variable stays out of scope on purpose — that is the boundary of what a static read can answer, not a defect.

## Accessibility rules for action buttons

Every interactive control that triggers an action (button, anchor styled as button, dialog trigger, pagination control, form submit/cancel) must carry **all** of:

- `title` — descriptive hover tooltip; include the resource name when meaningful (e.g. `title={\`Edit bank ${row.name}\`}`).
- `aria-label` — keep the accessible name **short and static** (`"Edit"`, `"Delete"`, `"Previous page"`). Inside a `role="cell"`/`role="row"` the cell's accessible name is computed from descendant control names, so dynamic labels containing row text break Playwright strict-mode locators (e.g. `getByRole("cell", { name: "Acme Savings" })` matches both the name cell and the actions cell) — put the dynamic part in `title` instead.
- A textual fallback for icon-only controls — visible text and/or `<span className="sr-only">…</span>` — so the control has a name when CSS fails to load.
- `aria-hidden="true"` on every decorative icon inside the control.
- For pagination/navigation controls that have no valid target (no previous or
  no next page), **hide** the control instead of rendering it disabled — a
  disabled control is still discovered by assistive tech and adds noise.
  - **Exception — cursor-only keyset pagination (D-A11y, PR3 / `BanksPagination`):**
    the prev/next pair is **always rendered and `disabled` when the envelope link
    is `null`, never hidden**. The keyset ADR (`docs/adr/keyset-pagination.md`,
    IMPLEMENTATION LOCKED, AR15) governs this scope and overrides the hide rule
    here: a persistent, well-labelled pair (`aria-label` + `title`, decorative
    icons `aria-hidden`) is a predictable, discoverable affordance, and keeping
    the control in the DOM preserves the system state the envelope expresses
    (and the Behat/e2e determinism that asserts `toBeDisabled()`, not absence).
    Hiding would drop that state. New cursor-only lists follow `BanksPagination`,
    not the hide rule above.

For destructive actions also wire a confirmation dialog (`Dialog.*` from `@/components/ui/dialog`). When the mutation fails, the dialog **closes itself** and the failure surfaces in a persistent `<MutationError>` from `@/components/erpify`, anchored to the mutation's origin (above the list/grid, under the detail H1, above the form) — never inside the dialog, and never a toast alone (the error toast is only a transient pointer to the persistent surface). The surface receives focus, stays until dismissed / replaced by a retry / cleared by a success, and lets the user copy the message, the `type · status` code, the correlation id, and the full problem JSON (production builds omit `debug`, mirroring the render). Typed recovery actions go in its `action` slot (`bank-not-found` → "Refresh list"; `bank-in-use` → "View accounts", routing to the bank's accounts surface). Never silently dismiss failures, and never synthesize problem payloads client-side. Contract: EXPERIENCE.md § «Errores de mutación — superficie persistente» (2026-06-04).
