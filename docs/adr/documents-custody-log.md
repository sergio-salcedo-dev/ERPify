# ADR — Documents: snapshot plus append-only custody log, erasure seam and storage port

> **Status:** accepted · **Date:** 2026-11-05 (D6: 2026-11-06, D8: 2026-11-12, D9: 2026-11-16, D10: 2026-11-17, D11: 2026-11-17, D12: 2026-11-19) · **Scope:** `api/src/Documents/Document` (aggregate, custody log, storage port, erasure seam, upload intent) and `api/src/Shared/Privacy/Application/PersonReferenceErasure.php`.
>
> Builds on [`images-vs-documents-conservation-contract.md`](./images-vs-documents-conservation-contract.md) (why evidence is a separate context) and the Documents spec decisions of #268. The application is **not in production**; nothing here carries backward compatibility.

## Context

`Documents` holds evidence-class binaries: the original byte is the proof, so the history of what happened to a document is part of the product. The persistence strategy was decided before this code (state-oriented, event sourcing rejected on measurement: the event store has no per-aggregate stream loading and its `aggregate_version` is informative), and this ADR records what the first code under it commits to and what it discarded.

## Decisions

### D1 — `Document` is a snapshot row; every change also appends a `document_custody` row in one transaction

Two tables, not one aggregate with children: `Document` (state-oriented, extends `AggregateRoot`) and `DocumentCustody` (a `final readonly` entity mapped `#[ORM\Entity(readOnly: true)]`, so the ORM never emits an `UPDATE` for it). A new document and its custody row 1 share one transaction (`ReceiveDocument`); a rollback leaves neither. **Each version is its own aggregate**: a first version's `series_id` is its own id and its `predecessor_id` is `NULL`; a successor copies `series_id` from its locked predecessor (D12). Both are without a setter and `updatable: false`, so no cycle can form and none is checked; the successor exclusion is D12's. `scope_id` is random, never derived from the document id, and carries its own `UNIQUE` (two documents sharing an encryption scope would let one's erasure shred the other's bytes).

`document_custody.event` is a string backed by a PHP enum holding only what is written today, with **no database CHECK**, so a later story adds a case without a migration; the cost is that a typo in a future writer is caught by the enum, not by the database. The value names a custody *fact*, never the document's current state, so a stored value never changes meaning. `document.state` does carry a CHECK, because the lifecycle is closed.

**Amendment (scan):** `document_custody.actor_id` is nullable and NULL means *the system*: the scan's own facts (the first claim, every verdict, the cap sweep) have no person to name, and inventing a service identity would put a pseudonym in the one column the erasure rewrites. An operator decision always names the operator and carries its `reason`, a nullable `document_custody.reason` column that only an operator decision (a re-scan, an erasure) and the system's erasure use. The constructor still refuses the erased-person marker and an empty string, `PersonReferenceSource` skips NULL (the keyset reader already does), and the actor index stays.

**Amendment (erasure):** the erasure a restore replay or the completion sweep finishes is the system's too — actor NULL, reason `ledger-replay` or `ledger-completion` — and **never the erased-person marker**. The ledger holds scope ids only, so the operator who authorised it is not recoverable by design; and `ErasedPersonMarker` keeps its one meaning, "a person who was erased", which `DocumentCustody` keeps refusing as a recorded actor. A system fact written with the marker would be indistinguishable from an erased operator in the trail, in `PersonReferenceSource` (which excludes the marker) and in the actor anonymisation. **Discarded:** relaxing the constructor for two events.

**Discarded:** event sourcing (cost measured in the spec), and a PostgreSQL `SEQUENCE` for `seq` (a rolled-back append would burn a number and leave a gap among committed rows).

### D2 — `seq` is computed under the lock on the document row; the unique constraint is the second defence

`AppendCustody` is the transaction owner: lock the `document` row (`FOR UPDATE`), compute `MAX(seq) + 1`, insert, commit. A foreign-key insert from another connection also blocks on that lock (`KEY SHARE` conflicts with `FOR UPDATE`), which `DocumentPersistenceFunctionalTest` measures from a second connection. `UNIQUE (document_id, seq)` fires only when something computed a stale number; that violation maps to `CustodySequenceCollision` and the use case re-runs the **whole** closure — lock, number, insert — up to three attempts, then answers `TransientTransactionFailure`. Re-running only the INSERT would repeat a number already computed from a stale read. A `deadlock_detected` is left to `DoctrineTransactionManager`, which already answers it; retrying it here would hide a lock-order defect.

The idempotency constraint (`uniq_document_idempotency_key_hash`, nullable and global over the actor-scoped hash) is a conflict (`ConcurrentUniqueWrite`, 409) and is **never retried**. A unique violation is classified by constraint **name**: DBAL exposes no structured name and PDO none, so `ViolatedUniqueConstraint::is()` asks whether the driver message contains the exact name, delimited on both sides by a character that cannot continue an identifier. It never parses the sentence around it, because `lc_messages` translates that sentence and a lost race would then read as a 500; the delimiters keep a column name or a longer constraint name from reading as this one. Anything else is rethrown unchanged. The driver text carries the offending key and is never chained into the exception the caller sees.

### D3 — Custody is append-only except one sanctioned statement: the actor anonymisation

A person's erasure rewrites `document_custody.actor_id` and `document.uploader_id` to **one constant marker** (the nil UUID, `ErasedPersonMarker::UUID`) and nulls `document.idempotency_key_hash` (replay protection for that actor ends, accepted). Sealing the actor under the subject's scope is circular — the scope id derives from the person — and a per-subject pseudonym kept in the row is the stable identifier the erasure exists to end. Cost: custody is no longer *absolutely* append-only, and it is not claimed cryptographically immutable. A document is never erased by this path: the uploader is not the subject of the evidence.

Two DBAL statements in the caller's transaction, each `UPDATE … WHERE id IN (SELECT id … WHERE <person> = :subject ORDER BY id FOR UPDATE)` — the shape of `DbalAuditActorAnonymiser` — documents first, then custody rows, in ascending id. Neither filters on state, so `Erased` rows are rewritten like any other, and both refuse to run outside a transaction (a `FOR UPDATE` outside one releases its locks at the end of the statement and orders nothing).

**Enforcement is a source gate, and nothing more:** `make php.lint.document-custody` (`DocumentCustodyMutationGateTest`, engine `tests/Support/DocumentCustodyMutations.php`) closes the set of statements `api/src` issues against `document_custody` to this one. It reads SQL text, DBAL's table-level `update()`/`delete()`, DQL and the ORM query builder naming the entity class, and `remove()` in a file naming the entity; each surface has a negative test and each shape it cannot read a pinned blind-spot test. No database role separation, `GRANT`, `REVOKE` or trigger exists in the tree and the gate sees neither a migration nor runtime-built SQL; adding a restricted role or a `BEFORE UPDATE/DELETE` trigger is a separate decision.

**ORM identity-map limit.** The statements are bulk DBAL on purpose, and nothing in the erasure path loads a `Document` or `DocumentCustody` into the unit of work: a managed instance read before the rewrite would keep the subject's id in the identity map, and a bulk statement refreshes none. Tests read the result through DBAL for the same reason. The foreign key `document_custody.document_id → document.id` has no cascade (re-injected by a `postGenerateSchema` listener) and the mapping has no association, so no ORM cascade or `orphanRemoval` can reach the log; a document is never physically deleted.

### D4 — The erasure reaches Documents through a `Shared\Privacy` port both consumers call

`PersonReferenceErasure::eraseReferencesTo(string): int` lives in `Shared/Privacy/Application` (always importable, so no allowlist or deptrac `skip_violations` entry). `FulfilIdentityErasure` and `ResweepErasedSubjects` receive it and call it inside their one transaction, after the identity, session, audit and business-log rows they already hold; its count joins `FulfilIdentityErasureResult` and the compliance metadata (`document_references_anonymised`, declared in `AuditMetadataKey`). `PurgeUserDocumentReferences` is its only implementer today and the named owner of both person columns in `api/.person-reference-policy`; each column also has a `PersonReferenceSource` that excludes the marker, so a correctly erased row is never reported. A row an in-flight action of the erased person commits after the purge statement's snapshot is missed by the `UPDATE`; the re-sweep and the detective source are the controls for that race.

Global lock order: identity, session, audit, event store, then upload intents, then documents, then their custody rows, each class in ascending id. The purge rewrites the subject's upload intents first (actor to the marker, key hash NULL, `Declared`/`Streaming` expired, nothing deleted), so a commit in flight has either committed — and its document is rewritten next — or is blocked on its intent row and finds it expired. `ErasureLockOrderTest` and `ErasureLockOrderFunctionalTest` hold it, the latter asking the database which rows are held when the document statement runs. **Discarded:** one `PurgeUser…` call per context in each consumer (every new context edits both), and a tagged collection now (one implementer; the next turns the alias into a collection by tag, as `PersonReferenceSource` already is).

### D5 — `Documents` has its own storage port, and its adapter is native filesystem calls

`DocumentStorage` carries `stage` (stream to a staging key under the scope, refusing an existing key), `promote` (create the destination exclusively, typed failure when it exists or the source is absent, not idempotent), `open` (a read stream or a typed absence) and `delete` (idempotent, naming the area it touches so a sweep of staged objects cannot reach the final one). It shares nothing with `ImageStorage`, declares no WORM guarantee, and carries neither key nor library message in a failure. The boot probe, the reaper and the fsync policy are D6's.

The first adapter uses `fopen(…, 'x')` and `link(2)` + `unlink(2)` rather than Flysystem: the library's local adapter overwrites on write and has no create-if-absent, and `rename(2)` silently replaces its destination. `link(2)` creates the destination exclusively and fails with `EXDEV` across mounts exactly as `rename(2)` does, so atomicity is claimed only for `staging/` and `final/` on one filesystem. The adapter's test asserts it on the test's own temporary filesystem only; the deployed volume is probed by the boot probe (D6: create a file in staging, promote it into final, remove it, refuse to start on any failure), not assumed from `st_dev`. The roots live on a volume of their own (`document_storage`, `DOCUMENTS_STORAGE_PATH`, a literal equal to the mount target); the entrypoint refuses to start when that path is not a mounted volume, and the adapter never creates a root, because an invented root in the container layer turns every later `delete` into a confirmed erasure of bytes elsewhere. Backup of that volume is not in place — an open residual of `PRODUCTION_SECURITY_CHECKLIST.md` §7.

### D6 — Ingest is an upload-intent state machine; the intent row is the lock the commit and the reaper share

`upload_intent` (`UploadIntent`) is created by the declare step and moves `Declared` → `Streaming` (the PUT's claim, before a byte is read or a key minted) → `Committed` (the commit, with the document id), or to `Expired` (the writer's own abort, the person purge, or implicitly by time: a `Declared` intent past `ttl_expires_at`, a `Streaming` one past `lease_expires_at` or `upload_deadline_at`). Every judgement of time uses the database clock read inside the transaction holding the row. Every transition to `Expired` nulls the key hash and sets the lease to now. The deadline is fixed at the claim (`ceil(size / 256 KiB) s + 60 s`); the heartbeat renews the lease (90 s, every 10 s of reading) and never past it. The constants live in `UploadLimits`.

The edge bounds the body before any of this: Caddy admits up to `MAX_ORIGINAL_BYTES` only on the canonical PUT path and only for a request carrying the session cookie, and 1MB otherwise, because the server receives a refused request's body whole before it answers — an anonymous client must not be able to trickle 100 MiB into a worker thread ahead of authentication. The cookie's value is the application's to judge.

No transaction spans the stream: the claim commits, the sealer mints the key after the first chunk and commits on its own, then one short transaction files the document. **Lock order, each class in ascending id:**

| Flow | Takes, in order |
|---|---|
| Claim | intent row → advisory lock per actor → advisory lock global (nothing else while held) |
| Heartbeat, writer's abort | intent row |
| Commit | intent row → keystore row of the not-yet-visible scope (the one sanctioned inversion, reachable only through the intent lock) → document insert + custody row 1 (a first version inserts its `document_series` row first) |
| Commit of a new version (D12) | intent row → keystore row of the new scope → series row → predecessor document row → document insert + custody row 1 |
| Close of a series by its erasure (D12) | series row alone, in its own transaction, before any version is erased |
| Reaper | intent row → keystore row → (staged delete, tombstone, intent delete) |
| Person purge | intent rows → document rows → custody rows |
| Roll-forward | document row → outbox insert of the scan wake-up (a plain insert) |
| Scan claim, heartbeat, verdict, return, cap sweep, re-scan | document row (one `UPDATE`, the compare-and-set) → custody append, which takes the same document row lock again → (re-scan only) outbox insert of the wake-up |
| Re-scan of a version that has a predecessor (D12) | series row → predecessor document row → its own row (the compare-and-set) → custody append → outbox insert |
| Re-scan of a first version (D12) | series row → its own row (the compare-and-set) → custody append → outbox insert |
| Declare | advisory lock per actor (declare namespace) → existing intent row (replay) → intent insert |

The commit asserts under both locks that the intent is `Streaming` with a live lease and deadline and that the scope is `Live` (`Absent` is a snapshot and never passes); actor and key hash come from the locked row. The reaper rechecks expiry and the absence of a document row under the same two locks: a claimed intent with no document gets its staged object deleted and an `aborted-upload` tombstone (minted even with no key), a never-claimed one is deleted with no tombstone, and one whose scope a document holds is deleted alone. `UploadLockOrderFunctionalTest` interleaves the pairs with a second connection and shows the waiter rechecks and stands down. A committed row owns its staged object: only the roll-forward (rechecking under the document lock that the row is still `Received`) moves it, accepting a final object already present and never overwriting it — and syncing the final directory before reporting it promoted (`syncFinal`), since a run that died after the move may have died before its sync; the staging age sweep deletes only an object older than 20 min that neither a row nor a live intent holds, its limit counting deletions rather than names walked; a final object with no row is alarmed on, never deleted. Every sweep logs and passes over an item it cannot process, so one poisoned row never stops a batch, and a writer's abort deletes its staged object only after expiring a still-`Streaming` intent under its lock — a commit whose answer was lost leaves a `Committed` intent whose document owns that object. The server's own plaintext copy of the body — PHP's `upload_tmp_dir` spool, held by the worker thread until its next request — is destroyed when the upload route's response leaves, filed, aborted or refused: the body is read to its end there and the one spool matching exactly what was read is truncated and unlinked, never one that could be another in-flight request's.

The scan wake-up is published inside the transaction that sets `promoted_at`, in the writer's promotion and in the roll-forward alike: the bus refuses an `async`-routed message outside a transaction, and the outbox row commits with the mark. **Discarded:** publishing after the commit (refused by the bus). The cost is that a message that cannot be published rolls the mark back and leaves the row for the roll-forward, so a down `async` transport delays the obligation, not only a hint.

**Every pair, interleaved** (`UploadLockOrderFunctionalTest`, `UploadLockOrderPairsFunctionalTest`, a real second connection holding one side mid-transaction). The first lock each flow takes decides the pair: a shared first lock serialises, disjoint lock sets never wait, and no flow takes the other's first lock second, so no pair can close a cycle.

| Pair | Shared first lock | The waiter, once the holder commits |
|---|---|---|
| claim / commit | intent row | a claim after a commit answers the document; a commit after a claim files it |
| claim / reaper | intent row | a claim after the reaper is gone; the reaper after a claim stands down on a live stream |
| claim / purge | intent row | a claim after the purge is gone (actor rewritten); the purge after a claim expires the stream |
| commit / reaper | intent row, then keystore row | a commit after the reaper aborts; the reaper after a commit stands down, the key stays live |
| commit / purge | intent row | a commit after the purge aborts (expired); the purge after a commit rewrites the filed document next |
| reaper / purge | intent row | the reaper after the purge tombstones the minted scope; the purge after the reaper rewrites nothing |
| purge / roll-forward | document row | the roll-forward after the purge still promotes; the purge after the roll-forward rewrites the row |
| scan transitions / person purge | document row | the transition after the purge still applies (the purge rewrites only the uploader and the custody actor); the purge after a transition rewrites the row it left |
| scan transitions / roll-forward | document row | the roll-forward rechecks `Received` and `promoted_at IS NULL` under the lock; a claim needs `promoted_at`, so the two never act on one row at once |
| roll-forward / claim, commit, reaper | none (document row vs intent and keystore rows; a committing document is invisible until commit) | never waits |

**Discarded:** deleting the intent at commit (the intent keeps holding the key until its 7-day retention sweep, then the document's own `UNIQUE` and the declare's re-read take over); a `NOT EXISTS` guard inside the reaper's `UPDATE` (under `READ COMMITTED` its snapshot predates a row committing while it waits); a pre-allocated document id on the intent (the scope id is enough to join them, and a document id before the document exists invites a dangling reference).

### D7 — `RetentionReason` is a closed set of four values, accepted by the owner

`contract-execution`, `tax-and-accounting`, `technical-file` and `legal-claims`, required at declare beside the six `LegalBasis` values of GDPR Art. 6(1). The specification fixes a closed enum but not its members; these four were chosen during implementation and accepted by the owner on 2026-11-08. Period, anchor, jurisdiction and enforcement of a retention still wait for counsel's matrix, so the enum names why a document is kept and decides nothing about when it may go. Adding a value is additive; removing one needs a data migration, because the value is stored on the document. **Discarded:** a free-text reason, which cannot be enumerated by a retention report.

### D8 — The scan is a PostgreSQL sweep over leased, epoch-carrying compare-and-sets; the scanner is a port

**The row is the obligation and the sweep is the only driver.** A scan is claimed by `ScanDueDocuments` (a tick of `documents_maintenance`, 60 s) over `state = 'received' AND promoted_at IS NOT NULL AND next_scan_at <= NOW()` with both counters under their caps; `ScanDocumentMessage` only wakes a pass early, so a lost, duplicated or late message changes nothing, and Messenger's retry is never a scan driver. Every transition is **one SQL compare-and-set** (`DbalDocumentScanLeases`) judged by the database clock: it names the state it expects, carries the monotonic `lease_epoch` (grown on every claim and operator reopen, never reset) and, for a verdict or a heartbeat, `NOW() < claimed_at + deadline`. `Erased` matches none of them. A lost compare-and-set is an answer, not an error, and writes no custody row. The custody row a transition owes is appended in the same transaction through `AppendCustody` (the statement already holds the row lock), so the pair commits together (*accepted 2026-11-12: one transaction, not one statement*). **Discarded:** one statement that also inserts the custody row through a CTE — it would bypass `AppendCustody`'s sequence computation and the custody gate's single writer.

**The scanner is probed before anything is claimed.** A down scanner leaves `Received` untouched: no claim, no epoch, no attempt, no custody row, so an outage never moves a document toward `ScanFailed`. `ClamdScanner` speaks `INSTREAM` over TCP; the decrypted plaintext is pushed by `unseal()` into a write-only stream whose every write is one clamd frame, so it goes to the socket and to no file. The wait for the verdict is a poll with a read timeout under the heartbeat, and the heartbeat renews the lease every 30 s without ever extending the deadline. `scan_streaming_started_at` is set by compare-and-set immediately before the first byte reaches the scanner and cleared on every return.

**How each ending is accounted** (constants in `ScanPolicy`, fixed by the scanner spike, `docs/deployment-guide.md` → "Document scanner"):

| Ending | Result |
|---|---|
| `OK` / `FOUND` | `Ready` / `Quarantined`, one custody row |
| a limit answer (`Heuristics.Limits.Exceeded*`, `INSTREAM size limit exceeded`), a failed authentication or missing final chunk, a missing final object | `ScanFailed` + alarm + custody row, no retry. A limit answer is never `Ready`, and `AlertExceedsMax yes` is what makes clamd say so |
| connect failed, or any return with streaming not started | `Received`, `scan_outage_returns` + 1 |
| reset, timeout, transient local read error, worker death (lease lapsed), deadline, with streaming started | `Received`, `scan_attempts` + 1 — or `scan_outage_returns` + 1 when the run's single probe finds the scanner down |
| a counter reaching its cap (attempts 3, outage returns 10) | `ScanFailed` in the same statement as the return, with its custody row |
| `DekDestroyed` mid-scan, a superseded epoch, `Erased` seen by a heartbeat, a verdict refused by the deadline | the pass counts nothing and leaves the claim live. If the lease lapses on a row that is not `Erased`, the expiry sweep returns it under the accounting of a worker that died (an outage return before streaming, an attempt after), so a document that keeps ending this way reaches `ScanFailed` with its alarm; a row that is `Erased` by then matches no predicate and nothing is counted |

The backoff is `next_scan_at = NOW() + ladder × (1 ± 20 %)` computed in the same `UPDATE`: counted returns use the first two entries of 1, 5, 15, 60 minutes, outage returns walk all four and then stay at 60. The tenth outage return ends the document, so only nine wait: 60 + 300 + 900 + 6 × 3600 = 22,860 s, about 6.35 hours (7.6 at the +20 % maximum). The cap sweep ends a `Received` row found at or above a cap (a constant lowered at a deploy). A return and a re-claim write no custody row; the first claim since the last operator decision (`first_claim_recorded`), every verdict and every operator decision do.

**The operator reopens a `ScanFailed` document** through `POST /api/v1/documents/{id}/rescan` (`document.rescan`, carried by the ADMIN wildcard alone) with a reason from a closed enum: both counters to zero, epoch + 1, due now, `first_claim_recorded` false, a `RescanRequested` custody row whose actor is the operator and whose `reason` column holds the reason. `Ready` is never rescanned and there is no console command. The reason is validated at the edge, stored in the row's nullable `reason` column (set for that one event, NULL for every other, enforced by the `DocumentCustody` constructor beside the actor pairing: a scan fact has a NULL actor, a re-scan a non-NULL one) and also logged on the observability channel. It is not a person reference, so it has no registry line and the anonymisation, which rewrites `actor_id` only, never touches it.

**Readability is one guard on the aggregate**, `Document::assertReadable()`, throwing `DocumentNotReadable` (409 `document-not-readable`) in every state but `Ready`; a consumer mints no refusal of its own.

**Alarms** (`ReportDocumentScansHandler`, hourly, ids and counts only): a document in `Received`/`Scanning` older than 10 hours (above the outage ladder plus jitter); a `Quarantined`/`ScanFailed` one older than 24 hours; outage returns at 5 or more; a `ScanFailed` no cap ended. Age is measured from the last custody-bearing event, which a return does not touch.

**Owner sign-off, 2026-11-12.** Accepted as built: the abort path does not release the claim (the pathological case of a destroyed key on a row that never becomes `Erased` ends in `ScanFailed` with an alarm rather than looping); the custody row shares the compare-and-set's transaction rather than its statement; the `scanner` compose profile is declared only in `compose.dev.yaml` (the prod stack always starts the scanner), with `ComposeStackCommands` refusing `profiles:` only on a service that runs a `command`.

**Residuals** (plaintext in memory and on the internal network, the host's `core_pattern`, the signature refresh's egress, the reload pause) are in `PRODUCTION_SECURITY_CHECKLIST.md` §7.

### D9 — The read is two verified passes behind one switch, and the use case is the crypto read boundary

`GET /api/v1/documents/{id}/content` (`ReadDocumentController`, `ReadDocument`) serves the original of a `Ready` document. Check order after the firewall and the voter: `Uuid::ensure()` → the erasure ledger's override set answers `gone` whatever the switch says (a port the read only asks; an adapter that is never set is bound until the ledger owns the flag) → `documents.read_enabled` false answers 404 → no row 404 → `Erased` `gone` with no alarm → `assertReadable()` (the only readability refusal, no type of its own) → serve.

- **Two passes.** The answer must precede the first byte, and the original may be 100 MiB. Pass 1 unseals into a digest that discards the bytes and compares sha256 and size with the row; pass 2 unseals again into the response and re-hashes. Only pass 1 can refuse with a status; pass 2 can only abort, and it withholds the last byte until the whole stream matched, so a swapped object ends one byte short of `Content-Length` (a broken transfer) instead of a complete body of foreign bytes. A buffered or tmpfs variant was discarded: it breaks size-independent memory and the rule that plaintext persists nowhere. Cost: a second decrypt and a second read of the object per download.
- **Translation lives in `ReadDocument`, not in the exceptions (#418).** After the failure the row is re-read: `Erased` answers `gone` with no alarm (an erasure can commit between the snapshot and the open); any other state raises one `error` on the `observability` channel (`documentId`, `reason` slug) and `DekDestroyed` answers `gone` while a missing object, a failed authentication and a digest or size mismatch answer the marker-less 5xx `document-integrity-failure`, which reaches the error tracker. `StreamTransferFailed` and a storage fault before the first byte stay untranslated. `DekDestroyed` and `DecryptionFailed` gain no marker because `PiiDiffSealer` shares them on the write path.
- **Authorization: ADMIN only, through `document.download` (decided by the owner, 2026-11-16).** The verb is no tier's, so no tier grants it and the tiers and `TIER_OPT_OUT` are untouched; the ADMIN wildcard reaches it and a declared `EXPLICIT_GRANTS` row records the grantee. There is no per-document ACL. The first non-ADMIN consumer, or a rule that an uploader may download what they filed, reopens it.
- **Audit: one `security`-level row, `DOCUMENT_READ`, written after pass 1 and before pass 2 (decided by the owner, 2026-11-16).** Fail closed: a failed write is a 5xx with no byte served. The row records that access was granted, not that the transfer completed, and carries no metadata and never the filename; a refused read writes none. The use case opens no transaction, because `RequestTransactionBoundaryListener` rolls back a leaked one and would take the row with it. The route sets `_audit_canonical` so the generic `ROUTE_*` row yields, and its name does not start with `shared_`.
- **The response** is a fixed `application/octet-stream` (the row has no media type), `nosniff`, a sandboxing CSP, `Cross-Origin-Resource-Policy: same-origin`, `no-store`, and `Content-Disposition: attachment` with no `filename`: the sealed name never leaves in a header, so the client names the file from the listing and sanitises it. No `ETag`, no `Last-Modified`, `Range` ignored. The transfer re-arms PHP's wall-clock time limit (`UploadTimeBudget`) before the stream and at every chunk, a 60 s STALL budget measured through Caddy/FrankenPHP: without it a client slower than about 3.5 MB/s was cut at 30 s by a fatal no alarm sees.
- **The switch** `documents.read_enabled` is closed in production until `docs/runbooks/documents-restore-proof.md` holds a valid `restore` record and a valid `drill` record (with `ledger_replay_verified`) for the declared backup mechanism, read by `DocumentsReadProofGateTest`. Open: a value injected by the deploy is outside that gate.

### D10 — The listing and the trail open names in batches, degrade per document and alarm from a schedule

`GET /api/v1/documents` (a keyset page, `createdAt` descending with the id tie-break, one `state` equality filter, the engine's cap of 100) and `GET /api/v1/documents/{id}/custody` (one document's metadata and custody trail) are ADMIN only through `document.custody`, a non-tier verb decided as `document.download` was (the owner, 2026-11-17): a `PermissionCatalog` entry and an `EXPLICIT_GRANTS` row, no tier touched. Neither serves bytes, so `documents.read_enabled` does not gate them; the erasure-ledger override answers 410 on both for any well-formed id and before any lookup (a malformed trail id is a 400 first), because after a restore without the ledger an erased document's key is back and its name would open. Neither sets `_audit_canonical`: the generic access-log row is their audit record (the trail's names the document through `_audit_resource_type`), and a `DOCUMENT_READ`-class row exists for byte reads only (`PRODUCTION_SECURITY_CHECKLIST.md` §7).

- **Names cost one keystore query per page.** `Keystore::wrappedDeksFor()` returns the usable keys of many scopes from one `WHERE … IN`, a corrupt live row degrading its own entry, and `EnvelopeEncryptor::decryptMany()` returns per value the plaintext or the crypto exception `decrypt()` would have thrown, never throwing for a value. `DocumentNameOpener` is the one place that knows how a name opens (scope from the row, associated data from `CommitUpload::filenameAssociatedData()`), skips an `Erased` or ciphertext-less row without a lookup, and turns `dek-destroyed` / `decryption-failed` / anything else into a `null` name with a cause. A keystore outage still fails the page. **Discarded:** `decrypt()` per document (N queries), and a marker on the shared exceptions (the write path needs their 500).
- **The alarm is a schedule, not a request line.** A page of broken names would write one `error` line per name per request into the buffered default channel, and a document nobody lists would never alarm. `ReportDocumentNamesHandler` (daily, beside the storage report) opens the names of non-`Erased` documents through the same opener, in id-ordered batches of 100 under a 60 s budget, and writes ONE `observability` line per run with the count per cause (`key-missing`, `decryption-failed`, `unreadable`), the number examined, whether it finished and the first 20 ids in ascending order: an `error` when a name failed, a `warning` with zero counts when none did but the run ran out of budget, nothing otherwise. **Discarded:** logging in the opener (the request path would alarm), and a per-name metric surface.
- **The trail is paged by a plain cursor, not the keyset engine.** The order is fixed and `(document_id, seq)` is unique and indexed, so `afterSeq` (integer ≥ 0, absent = start) and `limit` (default 25, max 100) read `WHERE document_id = :id AND seq > :afterSeq ORDER BY seq LIMIT :limit + 1`, and `nextAfterSeq` says whether a row beyond the page exists. The trail is unbounded (every manual re-scan appends a row), so a tail is never hidden behind a `truncated` flag; capping re-scans was discarded as a business policy on a different use case that would not bound a future event source. The metadata and the name ride the first page only, so walking a trail opens one name; an unknown document is 404 on every page. A row appended between two requests appears on a later page; no snapshot is promised. The `actorId` of an erased person is the nil UUID as stored: a marker, never a user.

### D11 — Erasure is one transaction behind a ledger entry the database cannot lose

`POST /api/v1/documents/{id}/erase` (`document.erase`, ADMIN wildcard only, no tier and no `EXPLICIT_GRANTS` row — as `document.rescan`) takes every non-terminal state, with a reason from `ErasureReason` (`data_subject_request`, `legal_obligation`, `uploaded_in_error`, `retention_expired`) and the caller's `currentPassword`. **The route re-proves it** — the shared `CurrentPasswordProofThrottle` budget, then `ProveActorPassword`, before the use case and so before any ledger write — and is classified `credential-affecting` (the gate's pinned set of fixed routes is eight, with the series erasure of D12): the act cannot be undone even from a backup, the listing enumerates what it can reach, and evicting a stolen session undoes nothing. `backoffice_user_erase`, which erases an identity with no proof, is the same gap and is not fixed here (`PRODUCTION_SECURITY_CHECKLIST.md` §7). The system's two reasons are a separate type, `ErasureSystemReason` (`ledger-replay`, `ledger-completion`), which the HTTP enum cannot hold (a test asserts the sets are disjoint) and `DocumentCustody` pairs with its actor: an `Erased` row is an operator and an `ErasureReason`, or NULL and an `ErasureSystemReason`, never anything else. A repeat answers as the first call did and writes no ledger entry, no custody row and no second tombstone.

**Order.** voter → `Uuid::ensure` → load (404) → `Erased`? answer → **ledger write** (off host, no transaction, no lock, 10 s) → one transaction: `SET LOCAL lock_timeout 5 s / statement_timeout 10 s`, the intents of the scope, the document row, the keystore row, the `Erased` compare-and-set, `AppendCustody`, `Keystore::destroy(scope, Erasure)`. The compare-and-set (`DbalDocumentErasures`, its own class beside `DbalDocumentScanLeases`) is `UPDATE … SET state = 'erased', filename_ciphertext = NULL WHERE id = … AND state IN (non-terminal)` and `=== 1` is the only verdict; it names no scan, lease or slot column, so a scan worker's later verdict, which names the state it expects, matches nothing, and erasure never waits on, steals or counts a scan. `destroy()`'s boolean decides nothing, and an `Absent` scope is tombstoned too (the early return of `EraseBankAccountSubject` is not copied): `lockState()` on an absent scope locks nothing, so the tombstone's safety against a concurrent `store()` rests on `destroy()`'s atomic first-writer-wins upsert. `AppendCustody` re-takes the document lock inside the outer transaction through a nested unit; a failure rolls the compare-and-set and the tombstone back together.

**Lock order: intent, document, keystore.** The commit and the reaper take intent then keystore (no document row exists yet in the commit), so sharing the intent lock first serialises every path that could meet the keystore row, and the scan's compare-and-set takes only the document row: no cycle. `UploadIntentRepository::lockByScope()` takes it without loading the entity; `EraseDocumentFunctionalTest` asks the database from a second connection which rows are held at each step.

**The ledger** is the `ErasureLedger` port (Application) over a restic repository behind `rest-server --append-only` on a second host (`ResticErasureLedger`, Infrastructure). Entries are at-least-once, deduplicated by scope id (the earliest wins). A failure before the entry is durable is `erasure-ledger-unavailable` (503) and the document is untouched; a timeout, and equally **any failure of the erasure transaction once the entry is durable** (a lock or statement timeout, a keystore or database fault), is `erasure-outcome-unknown` (503), which says the erasure may still complete — the entry is durable, so the completion sweep finishes it; the log carries a cause slug (`lock-timeout`, `statement-timeout`, …) and never a message, URL or stderr, and the adapter logs its own slug per failure (`not-configured`, `timeout`, `binary-missing`, `forbidden`, `exit-<n>`). An unreachable host is `erasure-outcome-unknown`, not `erasure-ledger-unavailable`: restic retries a refused connection with backoff, so the 10 s deadline fires first. `restic` runs in array form through `Process`, with the repository address, the REST credentials and the repository password in `RESTIC_*` environment variables (never the URL or argv), `--no-cache`, and no output or cause in any exception. **Spike (restic 0.18.1 against a local rest-server, `docs/runbooks/documents-erasure-ledger.md`):** `restic forget` is refused 403 per snapshot but exits 0; a stock server has no read-only credential (the fallback is the same credential, which changes no residual); `check --read-data` exits 1 on a corrupt snapshot file while `snapshots` skips it, prints `Ignoring "<id>"` and exits 0 — so "read in full" is `check --read-data` exit 0 **and** a listing with no `Ignoring` line. **restic ships in the php image** (the erase request, the completion sweep and the restore command all run PHP; a sidecar would need its own exec or HTTP surface for no gain), pinned by the digest of the upstream image in `api/Dockerfile`. **Discarded:** a sidecar.

**Completion and replay are one service, held to two callers, and the transaction behind them to two.** `ReplayErasure` skips the ledger write, records NULL and the system reason, tombstones a ledger scope no row holds and — for a restore replay only — deletes an object under it and reopens the sealed-object marker of an already erased row (objects can come back from a backup the marker never saw). It is never a parameter of `EraseDocument`; `ReplayErasureCallersGateTest` (`make php.lint.replay-erasure`) holds the classes whose constructors take it to exactly `ReplayErasureLedgerCommand` and `CompleteInterruptedErasuresHandler`, and the holders of `ApplyErasure` — whose public `apply()` also erases with no ledger write and no voter — to exactly `EraseDocument` and `ReplayErasure`; its universe is asserted against the real file count. The completion sweep (5 min) lists the ledger, ignores an entry younger than `ErasureLimits::COMPLETION_MIN_AGE_SECONDS`, derived as the write timeout (10 s) + the transaction's own bound (3 locks × 5 s `lock_timeout` + 10 statements × 10 s `statement_timeout` = 115 s) + a 60 s margin = 185 s, judged from the snapshot timestamp, which restic stamps on the writing host (this application's), so the margin covers clock drift between the write and the sweep and a worker that is slow rather than dead, not skew between two machines, replays the rest with `ledger-completion`, and writes one `error` line when it cannot read the ledger.

**A restore replay visits every scope of the ledger, not only the unfinished ones**, and reopens the sealed-object marker of an already erased row inside the same transaction as the erasure, so the sweep deletes the objects a backup brought back. The same statement stamps `erasure_reopened_at`, and both erasure alarms (objects and derivatives) measure their bound from the later of that stamp and the `Erased` custody row, so a restore does not make every erased row it reopened overdue at once (decided by the owner, 2026-11-19).

**The sealed object** is deleted by `DeleteErasedObjects` (60 s), the single owner: staged path first, then final, a missing one tolerated on each, the row done only when neither exists, recorded in the nullable `document.object_deleted_at` (read-only mapped like `promoted_at`, a partial index over the pending rows). A failed delete never rolls the erasure back; an object still there an hour after the `Erased` custody row raises an `error`. Staged first because a writer's post-commit rename can race the erasure and recreate the final object: once the staged name is gone a promotion that has not happened cannot, and one that did leaves a final object the same run deletes. **The tombstone reconciler** (`ReportTombstonedDocumentsHandler`, hourly) is driven by Document rows, since the shared reconciler skips `Document` scopes by design: a row that is not `Erased` whose scope is tombstoned is an `error`, whatever the ledger says.

**`restore.prod`** stops `php`, `messenger_worker` and `scheduler_worker`, runs `pg_restore`, then `documents:erasure:replay-ledger` in a one-off container; it restarts the writers only on a successful replay (recovery mode otherwise) or an override. **The override** is a row of `erasure_ledger_override` (id, set_at, cleared_at, closed reason, a random `record_ref`) that replaces `NeverSetErasureLedgerOverride` behind the same `ErasureLedgerOverride` alias, so the three read routes answer 410 with no controller change. **It holds no name, label, host user or key fingerprint**: any of those is personal data about an operator in a table no erasure path owns, and a label typed on a restored host proves nothing about who typed it. "Who" lives in the off-host operator log (`docs/vps-deployment.md` gate 3), cross-referenced by the printed `record_ref`. **No reason clears by itself** (renegotiated by the user, 2026-11-17, after review found that for a new empty repository the preconditions hold vacuously and would reopen reads over keys nobody replayed): they are necessary and never sufficient. `documents:erasure:clear-override` (no person or scope on argv) snapshots the uncleared ids FIRST, then checks that the ledger is readable in full, that every scope of it is finished and that no row of it is left un-erased, and clears exactly the ids it saw (`WHERE id IN (…)`, never an unbounded `UPDATE`, so an override set while it works is not cleared unchecked), printing their `record_ref`; it replays nothing itself. While any override stands, the completion tick writes one `error` line (count and age of the oldest, nothing else), so a standing 410 is never silent. **Discarded:** a typed `operator_label`, the OS user plus SSH fingerprint, an authenticated HTTP identity (php is stopped in recovery mode).

**Scale.** Every restic call runs `--no-cache` and the completion tick lists the whole ledger under a 60 s limit. Measured locally against an append-only rest-server (loopback, no latency): `record()` 0.6 s to 0.7 s and `entries()` 0.55 s to 0.8 s from one entry to ~5,000. Over a real link the listing grows with the round-trip time per entry, so the accepted growth limit is about 2,000 entries until the second host is measured; it is recorded in `PRODUCTION_SECURITY_CHECKLIST.md` §7.

**Residuals** (digest, size and timestamps surviving erasure; ciphertext in offsite backups; the erasure depending on the offsite channel; the write credential able to append an entry for a live scope; the ledger being a single copy; a deleted entry leaving no trace; a leaked repository password not rotatable) are in `PRODUCTION_SECURITY_CHECKLIST.md` §7. The real restore drill is the owner's: this decision ships the code, the tests against a stub `restic` and the runbook, never the `drill` proof record.

### D12 — A series row is the mutex of the two transitions that take a version slot; the slot itself is derived, never stored

Each version is its own `Document` (D1) and the accepted chain is linear: a new version needs a `Ready` predecessor, and a version that ended `Quarantined`, `ScanFailed` or `Erased` gives its slot back, so a corrected version is filed as a sibling. **A predecessor's slot is held while any version below it is live** — `Received`, `Scanning` or `Ready`, at any depth. That one definition carries every property the specification asks for: an `Erased` middle node with a live descendant still blocks a sibling (the descendant holds the slot); when the last live descendant under a contiguous run of `Erased` nodes is erased or quarantined the whole run stops holding it, because nothing below it is live any more — derived by the read, never written; and erasing a node that has a live descendant opens no fork.

`document_series` (`id`, `created_at`, `closed_at`) holds one row per series and **no head pointer and no count**: the only thing a transition reads from it is the one-way `closed_at` stamp a series erasure writes. `document.series_id` references it (`fk_document_series`) and `document.predecessor_id` references `document.id` (`fk_document_predecessor`, whose index the slot read walks); neither cascades. The row is inserted with a first version, in the repository's insert, and the migration backfills one per existing series. **Only the two transitions that take a slot lock it**, under `SELECT … FOR UPDATE` (`DbalDocumentVersionSlots`), and both go through one service, `TakeVersionSlot`:

- **Filing a new version** (`CommitUpload`): intent row → keystore row of the new scope → series row → predecessor row (`FOR UPDATE`, rechecked `Ready`) → the recursive read → insert, `series_id` copied from the locked predecessor. The intent → keystore → series stretch is safe for the reason D6 states for the commit: the new scope is reachable only through the intent this transaction holds, so nothing else can be waiting on that keystore row while holding the series.
- **Reopening a `ScanFailed` successor** (`RescanDocument`): series row → predecessor row (refused when `Erased`) → the recursive read → its own row through the D8 compare-and-set. It loads itself unlocked first only to learn its series and predecessor, which never change. A first version has no slot, but its reopen still takes the series row, only to refuse a closed series.

The recursive read is lock-free: `WITH RECURSIVE` down `predecessor_id` (`UNION`, so even a corrupt link could not loop), answering whether a live row exists. **Why that is safe without locking what it reads:** a version becomes live only by being inserted or reopened, and both happen under the series lock; outside it versions only *stop* being live (a verdict, a return capped to `ScanFailed`, the cap sweep, an erasure, a replayed erasure). So the read can see a slot held that a concurrent free is releasing: that answer is `document-version-slot-taken`, a **retryable conflict by contract** — the caller declares again — and never a double successor. It is the price of keeping every freeing transition off the series lock, not a residual. `VersionSlotPairsFunctionalTest` interleaves new version / new version (one winner), new version / erasure, new version / reopen and reopen / reopen with a real second connection.

**Consequences.** The erasure (D11), the scan's compare-and-sets (D8), the cap sweep and `ReplayErasure` take no series lock and are unchanged, so `ErasureLimits::TRANSACTION_LOCKS` stays 3 and the completion sweep's margin is untouched. Deadlock freedom does not rest on id order: only a take locks more than one document, takes are serialised per series by its row, and two series share no document. The person purge locks a subject's documents in ascending id; a reopen takes its predecessor before itself, and a successor's UUID v7 is minted after its predecessor became `Ready`, so the two orders agree — and a `deadlock_detected` would still map to a retry. A refused commit rolls back and the writer's abort expires its intent, so the loser's sealed bytes and key fall into the aborted-upload class (D6).

**Authorisation is RBAC**: the new-version declare (`POST /api/v1/documents/{id}/versions`) asks `document.write` **and** `document.download` (decided by the owner, 2026-11-19: replacing a document is filing evidence about one the caller may read, so today it is the ADMIN wildcard, as for the read route), with no row-level voter (`authorization-model-boundaries.md`), and an absent predecessor answers `document-predecessor-not-ready` like a non-`Ready` one, so the route is no existence oracle. The series page (`GET /api/v1/documents/series/{seriesId}`, `document.custody`) orders by `(created_at, id)` — `created_at` keeps whole seconds and the id is a UUID v7 — and the statement itself replaces the uploader of an `Erased` version with NULL: a tombstone keeps its id, digest, size, retention fields, key hash, links, state and timestamps, and names no person to a reader, while `uploader_id` stays on the row under the person purge's ownership. A live version's uploader id is returned to that ADMIN reader exactly as the listing returns it (D10), with the same generic access-log row as its only audit record. **A series erasure** (`POST /api/v1/documents/series/{seriesId}/erase`, `credential-affecting` like D11's) is `EraseDocument::eraseSeries()`. It first **closes the series** in its own short transaction — the series row under `FOR UPDATE`, then `closed_at` — and every take — and the reopen of a failed first version — refuses a closed series (`document-series-closed`, at the declare and under the lock). A take already holding the row commits first and its version is then listed; after the close commits nothing in the series can become live, so the run **terminates**. It then erases every non-`Erased` version newest first, each through the single erasure — its own ledger entry, its own transaction — and reports what remains, which is empty whenever the run completes; a failure stops it where it stands, leaves the series closed, and a repeat continues. The close is the series erasure's only touch of the series row and sits outside every erasure transaction, so `TRANSACTION_LOCKS` is unchanged. Closing is irreversible on purpose: a series being erased is never extended again. A person's erasure still touches no document.

**Discarded.** A **stored head pointer** moved by one `UPDATE` under the series lock (the first design): every *freeing* transition — erasure, verdict, cap sweep, replay — would have to take the series lock to move it, `TRANSACTION_LOCKS` would go from 3 to 4 and the completion sweep's derived margin with it, and one transition that forgot to move the head would block its series for ever. A **`holds_slot` flag** with a partial unique index on `predecessor_id`: correct, but kept consistent by a locked walk-up over the `Erased` ancestors on every transition that frees, the same reach into freeing transitions. **`UNIQUE (series_id, version_no)` alone**: two concurrent successors of one predecessor compute different numbers and both pass. A **transaction-scoped advisory lock** on a hash of the series id: no row to reference, unrelated series collide on a hash, and it sits outside the row-lock order this ADR states. **Event sourcing** of the series: rejected in D1 on measurement.

**Reopened by** a consumer that needs time travel or derived state over versions — an approval workflow that must ask "which version was current on date X", or a state computed across a series — which a mutex row and a lock-free read do not give.
