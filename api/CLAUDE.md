# api/CLAUDE.md — ERPify API (Symfony + FrankenPHP)

API-scoped guidance. Root [`../CLAUDE.md`](../CLAUDE.md) is authoritative for monorepo conventions, the Docker stack, and the full `make` target list — this file only covers API specifics. Also consult `../docs/rules/*.md` (especially `architecture`, `php-standards`, `database`, `security`, `clean-code`, `testing`).

## Stack

-   **Symfony** on **FrankenPHP** (worker mode; Caddy embedded). No separate edge proxy — FrankenPHP terminates TLS and reverse-proxies HTML to the `pwa` container on `:3000` while serving `/api/*` in Symfony on the same origin.
-   **PHP 8.5** (base image `dunglas/frankenphp:1-php8.5`, sha256-pinned).
-   **Doctrine ORM** + **PostgreSQL**. Migrations in `migrations/`, fixtures via **Hautelook Alice**.
-   **Symfony Messenger** with a dedicated `messenger_worker` service (async email + audit table).
-   **Mercure** hub (built into FrankenPHP) for real-time.
-   **PHPUnit** + **Behat** for tests. (Behat preferred)
-   Repo root `symfony-docker` scaffold is the upstream — when syncing, merge into the **root** Compose files, not into `api/`.

## Folder structure

-   `src/Kernel.php` — Symfony kernel.
-   `src/<BoundedContext>/<Module>/{Domain,Application,Infrastructure}/` — DDD + Hexagonal. Current top-level contexts:
    -   `Backoffice/` — internal modules (e.g. `Bank/`, `Health/`), each with its own `Domain`/`Application`/`Infrastructure`.
    -   `Frontoffice/` — client-facing modules.
    -   `Iam/` — identity & access. `Identity/` holds the user aggregate, login, and the RBAC core (`Permission`, `AuthorizationPolicy`, `PermissionVoter`); `Invitation/` owns the onboarding token and its lifecycle CLI; `Session/` owns the server-side session registry, its fail-closed admission gate and its retention sweep.
    -   `Organization/` — tenancy context. `Organization` + `Membership(userId, organizationId, roles)` aggregates: the authoritative user↔org link, org-scoped roles, one organization per installation. Bootstrapped by CLI (`organization:provision`, `organization:administrator:create`); no credentials in migrations.
    -   `Shared/` — vertical-slice capability modules over a minimal `Kernel/` (DDD building blocks). Capabilities each carry only the layers they need: `ErrorContract/` (RFC 9457 pipeline), `Uuid/`, `Http/`, `Serialization/`, `Persistence/`, `Clock/`, `Event/`, `Mailer/`, `Monitoring/`, `Search/`, `Validation/`, plus `Audit/`, `Access/`, `Token/`, `Crypto/`, `Privacy/`. No global `Domain`/`Application`/`Infrastructure` buckets — see [`../docs/adr/shared-module-organization.md`](../docs/adr/shared-module-organization.md). Put truly reusable code here; don't scatter it across modules.
-   `config/` — Symfony config (services, routes, packages, Messenger transports).
-   `migrations/` — Doctrine migrations (never edit applied migrations; generate new ones via `make db.diff`).
-   `tests/` — `Unit/`, `Functional/`, `Behat/`, `DataFixtures/`.
-   `tools/` — per-tool configuration, plus the one remaining isolated Composer install (PHPUnit). Behat is **not** here: its bridge was retired when `behat/behat` 4 lifted the `symfony/console` cap, and it now lives in `api/composer.json` like every other dev tool (see "Rules that bite" below).
-   `features/` — Behat `.feature` files.
-   `frankenphp/` — Caddyfile + worker entry.
-   `docs/` — upstream symfony-docker docs (options, TLS, Xdebug, Alpine, MySQL, troubleshooting); plus local-specific `domain-events-and-messenger/`, `production-ready/`, `ide-config/`.

## Layer rules (load-bearing)

Dependencies point inward toward `Domain/`. **No** Symfony/Doctrine/HTTP/Messenger imports inside `Domain/` — put adapters in `Infrastructure/` and orchestration in `Application/`. Domain entities and value objects are pure PHP + interfaces. Documented exceptions: entities may carry passive **persistence/validation** metadata (`#[ORM]`, `#[Assert]`) — serializer `#[Groups]` are **not** carried on entities; the HTTP wire contract is owned by per-view Resource DTOs (`Application/Resource/`) mapped in `Infrastructure/Http/` (see [`../docs/adr/api-resource-dtos.md`](../docs/adr/api-resource-dtos.md)) — and `Domain/` may import `symfony/uid` as a UUID value-object library (`Shared/Uuid/Domain/`) — see [`../docs/rules/architecture.md`](../docs/rules/architecture.md).

-   `Domain/` — entities, value objects, domain events, repository **interfaces**, domain services.
-   `Application/` — use cases / command + query handlers, DTOs, transaction boundaries. Orchestrates domain; consumes repository interfaces.
-   `Infrastructure/` — Doctrine repositories, HTTP controllers / API Platform resources, Messenger handlers, mailers, external clients, persistence mappings.

New bounded contexts/modules follow the same three-layer split. Cross-context calls go through `Application/` ports, not direct class references across `Domain/` boundaries.

**Question the status quo** (root [`../CLAUDE.md`](../CLAUDE.md) → "Question the status quo — argued improvement"): on every API change, distrust the existing design *of the code you touch* and look for the real improvement toward SOLID/DDD/hexagonal — leaky aggregate boundaries (object graph crossing a module), an anaemic handler mixing I/O and policy, a `Domain/` that reaches a framework, a missed read-side projection. Propose with principle + objective (maintainability / performance / scalability) + cost; let the user decide scope. Justified flexibility (the passive-metadata / `symfony/uid` exceptions) is the model, not an excuse for dogma or for unilateral refactors.

## Rules that bite

-   **Never** put Symfony services, HTTP concerns, or Messenger handlers inside `Domain/` — behavioral framework code stays out (the passive-metadata `#[ORM\…]` and `symfony/uid` value-object exceptions are covered in "Layer rules" above and [`../docs/rules/architecture.md`](../docs/rules/architecture.md)).
-   **Never** hand-edit a migration that has already been applied. Generate a new one with `make db.diff`.
-   **Don't skip** `make php.quality` locally — CI runs it and the fixers (`cs-fixer`, `rector`) mutate files, so running them first keeps diffs clean.
-   **PHPStan (`level: max`) is the sole static-analysis gate.** Psalm is gone: its general analysis was retired first (a redundant second type-checker that disagreed with PHPStan, plus a ~492-issue baseline and `--alter` auto-fix that were pure friction), and the taint-only remnant followed once it had gone 164 merged PRs without a single finding while its `sebastian/diff: ^8` ceiling held the app's PHPUnit back. **Never** reintroduce `vimeo/psalm` or a `psalm/*` plugin into `api/composer.json`. Security dataflow is now carried by a narrow, repo-owned Semgrep ruleset (`make semgrep.scan`, rules in [`../tools/semgrep/rules/erpify-rules.yaml`](../tools/semgrep/rules/erpify-rules.yaml)) plus review against the checklist in the root [`../CLAUDE.md`](../CLAUDE.md) — the ruleset covers three `Request`-sourced flows, not general taint, so review stays the primary control. Vendor rulesets were measured and rejected: they model only superglobals as sources and `src/` uses none, so both the community and Pro PHP rules report nothing here.
-   **A development tool may not constrain the app's Composer tree** unless it is needed to run the application or its test suite. A tool that drags the app's dependencies backwards gets isolated into its own tree under `tools/` or removed outright — psalm was removed once it did this. There is no automated gate: the symptom is silent (`composer update` simply declines to move a package), so diagnose it with `composer why-not <package> <version>`. Isolation is a last resort, and it is never free — a second vendor tree that has to be reconciled at runtime is a standing hazard, because Composer resolves a shared FQCN from the autoloader registered **last**. Behat needed that treatment for as long as `behat/behat` capped `symfony/console` and its siblings at `^7.0`; `behat/behat` 4 lifted the cap, so Behat now lives in `api/composer.json` like every other dev tool and the two-tree bridge is gone.
-   **Two Flex recipes are recorded in `symfony.lock` with files deliberately declined**, so `composer recipes` reports permanent drift for them. That is the intended state — **never** reconcile it with `recipes:install --force`, which would restore all four:
    -   `friends-of-behat/symfony-extension` — `behat.yml.dist` is Behat 3 YAML config, superseded by `behat.dist.php`; `features/demo.feature` and `tests/Behat/DemoContext.php` are scaffolding that would join the real suite. Only its `config/services_test.yaml` is kept.
    -   `symfony/translation` — `translations/` has nothing to hold while the translator is off (`config/packages/translation.yaml`).
-   **The acceptance suite runs on a prerelease: `behat/behat: ^4.0@alpha` (`require-dev`).** The constraint is what lifted the `^7.0` cap on `symfony/console` and its siblings; nothing else in the tree admits an alpha into the app's own dependencies. Be aware `@alpha` is a *floor on stability, not a ceiling on version*: it keeps admitting `4.x` prereleases, so once `4.0.0` is tagged stable a later `composer update` would still prefer a newer `4.1.0-alpha1`. **Retirement trigger:** the first stable `4.0.x` tag — narrow the constraint to `^4.0` and drop its `stability-flags` entry. Until then a Behat minor can change the `Behat\Config\*` API that `behat.dist.php` is written against, so treat a Behat bump as a change to the suite, not a routine update.
-   **Neutralising and retiring an upstream dependency regression.** When a release breaks the app, the four steps below are what a past regression cost us when each was skipped (`doctrine/doctrine-bundle` 3.2.5 changed a PostgreSQL check from platform to driver, which any DBAL middleware defeats — Symfony wraps by default — killing `doctrine:database:create` and with it the whole Behat suite).
    -   **Check the version you escape to.** Jumping the constraint forward is not neutralising: the next minor may carry the same defect. Here `^3.3.0` looked like a fix and was equally broken, so what actually kept the suite alive was an in-repo workaround nobody had labelled as load-bearing. Whatever holds the line, say so where the next reader looks.
    -   **Report it, and record the issue URL in the constraint's vicinity.** A pin with no upstream link and no retirement trigger never gets retired.
    -   **On the fix, raise the constraint — not just the lock.** A lock-only bump leaves the broken version reachable by the next `composer update`.
    -   **Verify positively, and force the broken path.** A green run proves nothing if the triggering condition quietly vanished: assert the condition still holds (dump the driver chain and confirm the wrapper is *still* there), and destroy the state that lets the code skip the broken branch (drop the test database so `--if-not-exists` must actually create it). Isolate the probe in its own throwaway stack under `tmp/` — for this class, an ephemeral Postgres whose role name differs from every database name, so a missing `dbname` surfaces as a failure instead of silently connecting.
        -   **For a deprecation regression, "cold" means `cache:clear --env=test --no-warmup`.** `trigger_deprecation` for a deprecated *class* sits at **file scope** (`vendor/symfony/http-kernel/DependencyInjection/Extension.php:16`), so it fires once, when the file is first autoloaded — during container compilation. Plain `cache:clear` clears **and warms**, which compiles the container inside the console process where no `failOnDeprecation` is watching; PHPUnit then runs against a warm cache, never compiles, and reports green over a real deprecation. Measured: the same tree that exits 1 with `Deprecations: 1` after `--no-warmup` exits 0 without it. When the falsification run refuses to go red, suspect the probe before the premise.
-   **Nothing that ships may track a branch (`make php.lint.composer-stability`).** `minimum-stability: stable` is a declaration, not an enforcement: a per-package flag (`0.4.x-dev`, `dev-main`, `^4.0@alpha`) overrides it silently and Composer records the override in `composer.lock`'s `stability-flags`, where nobody looks. This repo shipped exactly that — `symfony/mercure-bundle: 0.4.x-dev` in `require`, so an untagged upstream commit reached production and `composer update` on it moved to whatever `main` HEAD was. The exception was argued and real (the tagged release tripped the deprecation gate), but nothing in the build could tell it apart from an accident, and it was watched by a bespoke weekly cron that died with the pin. The gate now refuses any branch constraint or `@`-stability flag in `require`; `require-dev` is exempt by design, and holds the only two today (`behat/behat` at `@alpha`, `roave/security-advisories` at `dev-latest`). A green proves no *root* requirement carries one — not that a stable dependency doesn't itself require a dev package, which this gate never reads.
-   **A persisted person id needs a named owner of its erasure (`make php.lint.person-reference`).** `Shared/Privacy` carries two attributes and they are not interchangeable: `#[PersonalData]` is a contract of **treatment** (infrastructure reads it to decide encrypt-vs-clear per column) and `#[PersonSubjectReference]` is a contract of **reference** — this property holds a person's id, and this file erases it. Marking a foreign key as personal data would file the id under the encryption scope of the aggregate owning the ROW, so it would die with that aggregate and survive the person's own erasure. Every `Types::GUID` entity column is classified in `api/.person-reference-policy`; `person` with no owner is not a valid spelling, because an unowned person reference is the violation itself. The gate derives the universe by reflection, so a new entity column joins it the moment it is declared — and it requires the attribute at the property of every `person ::` column **except the subject's own primary key**, which is not a reference but the row whose deletion is the erasure.

    The same target carries the **detective** half. Every `person ::` column must also have a `Shared\Privacy\Application\PersonReferenceSource` in its owning context — a read-only `DISTINCT` list of the person ids that column still holds, tagged `erpify.person_reference_source` and collected by `ReconcileErasedSubjectReferences`, which reports the ones that resolve to no live identity (`identity:gdpr:reconcile-subject-references`). The contract lives in the shared kernel so no import crosses a context, and each source declares the registry key it covers: the gate compares declarations against the registry **in both directions** and asserts the tag wiring, so a fifth context that comes to hold a person id cannot join the registry and skip the control. `audit_log.resource_id` is deliberately outside that collection — its table has no entity, so it can never be a registry key — and stays a collaborator of the reconciler in its own right.
-   **The trail's own proof of an erasure may not expire before the thing it attests (`make php.lint.audit-evidence`).** `Shared/Audit` admits a closed set of three mutations on `audit_log`, and the prune is the one that deletes. It exempts `AuditErasureEvidence::ACTIONS` for ever: a `GDPR_SUBJECT_ERASED` row answers for a `dek_keystore` tombstone `DbalKeystore::destroy()` keeps on purpose, and `SubjectErasureReconciler` anti-joins the two with **no date bound** — so an evidence row that ages out turns every correctly crypto-shredded subject into a permanent reported divergence, daily and for ever. The exemption keys on `action` and never on `level`, because `action` is what the detective control reads and discriminating by different columns is how the two would drift apart in silence. Centralising the two literals in one class made a **drifted** token impossible (a rename breaks compilation); it did nothing about a **missing member** — a third context minting its own `GDPR_ACCOUNT_ERASED` — and that omission fails toward deletion, which is why the closed set earned a registry. Every action an `AuditLogger` collaborator declares as a string constant is classified `evidence`/`ordinary` in [`.audit-evidence-actions`](.audit-evidence-actions); the gate refuses an unrecognised verdict and a duplicated token outright (anything not exactly `evidence` would read as ordinary, and ordinary means deletion), then checks completeness, staleness and agreement with `AuditErasureEvidence::ACTIONS` in both directions. Two classes, each selected by exact name in its own run, so a vanished one is an empty suite rather than a green subset. **What a green does not prove** is in the registry header, and the first line of it matters most: it never judges a classification, so `ordinary` over real evidence passes. It also sees only **constructor**-injected collaborators and only **string constants**, so a logger arriving by setter, an action inlined at the `log()` call site, or a backed enum — the shape this repo already uses for `AuditLevel`, `ActorType` and `Role` — is invisible to it.

    The prune's own statement carries a second invariant that no behavioural test reaches: `ORDER BY id LIMIT :batch FOR UPDATE`. The ordering alone buys nothing — `LIMIT` blocks sublink pull-up, so the outer `DELETE` unique-ifies the subquery through a blocking node that discards its order, and the probe runs in that node's order however the subplan sorted. `FOR UPDATE` puts `LockRows` above the ordered scan and below that node, so the whole lock set is acquired ascending by `id`, which is the order `DbalAuditActorAnonymiser` imposes on itself and `DbalAuditSubjectRowLock` imposes on `DbalAuditResourceAnonymiser` — a bare `UPDATE` that orders nothing of its own. Both clauses are pinned twice on purpose: `AuditPruneStatementGateTest` reads the source and refuses a second `DELETE FROM audit_log` anywhere in `src`, and `AuditPrunePlanFunctionalTest` `EXPLAIN`s the statement the class actually emits. Deleting `FOR UPDATE` reds those two and **nothing else** — measured. Its own cost is named at the statement: `FOR UPDATE` under `LIMIT` drops a re-checked row without a replacement, which is a short batch and an early end to the drain; that needs a concurrent writer of `level`/`occurred_on`/`action` or a concurrent deleter, and the advisory lock excludes only a second session running the pruner.

-   **A schedule is not scheduled until a worker consumes it (`make php.lint.schedule-consumption`).** `AddScheduleMessengerPass` creates `messenger.transport.scheduler_<name>` from the `#[AsSchedule]` attribute and `config/packages/messenger.yaml` declares no scheduler transport at all — so a schedule whose transport no `messenger:consume` command names compiles, registers, passes deptrac and every test, and never ticks. Adding a schedule means adding its transport to the command in **both** root compose files, and **to the right service in each** (`compose.yaml`'s dev `messenger_worker`, `compose.prod.yaml`'s single-replica `scheduler_worker`) — ticks come from an in-process clock, so a scheduler transport on the horizontally scalable pool emits one per replica. The gate checks both directions and the service pairing; the stale direction matters because a leftover argument for a deleted schedule stops the worker booting rather than degrading. It parses the compose files as **YAML**, not as bytes: a commented-out `messenger:consume` line used to read as live wiring, a command written as a plain string parsed as nothing at all, and a receiver written after an option was invisible (`ArgvInput` takes arguments and options in any order). It reads them — outside the `./api` build context — through the read-only `./` bind mount at `/app/repo` declared in `compose.dev.yaml`, and fails loudly if it is missing instead of quietly passing. The attribute sweep covers every spelling Symfony accepts, bare `#[AsSchedule]` (which becomes `scheduler_default`) included.

    **Naming the right service is half the invariant; the other half is that the service runs once.** The same gate therefore refuses a consumer declaring more than one replica in any of the **three** root compose files — `compose.dev.yaml` included, because `make/config.mk` layers it over `compose.yaml` for dev, so a count written there runs two clocks while a sweep limited to the consumption pair stays green — and refuses `compose.prod.yaml`, the overlay a deploy applies, declaring none, since an absent count reads as "nobody wrote the constraint down" rather than "the default is fine". An interpolated count (`replicas: ${SCHEDULER_REPLICAS:-1}`) fails loudly instead of counting as a pin: it looks pinned while the real number sits in an env file no gate opens. The mechanism, not the intuition: `Checkpoint::acquire()` returns true unconditionally when a schedule carries no `->lock()`, and none does. The durable checkpoint pool shares *state*, never *exclusion* — `MessageGenerator` re-reads it each poll and suppresses a tick the other replica already saved — so a second replica **can** duplicate a tick rather than always doing so, in the window from the winner's `acquire()` to its `save()` (which runs after the handler). Eight of the nine are idempotent sweeps that mostly collapse in that race; `NotifyLockedIdentitiesMessage` holds the window open for an SMTP exchange and mails a person, sending before it stamps the suppression window. That is the tick the pin exists for.

    What a green proves is that the transport **name** is wired to the right service and that no root compose file over-declares that service: not that the worker runs, that the service is deployed, that `--time-limit` is sane, or that any tick ever produced a log line. **And the pin binds the file, not the deploy** — measured by running it, not by planning it: `docker compose up -d --scale <service>=2` leaves **two containers running** for a service declaring `replicas: 1`, exit 0, exactly as for a service declaring no count. The gate refuses a duplicated clock committed to the repository; one asked for on a command line leaves no trace here, and neither does a service that inherits the consume command through `extends` (nothing in the tree uses it — named rather than guarded). Closing those vectors needs `symfony/lock`, declined in #261 with this asymmetry as the recorded cost.

-   **A schedule with a period longer than the worker's life must be `->stateful()`.** The checkpoint is otherwise process memory, so the first run date is computed from the moment the worker booted — and both workers run `messenger:consume` under `--time-limit=3600` with `restart: unless-stopped`, so the process is replaced hourly and the clock restarts with it. A `1 day` period then never comes due, in dev or prod, while `debug:scheduler` still prints it and every gate stays green. Each schedule's unit test asserts `getSchedule()->getState()` is not null — that assertion is the only thing in the suite that goes red on the state being dropped entirely.

    **Surviving the hourly restart is the easy half; the checkpoint has to survive the DEPLOY, and the pool it sits on decides that.** That unit assertion is satisfied by any pool at all, which is how the checkpoint sat on the autowired `app` pool — the filesystem adapter under `var/cache`, and **no production service mounts a volume there**, so a deploy recreates the container with an empty checkpoint. `Checkpoint::acquire()` then seeds it to `now` and `PeriodicalTrigger` anchors the period at that instant, because `'1 day'` does not match its `canBeConvertedToSeconds()` regex (`sec|second|min|minute|hour` — no `day`) and takes the `DatePeriod` branch. The cost is not the one period of delay the docblocks used to claim: at a deploy cadence at or below the period the tick is re-anchored before it ever comes due. **Measured over seven simulated days, a worker polling every five minutes: cadences of 6 h, 12 h and 24 h each fire the daily ticks 0 times against the 7 expected** (25 h gives 6, 72 h gives 4). That covered the `audit_log` retention prune and both GDPR reconciliations. Every `#[AsSchedule]` therefore names `#[Autowire(service: 'cache.scheduler_checkpoint')]`, a Postgres-backed pool (`cache.yaml`, table created by migration for the reason the messenger transport carries `auto_setup=0`). Gate: `SchedulerCheckpointDurabilityGateTest`, which walks `src` for `#[AsSchedule]`, pins the population so the walk itself is falsifiable, and asserts both halves — every schedule's state IS that pool service, and the pool is on an adapter readable from a container that did not write it. Deleting the pool is fail-loud rather than silent: the container stops resolving. A green says where the checkpoint is written, and nothing about whether a tick ever ran.
-   **A validation constraint and its validator are bound by NAME, so never separate them.** `Constraint::validatedBy()` returns `static::class . 'Validator'`; move a constraint one directory and the derived name points at a class that does not exist, so every annotated property fatals on validation — while **PHPStan, deptrac and the whole unit suite stay green**, because a constraint's test instantiates the validator directly (`ConstraintValidatorTestCase::createValidator()`) and never travels through `validatedBy()`. That is exactly how a layering "fix" that moved `EnumType` out of `Shared/Validation/Infrastructure/` shipped a runtime fatal past four green gates. The validator cannot follow inward either — it extends `ConstraintValidator`, which is framework runtime. `BankAccount → EnumType` therefore stays as a documented baseline entry rather than being "paid" by a move; the three ways to split the pair are all worse, and are argued in [`../docs/adr/external-dependencies-in-domain.md`](../docs/adr/external-dependencies-in-domain.md). Gate: `ConstraintValidatorResolutionGateTest` resolves `validatedBy()` for every concrete `Constraint` under `src` and fails when the target is missing. A green proves the name loads — not that the validator is correct, and not that a constraint returning a **service id** instead of a class name is wired (that indirection fails here on purpose).
-   **A validation message may describe the rule, never the value (`ConstraintMessageValueGateTest`).** A violation message is interpolated with what it rejected, and `ValidationFailedException::getMessage()` renders the whole list — which reaches the per-error log line AND the Sentry event, two sinks no erasure path touches. `RedactionDenylist` cannot help: it strips by KEY and the key is `exception_message`. Measured: `Assert\Bic`'s default `ibanMessage` interpolates `{{ iban }}`, `BankAccount::$iban` is `#[PersonalData]`, and a mismatched BIC wrote a real account number into `var/log` on a live request. The gate walks every class under `src` declaring a constraint — class-level attributes included, since `#[UniqueEntity]` lives there — and refuses any message placeholder outside the configuration allowlist (`{{ limit }}`, `{{ charset }}`, `{{ choices }}`, `{{ compared_value }}`). Its universe is deliberately NOT scoped to `#[PersonalData]`: the command DTOs hold the same values straight off the wire, declare no such attribute, and are the layer that rejects first. A green proves no *declared* message interpolates input — never that a hard-coded message is safe, and never anything about a constraint nested inside a composite (`All`, `Sequentially`, `Collection`), which exposes no message option of its own.

-   **Deptrac architecture gate (`make php.deptrac`).** AST-aware boundary check over `src`, in `php.quality` / `php.quality.dry-run` (CI gates on it). Config `tools/deptrac/deptrac.yaml` enforces three things at once: hexagonal layering (`Infrastructure → Application → Domain`), bounded-context isolation at the **module** level (`Backoffice/Bank` ⊥ `Backoffice/BankAccount`), and the Domain/Application external-dependency allowlist (only `Psr\*`, `symfony/uid` and the passive-metadata attribute namespaces inward; frameworks confined to `Infrastructure`). Using it:
    -   **A new module** must be registered in `deptrac.yaml` (`layers` + `ruleset`) — it does not auto-discover (the sibling `php.lint.bounded-context` does, so cross-context is still covered meanwhile). Follow the existing per-module block; `Domain` reuses the `*domain` anchor. **Nested `Shared/` modules are the exception** — the `src/Shared/(.*/)?Domain` collectors auto-fold them into the `Shared.*` layers, so the event backbone `Shared/Event/{Domain,Application,Infrastructure}` (hardened `DomainEvent`, `EventBus`, the raw-DBAL `event_store`, mapper/serializer/upcaster, projection runner) needs no separate registration. Its `ProjectionRunner` owns its transaction boundary through the `TransactionManager` port like every write-side use case, so no `EntityManagerInterface` is grandfathered for it.
    -   **A violation** means a real boundary breach: fix the dependency (move the framework use to `Infrastructure`, reference another module by id + event, point the layer inward). Do **not** silence it by editing the baseline.
    -   **`tools/deptrac/deptrac.baseline.yaml` is generated**, never hand-edited — it grandfathers inner-layer framework debt that predates the gate (ratchet; paying it down is issue #305). Regenerate only when you *reduce* debt: `make php.deptrac.baseline` (runs `tools/deptrac/regen-baseline.sh`, which strips the cross-context seams deptrac re-dumps and re-prepends the header).
    -   **A genuine published cross-context seam** goes in `skip_violations` in `deptrac.yaml`, kept in sync with `api/.bounded-context-allowlist` — never in the baseline.
-   **PostgreSQL Migrations:**
    -   Migrations are **transactional** (the default). The migrate pipeline runs `--all-or-nothing` and the `php` entrypoint migrates on boot — doctrine-migrations **rejects** `isTransactional() => false` under all-or-nothing (`MigrationConfigurationConflict` breaks stack boot). Plain `CREATE INDEX` is fine at current table sizes.
    -   `CREATE INDEX CONCURRENTLY` (which requires `isTransactional() => false`) is reserved for a genuinely large, write-hot table, and runs **out-of-band**: a deliberate one-off `doctrine:migrations:migrate --no-all-or-nothing` for that deploy — never by weakening the default pipeline.
    -   Use `IF [NOT] EXISTS` for idempotency and resilient rollbacks.
    -   Review lock impact of non-concurrent operations (e.g., `ALTER TABLE`).
    -   Always verify migrations in staging before production.
-   Add async jobs via Messenger buses; don't spawn processes or inline long work in request handlers. See [`docs/architecture-api.md`](../docs/architecture-api.md) for the `event_store` reproducible-log + projector/reactor flow (ADR [`docs/adr/event-store-and-projections.md`](../docs/adr/event-store-and-projections.md)).
-   **The Behat step vocabulary is an asset to spend, not inventory to audit.** Every idle step is an assertion somebody already built and nobody is making, which is a coverage signal, not dead code. **The inventory is [`.behat-step-vocabulary`](.behat-step-vocabulary)** — every declared pattern classified `used` / `idle` / `manual` / `refused`, gated by `make php.lint.step-vocabulary`. Read it there and nowhere else, this page included: the counts and the examples that used to live in this paragraph had drifted within weeks (205 patterns against 209, 47 features against 49, and one of the three contexts it named as wholly idle was reached by eighteen step invocations across thirteen scenarios) with every gate green, because nothing recomputed any of it. That drift is what the registry and its gate exist to make impossible. The three rules below pull the same way.
    -   **Never delete a step for being unused, and never write a new one before searching.** Deleting shrinks what the suite *can* say; the idle ones are there to be picked up as features arrive — and the gate makes the subtraction visible, because a classification whose pattern is gone fails the build. Before adding a step definition, read [`.behat-step-vocabulary`](.behat-step-vocabulary), then confirm against the running suite — `make php.behat c='-dl'` for all of it, `make php.behat c="-d '<text>'"` to search it and print each match's `Context::method()` — and reuse or extend what exists. A near-duplicate phrasing for an assertion that already exists is the actual waste: it splits the vocabulary and leaves both halves half-used. **Nothing detects that split**; the registry is the list to search so a reader can avoid causing one.
    -   **When you touch a feature, spend the idle steps that fit it.** Writing or editing a scenario is the moment to ask what else this behaviour lets you pin — a payload field that should be absent, a collection whose size is the point, an event that must *not* have been published. Reaching for `there should not have been an outbox event created on the queue :queueName containing:` costs one line and pins a claim the scenario was only implying. That is where the confidence comes from: an assertion that exists and is never made proves nothing.
    -   **A step that is deliberately not for scenarios says so at its declaration, and is classified in the registry.** Two kinds: `manual` — a debugging escape hatch (`I print all outbox events`) or a manual override of an automatic `BeforeScenario` hook, which committing into a scenario either prints noise on every CI run or blanks state the scenario had already built; and `refused` — a superseded phrasing kept registered only so reaching for it hands back the canonical form instead of "step undefined". Neither is coverage debt, which is why they are counted apart from `idle`, and the gate fails if a committed scenario calls either.
-   **If `src` imports it, `require` declares it (`make composer.check.missing-deps`).** composer-require-checker reads the PSR-4 map, so every symbol reachable from the *production* autoload must be satisfied by `require` — `require-dev` does not count, and a package arriving transitively counts for nothing. Four packages were being imported by `src` without ever being asked for (`monolog/monolog`, `symfony/cache-contracts`, `symfony/finder`, `symfony/security-http`): each rode in behind a bundle, so the day `security-bundle` stops depending on `security-http` the app breaks with no lock signal. Declaring them changed no installed version — only the lock's `content-hash`.

    The one legitimate escape is a **dev-only symbol that the checker cannot recognise as dev-only**, which is what the `symbol-whitelist` in [`tools/composer-require-checker/composer-require-checker.json`](tools/composer-require-checker/composer-require-checker.json) holds: the dev bundles named by `config/bundles.php` (a `scan-files` entry), and `Twig\Environment`, a constructor argument of `WebDebugToolbarLoaderController`, which carries `#[When(env: 'dev')]` + `#[When(env: 'test')]`. **The config is strict JSON and rejects any key it does not know** (`_comment is not a known option`), so the reasoning cannot live beside the entry — it lives here and at the class.

    **What holds that whitelist honest is the prod container compile — `make php.lint.prod-container`.** Strip the `#[When]` attributes and `cache:warmup --env=prod` dies with `Cannot autowire ... Twig\Environment but no such service exists` — measured, exit 2 against exit 0 for the same tree with them. That gate exists because for a long time nobody performed it: `.github/workflows/ci.yml` bakes only `compose.yaml` + `compose.dev.yaml`, no workflow names `compose.prod.yaml` or `frankenphp_prod`, and the container is compiled by `composer run-script post-install-cmd` inside the prod image build — so the first reader of a `#[When]`-guarded class was the deploy. It now runs in `php.quality[.dry-run]`, which is what CI already invokes, together with `composer.check.missing-deps` (this check itself, which CI had never run either).

    Both gates compile or resolve against the **dev** vendor tree, since that is what the dev image installs. A `src` class importing a `require-dev` package therefore passes `php.lint.prod-container` and dies under the image's `composer install --no-dev`; `composer.check.missing-deps` is the half that catches that, which is why the two are wired together rather than either being treated as sufficient.
-   Keep lines under 120 characters; wrap longer ones unless breaking them hurts readability (e.g. long URLs, string literals).

## Security review (mandatory on every change)

Every PR — even small fixes — runs the checklist in the root [`../CLAUDE.md`](../CLAUDE.md) ("Security review on every change"); its **Backend (`api/`)** list is authoritative. Quick recap of what to walk before pushing: parameterised Doctrine queries (no `${…}` reaching SQL/DQL); a Security voter / `IsGranted` per new controller/handler (or a documented public route); `#[Assert\…]` DTOs via `#[MapRequestPayload]`/`#[MapQueryString]`, `Validator::ensure()` for other inputs, `Uuid::ensure()` for route ids (400 `invalid-uuid` before any lookup; absent valid id → 404); no audit fields (`id`, `createdAt`, `updatedAt`) exposed to client payloads; RFC 9457 errors with no stack-trace/DB-string leak outside `dev`; no `.env*.local`/secrets in the diff; CORS/CSRF/Mercure allowlist unbroadened; reversible, PII-free, no-untracked-`DROP TABLE` migrations; idempotent Messenger handlers. If a class doesn't apply, say so in the PR rather than silently skipping.
